# Фильтры и операторы фильтра

## Общий набор — для каждого «обычного» поля {: #generic-set }

Регистрируется для **каждого** поля самой модели, какой бы ни был его тип в Python:

`exact` (без окончания), `not`, `in`, `not_in`, `isnull`, `not_isnull`, `gte`, `lte`, `gt`, `lt`,
`range` (ровно 2 значения), `contains`, `startswith`, `endswith`, `iexact`, `icontains`, `istartswith`,
`iendswith`, `search`, `posix_regex`, `iposix_regex`, а в PostgreSQL ещё `trigram_similar`,
`trigram_word_similar`, `trigram_strict_word_similar` (см.
[Поиск по тексту — сходство по триграммам](../dialects/postgresql/text-search.ru.md#trigram-similarity-and-unaccent)).

`CharField`/`TextField`/`CitextField` в PostgreSQL принимают ещё часть пути `unaccent`:
`filter(name__unaccent__icontains="saldana")` сравнивает текст без диакритических знаков.

`DateField`/`TimeField`/`DatetimeField` получают также свои операторы по частям даты и времени — см.
[Операторы по частям даты и времени](#date-part-lookups) ниже; у полей других типов их нет
(`FieldError`, как для любого другого неизвестного окончания).

Все варианты `contains`/`startswith`/`endswith`/`iexact`/`i*` и `posix_regex`/`iposix_regex` сначала
приводят левую часть к тексту — формально их можно вызвать и для числового поля, хотя это редко
нужно; число с плавающей точкой или десятичное читается на любой базе так, как его пишет PostgreSQL
(`2`, а не `2.0`). `CitextField` остаётся `citext`, поэтому эти операторы сравнивают без учёта
регистра (и `posix_regex` тоже).

```python
await Book.objects.filter(title__icontains="dispossessed")
await Book.objects.filter(published_at__year=1974)
await Author.objects.filter(created_at__range=(start, end))
await Author.objects.filter(created_at__range=(start, None))   # без верхней границы: created_at >= start
await Author.objects.filter(created_at__range=(None, None))    # каждая строка без NULL
```

`range` принимает `None` на месте любой границы (или обеих) — тогда проверка идёт без этой границы
вместо полного `BETWEEN`; передавайте кортеж как есть, отдельно обрабатывать `None` не нужно.
`in`/`not_in` принимают любой итерируемый объект, как в Django, — список, кортеж, множество,
`frozenset`, `range`, генератор, `dict.keys()`/`.values()` — и читают его ровно один раз; строка или
байты дают `UnSupportedError`, а не сравниваются по символам. `field=None` и `field__iexact=None`
означают `field__isnull=True`. `isnull`/`not_isnull` требуют настоящий `bool` — строка (например,
неразобранный параметр запроса) даёт `UnSupportedError`, а не проверку на истинность.

`posix_regex`/`iposix_regex` требуют подключения с регулярными выражениями
(`features.supports_posix_regex`): это любое подключение PostgreSQL и подключение SQLite, в адресе
которого есть `?install_regexp_functions=true`. На любом другом подключении фильтр с ними даёт
`UnSupportedError` до выполнения запроса.

!!! warning "`posix_regex`/`iposix_regex` в SQLite: никогда не передавайте непроверенный ввод"
    PostgreSQL выполняет их своими операторами `~`/`~*`, а в SQLite своего движка регулярных
    выражений нет — там hare-orm использует `re.search()` из Python. Модуль `re` в Python не защищён от
    катастрофического перебора с возвратом: неудачный шаблон может «повесить» всё соединение на
    данных обычной длины, каким бы коротким ни был сам шаблон (ReDoS). Для шаблона, который написали
    вы сами, это нормально; шаблон от пользователя этому оператору в SQLite не передавайте никогда.

    Перевод шаблона сам стоит времени и памяти, ещё до сравнения с первой строкой. В `re` нет
    классов POSIX, поэтому каждый `[[:upper:]]`/`[[:punct:]]`/... превращается в явный список всех
    подходящих диапазонов Unicode — несколько тысяч символов исходного текста `re` на класс. Шаблон
    короче 1000 символов из таких классов (`[[:upper:]]`, повторённый 90 раз) разрастается до более
    чем 600000 символов, и его сборка занимает около секунды и несколько мегабайт — для каждого нового
    шаблона (сохраняются только последние шаблоны). `iposix_regex` ещё и разворачивает каждую букву и
    диапазон в варианты регистра. Ограничивайте длину и содержимое любого шаблона, который писали не
    вы, или выполняйте такой поиск в PostgreSQL.

    В SQLite шаблон сравнивается так же, как расширенное регулярное выражение PostgreSQL (в UTF8):
    `.` совпадает и с переводом строки, `$` — только с концом текста, а классы POSIX (`[[:upper:]]`,
    `[[:alpha:]]`, `[[:space:]]`, ...) охватывают весь диапазон Unicode (`[[:digit:]]` — это `0-9`, как
    в PostgreSQL). `iposix_regex` сравнивает символ шаблона с ним самим и с его односимвольными
    вариантами в верхнем и нижнем регистре, как `~*`: `i` совпадает с `I`, но не с турецкой `İ`, а
    `İ` совпадает с `i`; `[[:upper:]]`/`[[:lower:]]` совпадают с любой буквой.

`iexact`/`icontains`/`istartswith`/`iendswith` и `Upper()`/`Lower()` меняют регистр посимвольно на
обоих диалектах, как PostgreSQL: символ, полное изменение регистра которого дало бы несколько
символов, сохраняет односимвольный вариант или остаётся как есть (`ß` и `ﬀ` не меняются, поэтому
`straße` не совпадает с `STRASSE`; `İ` в нижнем регистре — это `i`).

## Операторы по частям даты и времени {: #date-part-lookups }

`DateField`, `TimeField` и `DatetimeField` получают только те части, которые есть у того, что они
хранят:

| Поле | Части |
|---|---|
| `DateField` | `year`, `iso_year`, `quarter`, `month`, `week`, `week_day`, `iso_week_day`, `day` |
| `TimeField` | `hour`, `minute`, `second`, `microsecond` |
| `DatetimeField` | все двенадцать, а также `date` и `time` |

`week` и `iso_year` следуют ISO-8601, `week_day` считает от 1 (воскресенье) до 7 (суббота), а
`iso_week_day` — от 1 (понедельник) до 7, как в Django. `date`/`time` у `DatetimeField` сравнивают его
дату или время суток (значение `date`/`time` или его текст ISO). После каждой части можно добавить
сравнение: `not`, `gt`, `gte`, `lt`, `lte`, `in`, `not_in` и `range` (`published_at__year__gte=2020`,
`starts_at__date__range=(start, end)`, `created__week_day__in=[1, 7]`).

Часть, которой у поля нет (`a_date_field__hour=...`, `a_time_field__year=...`), не зарегистрирована
вовсе — `FieldError`, как для любого другого неизвестного окончания, а не бессмысленное извлечение в
базе. У полей, которые не хранят дату или время, этих частей тоже нет.

```python
await Book.objects.filter(published_at__year=1974)
await Event.objects.filter(scheduled_on__week=3)
await Shift.objects.filter(starts_at__hour=9)
await Order.objects.filter(created_at__date=date(2026, 1, 5), created_at__hour__lt=12)
```

### Часовые пояса у `DatetimeField` {: #time-zone-semantics-on-datetimefield }

Части `DatetimeField` берутся из **времени на часах, которое сам hare-orm записывает и читает** для
поля, а не обязательно в том поясе, в котором база показывает значения в сеансе:

- **`use_tz=True`**: в настроенном поясе `timezone` (`Hare.init(timezone=...)`) — в том же, в который
  `DatetimeField.from_db_value()` переводит каждое прочитанное значение.
- **`use_tz=False`**: во времени на часах в том виде, в котором оно было записано, — в том же значении
  без пояса, которое проходят туда и обратно `DatetimeField.to_db_value()`/`from_db_value()`. В
  SQLite это получается само (колонка хранит этот же текст без пояса, переводить нечего). В
  **PostgreSQL** колонка и при `use_tz=False` остаётся `TIMESTAMPTZ`, а сам PostgreSQL иначе всегда
  берёт части в поясе своего сеанса, что молча расходится с местным временем, которым пользовался
  записывающий процесс, когда эти пояса различаются. hare-orm поправляет это, указывая при извлечении
  **местный пояс системы** (`AT TIME ZONE <пояс IANA>`), а не постоянное смещение: постоянное смещение
  ошиблось бы для даты по другую сторону перехода на летнее время.

  Чтобы узнать имя местного пояса IANA, нужен необязательный пакет `tzlocal`:

  ```bash
  pip install hare-orm[tzlocal]
  ```

  Без него оператор по части даты у `DatetimeField` в PostgreSQL при `use_tz=False` даёт
  `ConfigurationError` с подсказкой по установке — только в этом сочетании (PostgreSQL + `use_tz=False`
  + оператор по части даты); больше `tzlocal` ничему не нужен, в том числе при `use_tz=True` и в
  SQLite.

Чтобы брать части в другом поясе для блока кода — например, в поясе пользователя, — оберните его в
`Timezone.override()` (`from hare.utils import Timezone`), как `timezone.override()` в Django:

```python
with Timezone.override("Europe/Moscow"):
    orders_today = await Order.objects.filter(created_at__date=moscow_today).count()
```

Внутри блока (и в задачах, которые он запускает) `Timezone.name()` возвращает этот пояс, поэтому
операторы по частям даты и времени (`__date`, `__year`, `__hour`, ...), `Extract*` и `Trunc*` берут
части в нём, а дата-время без пояса читается в нём же; значения даты-времени по-прежнему возвращаются
как те же моменты. Пояс задаётся именем IANA или объектом `ZoneInfo` — неизвестный пояс или
постоянное смещение без имени IANA дают `ConfigurationError`. Отдельное выражение получает свой пояс
через `tzinfo=` — см. [Функции даты](functions.ru.md#date-functions).

## Прямые `ForeignKeyField` / `OneToOneField` {: #forward-foreignkeyfield-onetoonefield }

Оператор по имени самой связи работает с её колонкой ключа, как в Django: `author__isnull=True`,
`author__in=[author1, author2]` (объекты или значения ключа вперемешку), `author__not_in=[...]`,
`author__gt=5`, `author__in=Author.objects.filter(...)` — в `filter()`, `exclude()`, `Q` и `When`, так же, как
`author_id__...`. Объект заменяется значением своего `to_field` (первичного ключа, если у связи не
задан `to_field=`); несохранённый объект или объект другой модели дают `QueryError`, как и такой
оператор у связи с составным ключом (фильтруйте по каждой колонке ключа отдельно). Имя поля связанной
модели (`author__name`) по-прежнему фильтрует через соединение таблиц.

## Длинные списки `__in` {: #large-in-lists }

Длинный список `__in`/`__not_in` передаётся одним параметром, поэтому его длина не ограничена
ограничением драйвера на число параметров: PostgreSQL использует `= ANY($1::type[])` начиная с 20
значений, SQLite — `IN (SELECT value FROM json_each(?))` начиная с 20 значений
(`SQLITE_IN_JSON_ARRAY_THRESHOLD`), с теми же правилами сравнения, что и обычный `IN (...)`, для целых
чисел, текста, чисел с плавающей точкой, `Decimal`, дат, даты-времени, `UUID`, `bool` и `bytes`. Такой
список держит один план запроса при любой длине. Так же
работают операторы «многие-ко-многим» и обратного внешнего ключа (`tags__in=`, `children__not_in=`) и
`__in` у вычисляемого значения: значение без известного типа поля (`RawSQL`, `Count()` в сравнении в
`HAVING`) в PostgreSQL получает тип по своим значениям — целые как `BIGINT`, текст как `TEXT` и так
далее; список со значениями разных типов остаётся в обычном виде. `Length()` и
`ExtractYear()`/`ExtractMonth()`/`ExtractDay()` — целые числа, а `StringAgg()` — текст, каким бы ни
был их аргумент, поэтому `__in` по ним передаёт целые числа или текст.

Составной первичный ключ фильтруется через `pk` так же, как ключ из одной колонки: `pk=(1, 2)`,
`pk__in=` со списком кортежей, запросом, `values_list("pk", flat=True)` или объединением
(`(a, b) IN (SELECT ...)`), а связь с ним сравнивает весь ключ — `bay=obj`, `bay=(1, 2)`, `bay__in=`,
`bay__not`, `bay__isnull`; `update(bay=obj)` (или кортеж, или `None`) записывает каждую колонку ключа.
`pk__in=[(a, b), ...]` у составного первичного ключа — одна проверка строки значений,
`(a, b) IN ((1, 2), ...)`; длинный список передаётся одним массивом на колонку в PostgreSQL
(`IN (SELECT * FROM unnest($1::int[], $2::int[]))`, начиная с 20 строк) и одним массивом JSON строк в
SQLite (`IN (SELECT json_extract(value, '$[0]'), ... FROM json_each(?))`, начиная с 20 значений),
поэтому его длина тоже не ограничена. `__in`/`__not_in` связи «многие-ко-многим» с составным ключом
работают так же. `add()`/`remove()` связи «многие-ко-многим» и проверка `on_delete=PROTECT` при
массовом удалении тоже справляются с любым числом объектов — `add()` делит свой `INSERT` на столько
команд, сколько требует ограничение на число параметров, в одной транзакции.

## `ManyToManyField` {: #manytomanyfield }

`exact`, `not`, `in`, `not_in` (все — через промежуточную таблицу; для связанной модели с составным
первичным ключом каждое значение — кортеж ключа или объект). `isnull`/`not_isnull` доступны всегда, в
`filter()`, `exclude()` и `Q`: `tags__isnull=True` находит строку без связанных строк. Связь
учитывается, только если и связанная строка, и (для `through=Model`) промежуточная строка проходят
собственные ограничения мягкого удаления и арендатора — так же, как оператор по обратному внешнему
ключу пропускает мягко удалённую связанную строку.

## Обратные внешние ключи {: #backward-fk-relations }

`exact`, `not`, `in`, `not_in`, `isnull`, `not_isnull`. Для модели-владельца с составным первичным
ключом значение — объект или кортеж его ключа (`cemps=obj`, `cemps__in=[obj, (1, 2)]`), сравнение идёт
по колонкам.

Как в Django, `relation=None` у связи «ко многим» («многие-ко-многим» или обратный внешний ключ) — это
`relation__isnull=True`, строки без связанных строк; `relation__not=None` — это
`relation__isnull=False`.

Оператор по имени самой связи «ко многим» (`tags=tag`, `tags__in=[...]`, `tags__not=...`,
`books__isnull=...`) — это тот же оператор по первичному ключу связанной модели (`tags__id=tag.id`),
как в Django. Внутри одного вызова `.filter()` он делит `JOIN` с другими операторами через эту связь
(`filter(tags=1, tags__name="y")` требует одного тега, подходящего под оба условия), отдельный вызов
`.filter()` получает свой `JOIN` (`filter(tags=1).filter(tags=2)` находит строку, связанную с обоими,
— и дальше по пути, `Task.objects.filter(emp__tags=1).filter(emp__tags=2)`), а проверки размножения строк
агрегатами видят его как любой другой `JOIN` — `filter(tags__in=[...]).annotate(n=Count("tags"))`
считает только подходящие теги. Оператор «многие-ко-многим» сравнивает колонку связи в промежуточной
таблице, поэтому сама связанная таблица не присоединяется.

## `JSONField` {: #jsonfield }

Полностью отдельный набор (общий набор выше **не** применяется): `exact`, `not`, `in`, `not_in`,
`isnull`, `not_isnull`, `gt`, `gte`, `lt`, `lte`, `range` (в порядке `jsonb` — см.
[`F("data__key")`](expressions.ru.md)), `contains`, `contained_by`, `has_key`,
`has_keys`, `has_any_keys`, `filter` (оператор по вложенному пути в словаре).

Любое другое имя после поля — это ключ, как преобразования ключей в Django:
`filter(data__owner__name="a")`, `filter(data__score__gt=10)`, `filter(data__tags__0="x")`,
`exclude(data__owner__isnull=True)` читают значение JSON по этому пути и принимают его операторы — так
же, как фильтр по [`F("data__owner__name")`](expressions.ru.md). Имя оператора сразу
после поля (`data__contains`) — это оператор для всего значения; ключ, названный как оператор,
доступен через `__filter` (`data__filter={"contains": 1}`). Те же пути работают внутри вычисляемого
значения JSON (`annotate(summary=JSONObject(...)).filter(summary__total__gte=10)`) и после связи
(`filter(owner__data__plan="pro")`). Все они работают одинаково в PostgreSQL и SQLite: в SQLite они
следуют правилам `jsonb` через `json_extract()` и несколько встроенных функций SQL, которые hare
регистрирует в каждом соединении. `__filter={...}` поддерживает вложенные ключи-операторы: `not`,
`isnull`, `not_isnull`, `has_key`, `has_keys`, `has_any_keys`, `in`, `not_in`, `gte`, `gt`, `lte`, `lt`,
`range`, `contains`, `startswith`, `endswith`, `iexact`, `icontains`, `istartswith`, `iendswith`, `year`,
`quarter`, `month`, `week`, `day`, `hour`, `minute`, `second`.

Тип сравнения определяется значением: число сравнивается как число, строка — как текст
(`{"name__gt": "b"}`), `bool` — как логическое значение, `date`/`datetime` — как момент времени.
`datetime` с поясом сравнивается как `timestamptz` с учётом собственного смещения сохранённой строки;
`datetime` без пояса сравнивает цифры времени на часах, не учитывая сохранённое смещение. Сохранённое
значение другого типа JSON никогда не совпадает — в том числе строка при сравнении дат, если это не
дата или дата-время ISO-8601 (или она называет день, которого нет в этом месяце): такая строка просто
не подходит. Значение `dict`/`list` сравнивается со значением `jsonb` по пути (`{"a": {"x": 1}}`,
`{"a__in": [[1, 2]]}`); принимают его только `exact`/`not`/`in`/`not_in`.
`contains`/`startswith`/`icontains`/... принимают строку (другое значение даёт `QueryError`) и
совпадают только с сохранённой строкой. Оператор можно записать и вложенным словарём с одним ключом
— `{"enabled": {"not": False}}` то же самое, что `{"enabled__not": False}` (словарь с одним ключом,
который является именем оператора, всегда читается как оператор; чтобы найти такой объект буквально,
используйте `__contains`). Значения одного списка `in`/`not_in` должны быть одного типа, иначе `QueryError`, —
кроме `None`, который совпадает с JSON `null` или отсутствующим ключом (`{"a__in": [1, None]}`
совпадает с числом `1`, с `null` и с отсутствием `a`; `not_in` их отбрасывает). Часть пути из цифр —
это ключ объекта или индекс массива; как индекс она совпадает только внутри массива, никогда со
скалярным значением. Отрицательный индекс отсчитывается с конца массива (`{"scores__-1": 30}`, также
`F("data__scores__-1")`).

`exact`/`not`/`in`/`not_in` по всей колонке сравнивают значения JSON на обоих диалектах — порядок
ключей, пробелы и разница между `1` и `1.0` не важны (SQLite приводит обе стороны к единому виду,
PostgreSQL сравнивает `jsonb`); `None` в списке `in`/`not_in` означает колонку SQL `NULL`.
`contains`/`contained_by` следуют `@>`/`<@` из `jsonb`: объект содержит другой, если в нём есть каждый
ключ другого с содержащимся значением; массив содержит другой, если каждый элемент другого содержится
в каком-то его элементе (порядок и повторы не важны); и только массив верхнего уровня содержит также
отдельное скалярное значение (`data__contains="bar"` совпадает с `["foo", "bar"]`).

```python
await Widget.objects.filter(values__contains=["approved"])
await Widget.objects.filter(config__filter={"enabled": {"not": False}})
```

### Наличие ключа: `has_key` / `has_keys` / `has_any_keys` {: #key-existence }

`?` / `?&` / `?|` из `jsonb` PostgreSQL, с теми же результатами в SQLite. Они проверяют ключи
**верхнего уровня** сохранённого объекта (вложенный ключ не считается):

| Оператор | Значение | Подходят строки, где |
|---|---|---|
| `data__has_key="breed"` | строка | ключ есть |
| `data__has_keys=["a", "b"]` | список строк | есть **все** ключи (пустой список подходит к каждой строке, где есть документ) |
| `data__has_any_keys=["a", "b"]` | список строк | есть **хотя бы один** ключ (пустой список не подходит ни к чему) |

Внутри `__filter` эти три работают как ключи-операторы на вложенном пути —
`data__filter={"pet__has_key": "breed"}` проверяет объект в `data->'pet'`, а просто
`data__filter={"has_key": "pet"}` проверяет саму колонку. Ключ со значением JSON `null` считается
существующим. Колонка SQL `NULL` (документа нет вовсе) не подходит ни под один из трёх. Как и в самом
PostgreSQL, `?` также совпадает со строковым элементом массива верхнего уровня или со строкой
верхнего уровня, равной ключу.

```python
await Pet.objects.filter(data__has_key="breed")
await Pet.objects.filter(data__has_keys=["breed", "age"])
await Pet.objects.filter(data__has_any_keys=["breed", "color"])
await Pet.objects.filter(data__filter={"owner__has_key": "phone"})
```

!!! warning "`__isnull` на пути JSON означает, что значения там нет: и JSON `null`, и отсутствующий ключ"
    `__filter={"key__isnull": True}` (и `{"key": None}`) построен на извлечении текста через `->>`,
    которое возвращает SQL `NULL` в **трёх** случаях: ключ есть со значением JSON `null`, ключа нет в
    объекте, вся колонка JSON равна SQL `NULL`. `isnull=True` подходит ко всем трём; `isnull=False` —
    только к существующему значению, не равному `null`. Так это устроено, это не ошибка (у операторов
    `jsonb` в Django та же неоднозначность). Чтобы различить случаи, сочетайте `isnull` с `has_key`:

    ```python
    # ключ есть, значение — JSON null
    Q(data__filter={"key__isnull": True}) & Q(data__has_key="key")
    # ключа нет в объекте (или документа нет вовсе)
    Q(data__filter={"key__isnull": True}) & ~Q(data__has_key="key")
    # ключ есть с настоящим (не null) значением
    Q(data__filter={"key__isnull": False})
    ```

## Как работает NULL {: #null-semantics }

`exclude()`/`~Q(...)` следуют описанному в Django поведению `exclude()`: строка остаётся в
результате, **если только исключаемое условие не равно точно `TRUE`** — и `FALSE`, и
`NULL`/`UNKNOWN` (трёхзначная логика SQL) считаются «не подошло». Для колонки, допускающей `NULL`:

```python
await Player.objects.exclude(nick="n1")   # оставляет строку, где nick IS NULL — NULL не равен "n1"
await Player.objects.exclude(score__gt=1) # оставляет строку, где score IS NULL — NULL не больше 1
await Player.objects.exclude(team=some_team)          # оставляет строку, где team IS NULL (команды нет)
await Player.objects.exclude(team__rank=1)            # так же — через связь
```

Это одинаково относится к колонке самой модели и к связи, через которую идёт условие. Для составного
условия (`exclude(Q(a) | Q(b))`) это действует для условия целиком, а не для каждой части: строка
остаётся, если только ВСЁ составное условие не равно `TRUE`.

Колонку без `NULL` это не затрагивает — у неё нет строки `NULL`, которую надо было бы оставить, и SQL
не меняется.

Агрегатное вычисляемое значение, отфильтрованное в `HAVING`, следует тому же правилу:
`annotate(total=Sum("books__pages")).exclude(total__gt=500)` оставляет автора без книг, у которого
`SUM` равен `NULL`.

Тот же принцип «обращаться с `NULL` так, как это сделали бы `not in`/`!=` в Python» действует ещё для
двух операторов:

- `field__not_in=<запрос/Subquery>` / `exclude(field__in=<запрос/Subquery>)`: строка `NULL` в
  результате подзапроса не опустошает весь результат (как это сделал бы `NOT IN (..., NULL)` в SQL,
  который всегда `UNKNOWN`) — значение, которого действительно нет среди значений подзапроса, не
  равных `NULL`, остаётся, как `x not in [1, None]` в обычном Python. `field__in`/`.filter()` со
  списком Python так же обрабатывают `None` внутри списка.
- `field__not=F(other_field)` (или любое другое выражение справа): сравнивается через
  `IS DISTINCT FROM` в SQL (`IS NOT` в SQLite, с тем же смыслом), а не через простое `<>`, — одинаково
  правильно в обе стороны при `NULL`: строка остаётся, если стороны действительно различаются, в том
  числе когда `NULL` только одна из них, и исключается, когда обе `NULL` (два `NULL` не считаются
  различными). Простое значение справа (`field__not="foo"`) этого не затрагивает — только выражение.

## Имена полей из пользовательского ввода {: #field-names-from-user-input }

Значения, переданные в `filter()`/`exclude()`, всегда передаются как параметры, а вот **имена**
полей — в `order_by()`, `values()`/`values_list()`, ключах `filter()`/`exclude()`,
`select_related()`/`prefetch_related()`, `only()` — считаются доверенными: hare-orm разбирает любой
переданный путь через связи и не ограничивает его длину. Каждый шаг добавляет `JOIN` (шаг
«многие-ко-многим» — два), а путь через несколько связей «ко многим» умножает число строк, которые
должна построить база. Поэтому имя, взятое прямо из запроса
(`?sort=company__docs__company__docs__...`), позволяет клиенту заставить базу выполнить сколько
угодно работы — и прочитать поля, которые вы не собирались показывать (`?sort=owner__password_hash`
раскрывает его через порядок строк). Как и в Django, встроенного ограничения глубины нет;
сопоставляйте ввод пользователя с именами полей через белый список:

```python
SORTABLE_FIELDS = {"title": "title", "-title": "-title", "created": "created_at", "-created": "-created_at"}

async def list_articles(sort: str) -> list[Article]:
    ordering = SORTABLE_FIELDS.get(sort)
    if ordering is None:
        raise ValueError(f"неподдерживаемый ключ сортировки {sort!r}")
    return await Article.objects.all().order_by(ordering)
```

Для каждого ключа из белого списка [`get_lookup_info()`](describing-filters.ru.md) сообщает, через какие
связи он проходит и значение какого типа принимает, поэтому параметр запроса можно разобрать до того,
как он попадёт в `.filter()`.

В SQLite запрос, соединяющий больше 64 таблиц, даёт `OperationalError` с этим объяснением.

Имя, которое записывается в текст SQL, — выходное имя `values()`/`annotate()`, ключ JSON в пути
(`data__key`, `F("data__key")`, `data__filter={...}`) — не может содержать нулевой байт (`"\x00"`):
это даёт `ValidationError` до отправки команды, на любой базе. В PostgreSQL готовый текст SQL с
таким байтом (`RawSQL(...)`, `execute(...)`) тоже даёт `ValidationError`, а не ошибку драйвера,
похожую на потерянное соединение; передавайте такое значение параметром.
