# Методы QuerySet

Все методы `QuerySet` — что каждый возвращает, выполняет и какие ошибки даёт, — а затем то, что не
помещается в строку таблицы: порядок `NULL` при сортировке, `Prefetch`, поток строк, рекурсивные
запросы, выборка из таблицы, записанные строки, вставка строк запроса и слияние.

## <a id="method-reference"></a>Список методов

Обозначения: **цепочка** — возвращает новый `QuerySet` (ничего ещё не выполняется); **await** —
возвращает особый объект, который нужно дождаться через `await`; **конечный** — сам
`QuerySet`/`QuerySetSingle` становится объектом для `await`.

Запрос, не закреплённый за подключением через `using()`, выбирает подключение при
каждом выполнении. Поэтому один и тот же объект запроса можно снова выполнить после окончания
транзакции, внутри другой транзакции или из другой задачи — каждый раз используется подключение (или
открытая транзакция), текущее в этот момент.

| Метод | Тип | Что делает |
|---|---|---|
| <code>filter(&#42;args: Q &#124; Exists, &#42;&#42;kwargs)</code> | цепочка | Копирует запрос и добавляет условия через AND. Поддерживает `related__field=...`, позиционные объекты `Q` и условия `Exists(...)`. Как в Django, запрос со срезом (`.limit()`/`.offset()`/`qs[a:b]`) фильтровать нельзя: `filter()`/`exclude()`/`get(**kwargs)` на нём дают `QueryError("Cannot filter a query once a slice has been taken.")` — сначала фильтр, потом срез. Запрос `.values()`/`.values_list()` (или операция над множествами) в роли значения фильтра (`id__in=...`) должен выбирать одну колонку — если больше, будет `QueryError("Cannot use multi-field values as a filter value...")`, а не ошибка базы. |
| <code>exclude(&#42;args: Q &#124; Exists, &#42;&#42;kwargs)</code> | цепочка | То же, но отбрасывает строки, которые подходят под **все** условия вызова вместе, как в Django: `exclude(a=1, b=2)` — это `NOT (a = 1 AND b = 2)`, то же, что `exclude(Q(a=1, b=2))`. Для связи «ко многим» hare ведёт себя иначе, чем Django: условия одного вызова `exclude()` (или одного `~Q(...)`) относятся к **одной и той же** связанной строке, как в `filter()` — `exclude(books__name="a", books__rating=5)` отбрасывает автора, только если одна книга подходит под оба условия, и оставляет автора, у которого одна книга называется «a», а другая имеет оценку 5. В Django условия одного `exclude()` не обязательно относятся к одной строке, поэтому такой автор тоже отбрасывается; чтобы получить это в hare, используйте отдельные вызовы — `.exclude(books__name="a").exclude(books__rating=5)` отбрасывает авторов, у которых любая книга подходит под любое из условий. Каждый отдельный `.exclude()` отбрасывает свои строки. `exclude()` через связь «ко многим» — это подзапрос `NOT EXISTS`, поэтому он не добавляет в запрос `JOIN`: следующий `.filter(books__...)` всё равно строит `JOIN`, который читают `values("books__...")`, `order_by("books__...")` и `Count("books")`. Пустой `Q()` здесь, как и везде, ничего не делает — `~Q()` и `exclude(Q())` подходят под каждую строку. Как обрабатываются колонка или значение `NULL` — см. [Как работает NULL](filters.ru.md#null-semantics) ниже. |
| <code>annotate(&#42;&#42;kwargs: Expression &#124; Term)</code> | цепочка | Добавляет в `SELECT` вычисляемые значения и агрегаты и регистрирует для них операторы фильтра, чтобы потом по ним можно было вызывать `.filter()`/`.exclude()` (условие попадает в `HAVING`, если в нём есть агрегат, — в том числе в выражении, смешивающем агрегат с колонкой, вроде `Count("books") + F("id")`, или когда поле сравнивается с агрегатным вычисляемым значением, `budget__lt=F("total")`; иначе — в `WHERE`). Имя, совпадающее с полем модели (или `pk`), даёт `FieldError`, как и такое имя для выражения в `alias()`/`values()`/`values_list()`: иначе все остальные обращения к нему читали бы вычисляемое значение вместо поля. Значение, которое не является выражением (например, просто строка с именем поля — используйте `F("field")`), даёт `TypeError`, и в `alias()` тоже. Как в Django, `.alias()`, которое ничто не читает — ни фильтр, ни сортировка, ни группировка, ни другое вычисляемое значение, ни поле `values()`, — в запрос не попадает, поэтому его `JOIN` «ко многим» не размножает строки. |
| `alias(**kwargs)` | цепочка | Как `annotate()` — выражение можно использовать в `.filter()`/`.order_by()`, — но в `SELECT` оно попадает, только если `.values()`/`.values_list()` попросят его по имени. `FieldError`, если имя совпадает с полем модели или с `pk`. |
| <code>order&#95;by(&#42;orderings: str &#124; Ordering)</code> | цепочка | `'-field'` — по убыванию (`DESC`); путь внутрь поля JSON или вычисляемого значения (`'-data__score'`) сортирует по значению JSON, в порядке `jsonb` на любой базе; [часть даты](values.ru.md#date-part-paths) (`'-created__month'`) сортирует по этой части; `F('field').asc()`/`.desc()` с `nulls_first=True`/`nulls_last=True` задают, где окажутся `NULL`, — см. [Порядок NULL при сортировке](#null-ordering). Поддерживает `related__field`; имя прямой связи (`'tournament'`), в том числе в конце пути через связь (`'event__tournament'`), сортирует по колонкам её ключа (`tournament_id`, `event__tournament_id`), и в `Meta.ordering` тоже; имя связи «ко многим» или обратной «один-к-одному» (`'events'`, `'-tags'`) сортирует по первичному ключу связанной модели (по строке на каждую связанную строку), а `pk` в конце пути (`'author__pk'`, `'tags__pk'`) — по полям первичного ключа, как в Django, — см. [связи и `pk` в путях к полям](values.ru.md#relation-field-paths). Нельзя вызывать после `.after_cursor()`. Как в Django, запрос со срезом (`qs[a:b]`, `.limit()`, `.offset()`, индекс) нельзя пересортировать — `QueryError("Cannot reorder a query once a slice has been taken.")`; сначала сортировка, потом срез (`order_by("name").limit(2)`). То же относится к `union()` и к операции над множествами из `.values()`/`.values_list()`. `order_by()` без аргументов убирает всю сортировку, включая `Meta.ordering`. `'?'` упорядочивает строки случайно — по `Random()`, новому числу для каждой строки, отдельно или рядом с другими сортировками (`order_by('category', '?')`); база читает все строки, чтобы их отсортировать, поэтому на большой таблице выбирайте строки иначе. |
| `orderings -> tuple[tuple[str, Order], ...]` | свойство | Сортировка, заданная через `order_by()`, — по одной паре `(путь, Order)` на каждую колонку сортировки: `pk` означает все поля первичного ключа, прямая связь — колонки её ключа (`"tournament"` → `"tournament_id"`), `F("score").desc(nulls_last=True)` — `("score", Order.DESC_NULLS_LAST)`. Пусто без `order_by()` (тогда запрос сортируется по `Meta.ordering`, которая сюда не входит, — читайте `Model._meta.ordering`) и после `order_by()` без аргументов, который оставляет запрос несортированным. `before_cursor()` оставляет его как задано; копия запроса его сохраняет, следующий `order_by()` заменяет. `Order` находится в `hare.sql`. |
| `after_cursor(*values)` | цепочка | Постраничный вывод по курсору (по значениям ключа сортировки) вместо `OFFSET` — нужен `.order_by()`; поддерживает `related__field` в сортировке (связь соединяется так же, как в `order_by`), но не вычисляемое значение. У запроса с `.distinct(<поля>)` граница применяется к строкам, которые выбирает `DISTINCT ON` (через `pk IN (SELECT ...)`), как и у `before_cursor()`. |
| `before_cursor(*values)` | цепочка | Предыдущая страница: строки строго **до** значений. Выполняется в точно обратной сортировке (поэтому `.limit(n)` берёт `n` строк, ближайших к курсору) и возвращает строки в исходном порядке `.order_by()` — для объектов, `values()` и `values_list()` одинаково; `first()`/`get()` берут строку прямо перед курсором. Ошибки те же, что у `after_cursor()`. Вместе с `after_cursor()` (в любом порядке) задаёт окно; повторный вызов любого из них заменяет только свою границу. Не поддерживается в `iterator()`/`stream()`. |
| `cursor_values(instance) -> tuple` | синхронно | Значения курсора объекта `instance` для текущего `.order_by()` — передавайте их в `after_cursor()`/`before_cursor()`. Сортировка `related__field` требует загруженной связи (`select_related()`), иначе `QueryError`; связь `NULL` даёт `None`; сортировка по внешнему ключу или «один-к-одному» (`'city__country'`) даёт значение ключа, а не связанный объект; связь «ко многим» или вычисляемое значение дают `FieldError`. |
| `none()` | цепочка | Заведомо пустой запрос — ничего не отправляет в базу (`count`/`exists`/`values`/`delete`/`update`/... отвечают без запроса). |
| `limit(limit)` / `offset(offset)` | цепочка | `QueryError` при отрицательном значении. `qs[start:stop]` — то же, что `.offset(start).limit(stop-start)` (шаг только `1`/`None`, `start`/`stop` не отрицательные); `stop`, не превышающий `start` (`qs[3:3]`, `qs[4:2]`), не выбирает строк, как срез списка. Смещение без ограничения записывается в SQLite как `LIMIT -1 OFFSET n` (SQLite не принимает `OFFSET` без `LIMIT`), и для запросов, и для объединений. `qs[i]` — один объект с индексом `i`; если его нет, при `await` будет `IndexError`; отрицательный индекс даёт `QueryError`. Объединение принимает срезы и индекс так же. |
| `distinct(*fields)` | цепочка | Без аргументов — обычный `DISTINCT`. С аргументами — по одной строке на сочетание полей: поле, связь, вычисляемое значение или [часть даты](values.ru.md#date-part-paths) (`"created__date"`), первая в сортировке: `order_by` должен начинаться с тех же полей в том же порядке; `count()`/`exists()` (и со срезом) считают строки, которые он выбирает; `aggregate()` даёт `QueryError`. PostgreSQL выполняет `DISTINCT ON (поля)`; база без него (SQLite) выбирает те же строки через `ROW_NUMBER() OVER (PARTITION BY <поля> ORDER BY <сортировка>) = 1` в подзапросе `pk IN (SELECT ...)` — там модели нужен первичный ключ, без сортировки остаётся строка с наименьшим первичным ключом, а `OuterReference(...)` в его фильтрах по-прежнему читает запрос, в который вложен queryset. Ветка `union()` с `distinct(*fields)` сохраняет свою сортировку. Как в Django, `distinct()` (с полями или без) на запросе со срезом даёт `QueryError("Cannot create distinct fields once a slice has been taken.")` — вызывайте его до среза. |
| `union(*other_querysets, all=False)` | цепочка | Возвращает QuerySet объединённых строк — тот же класс `QuerySet`, поэтому всё описанное ниже — обычный API QuerySet. Цепочка вызовов `union()`/`union(all=True)`/`intersection()`/`difference()` объединяет каждую новую ветку со всем результатом, полученным до неё, в порядке вызовов: `a.union(b).union(c, all=True)` — это `(a UNION b) UNION ALL c` (повторы, которые приносит `c`, остаются), `a.union(b, all=True).union(c)` убирает все повторы, а `a.union(b).intersection(c)` — это `(a UNION b) INTERSECT c` на любой базе (производная таблица не даёт более высокому приоритету `INTERSECT` в PostgreSQL изменить смысл). У каждой ветки может быть свой `.annotate()`, если имя не совпадает с настоящим полем модели. Вычисляемое значение раскодируется через поле первой ветки, у которой оно есть, как в Django: у ветки с `Value(None)` поля нет, и она ничего не меняет (`date` в SQLite остаётся `date`), а не раскодированным значение остаётся, только если у значения другой ветки поля нет вовсе (например, `Value("text")`). `.order_by()` у объединения ссылается на выбранные колонки по номеру, поэтому работает на любой базе и с ветками, соединяющими связь или группирующими по агрегату. `select_related()`/`prefetch_related()` у отдельной ветки (до `.union()`/`.intersection()`/`.difference()`) по-прежнему дают `QueryError`: загруженная связь не переживёт слияния в общий результат. Вызывайте `.prefetch_related()` у самого объединённого QuerySet: он выполняет предзагрузку партией по уже полученному списку результата через `prefetch_related_objects()`, после выполнения, и принимает то же (`str`/`Prefetch(...)`), что `QuerySet.prefetch_related()`. Ветка сама может быть операцией над множествами — `a.union(b.intersection(c))` объединяет `b INTERSECT c` целиком. Ветку — и вложенную операцию тоже — можно отсортировать и взять у неё срез (`a.order_by("-rank")[:3].union(b)`): она объединяется как производная таблица своих строк. Все ветки выполняются на одном подключении — ветка, чья модель или маршрутизатор выбирает другое подключение, чем у первой ветки, даёт `QueryError`. Объединение работает как значение `__in`, как запрос: `filter(pk__in=a.union(b))`, `filter(author__in=a.union(b))` сравнивают с первичным ключом его строк. Получение результата работает, как у запроса: `count()`, `exists()` (со срезом), `first()`/`last()` (без сортировки — по первичному ключу; `last()` у объединения со срезом даёт `QueryError`), `get(*args, does_not_exist_exception=..., multiple_objects_returned_exception=..., **kwargs)` (как у обычного запроса), `iterator(chunk_size=1000)` (страницы через `OFFSET`, в порядке `order_by()`, а затем всех выбранных колонок — и для объединения нескольких моделей ещё и модели — чтобы равные строки шли в постоянном порядке; срез ограничивает перебор; `prefetch_related()` выполняется для каждой страницы) и `stream(chunk_size=1000)` (курсор, как [`QuerySet.stream()`](#stream), — внутри транзакции, без `prefetch_related()`). В отличие от Django, который не принимает там условий, `get()` их принимает: условия применяются к каждой ветке до объединения (условие на строку оставляет те же строки до и после `UNION`/`INTERSECT`/`EXCEPT`), а на объединении со срезом дают `QueryError` — его строки зависят от строк, которые условие отбрасывает. `aggregate()` считает по объединённым строкам. Методы, меняющие то, какие строки выбирает запрос, — `filter()`/`exclude()`/`annotate()`/`alias()`/`distinct()`/`group_by()`/`only()`/`defer()`/`select_related()`/`select_for_update()`/`with_cte()`/курсоры/`all_tenants()`/`include_deleted()`/`only_deleted()` — и записи (`update()`/`delete()`/`hard_delete()`/`create()`/...) у самого объединения дают `QueryError`, как в Django, — применяйте их к веткам. Запросы к моделям объединяются с запросами к моделям, а запросы `.values()`/`.values_list()` — друг с другом (смесь — `QueryError`, см. [Запросы `values()` / `values_list()`](values.ru.md)); `.values()`/`.values_list()` у объединения запросов к моделям превращают его в объединение значений. |
| `with_cte(name, query)` | цепочка | Добавляет именованный `WITH` (общее табличное выражение, CTE), не меняя собственный `FROM` запроса; `filter(id__in=CteRows(name, "id"))` берёт строки запроса из него — см. [Рекурсивные запросы и CTE](#recursive). |
| `with_recursive(relation, *, max_depth=None)` | цепочка | Строки, достижимые от строк запроса по связи `relation` — прямой, обратной или «многие-ко-многим» связи модели с самой собой, — шаг за шагом, вместе с самими строками, одним запросом `WITH RECURSIVE`: потомки, предки, связанные строки графа. См. [Рекурсивные запросы и CTE](#recursive). |
| `sample(percent, *, method=TableSampleMethod.BERNOULLI, seed=None)` | цепочка | Читает случайную выборку таблицы модели вместо всей таблицы — `TABLESAMPLE`. См. [Выборка из таблицы](#sample). |
| `select_for_update(*, nowait=False, skip_locked=False, of=(), no_key=False, share=False, key_share=False)` | цепочка | `SELECT ... FOR UPDATE`. Сила блокировки — одно из: по умолчанию `FOR UPDATE`, `no_key=True` — `FOR NO KEY UPDATE` (строки, ссылающиеся на заблокированные, можно записывать; на базе без неё — обычный `FOR UPDATE`), `share=True` — `FOR SHARE` (другие транзакции могут взять ту же блокировку, но никто не может обновить или удалить строки), `key_share=True` — `FOR KEY SHARE` (ждут только удаление и изменение ключа); больше одного флага или флаг не типа bool дают `QueryError`; `FOR SHARE`/`FOR KEY SHARE` на базе без них (`features.supports_select_for_share`/`supports_select_for_key_share`) дают `UnSupportedError` при выполнении запроса. Строки, которые читает `prefetch_related()` этого запроса, блокируются так же. Если запрос выполняется на базе без `FOR UPDATE` (`features.supports_select_for_update` ложно, например SQLite), даёт `UnSupportedError`: молча пропустить вызов значило бы позволить вызывающему думать, что строки заблокированы, хотя это не так. На базе, которая это умеет, даёт `QueryError`, если запрос выполняется вне блока `Transactions.atomic()`: иначе блокировка была бы взята и тут же снята (автоматическая фиксация), не давая настоящей защиты, но создавая её видимость. `of` принимает `"self"` (или имя таблицы самой модели) и пути прямых связей в том виде, в каком их принимает `select_related()` (`"author"`, `"author__country"`); в SQL они становятся псевдонимами, под которыми запрос соединяет таблицы. Связь, названная в `of`, соединяется через `INNER JOIN` вместо `LEFT OUTER JOIN` (PostgreSQL не может блокировать сторону внешнего соединения, допускающую `NULL`), поэтому каждый шаг её пути должен быть внешним ключом `NOT NULL` с `db_constraint=True` и без условий мягкого удаления, арендатора или `Select(extra_condition=...)`; иначе, а также для имени, которое не является таким путём или не соединяется запросом, будет `QueryError`. Без `of` запрос с любым `JOIN` блокирует только строки самой модели. Запрос с агрегатным вычисляемым значением или `GROUP BY` даёт `QueryError`: сгруппированная строка обозначает несколько строк таблицы, которые SQL заблокировать не может, — блокируйте строки отдельным запросом. То же относится к запросу с `.distinct()`/`.distinct(<поля>)`, к запросу, читающему оконную функцию (`Window(...)`), и к ветке `union()`/`intersection()`/`difference()` — в том числе запросу `.values()`/`.values_list()`, — их PostgreSQL тоже заблокировать не может. |
| `group_by(*fields)` | цепочка | До или после `.values()`/`.values_list()`, которые затем возвращают по строке на группу. Объекты моделей всегда группируются по первичному ключу, поэтому на запросе объектов строки не меняются — `await qs`, `count()`, `exists()`, `contains()`, `update()` и `delete()` видят по строке на объект. `aggregate()` работает над сгруппированными строками (теми, что вернул бы `.values()`) и может читать только поля группировки и вычисляемые значения (иначе `QueryError`): `.annotate(n=Count("id")).group_by("author_id").aggregate(most=Max("n"))` — наибольшее число на одного автора, как `values().annotate().aggregate()` в Django. Сгруппированный запрос `.values()`/`.values_list()` не учитывает `Meta.ordering` (её колонки не сгруппированы) — без сортировки он упорядочен по ключу группировки. |
| `values_list(*fields, flat=False, named=False, **expressions)` | цепочка | QuerySet кортежей (отдельных значений с `flat=True`, именованных кортежей с `named=True`) — см. [Запросы `values()` / `values_list()`](values.ru.md). Несовместим с `.only()`/`.defer()`. Без аргументов — все поля и вычисляемые значения. Имя может быть путём внутрь поля JSON или вычисляемого значения (`"data__owner__name"`), читаемым так же, как его читает `F()`, или [частью даты](values.ru.md#date-part-paths) (`"created__year"`). `named=True` возвращает каждую строку как именованный кортеж с атрибутом на каждое выбранное имя (имя, которое не является допустимым идентификатором, становится `_<номер>`); `flat` вместе с `named`, позиционный аргумент не-строка или именованный аргумент, который не является выражением, дают `QueryError`. Полноценный запрос, возвращающий кортежи, — см. [Запросы `values()` / `values_list()`](values.ru.md). |
| `values(*args, **kwargs)` | цепочка | QuerySet словарей — см. [Запросы `values()` / `values_list()`](values.ru.md). `kwargs` — пары `псевдоним="имя_поля"` или `псевдоним=<выражение>`; любое другое значение даёт `QueryError`. Имя может быть путём внутрь поля JSON или вычисляемого значения (`"data__owner__name"`), читаемым так же, как его читает `F()`, или [частью даты](values.ru.md#date-part-paths) (`"created__year"`). Несовместим с `.only()`/`.defer()`. Полноценный запрос, возвращающий словари, — см. [Запросы `values()` / `values_list()`](values.ru.md). |
| `delete()` | await | `DeleteQuery`, возвращает число строк. Работает так же, как `Model.delete()`, но для многих строк сразу: при заданном `Meta.soft_delete_field` превращается в `UPDATE` вместо настоящего `DELETE` (одна команда, если на эту модель ничто не ссылается, иначе — вместе с тем же каскадом, что выполняет `Model.delete()`); сразу даёт `ProtectedError`, если на найденную строку ещё ссылается связь с `on_delete=PROTECT` (проверяется один раз для всего найденного набора, а не для каждой строки); сначала выполняет каскад в Python, если у связи `db_constraint=False` (в базе нет настоящего `FOREIGN KEY`, поэтому при обычном массовом `DELETE` её `on_delete` никто не выполнит). Каскад в Python идёт партиями в одной транзакции: каждая волна затронутых строк стоит одного запроса на связь и модель (больше — только сверх ограничения базы на число параметров), а не запроса на строку, и все строки, которые он мягко удаляет, получают одно и то же `deleted_at`. Только если модель переопределяет `delete()`, каждая найденная (или затронутая каскадом) строка удаляется через это переопределение по одной. На запросе со срезом (и с `.distinct(<поля>)`) удаляются ровно те строки, которые возвращает `await qs`, — через `pk IN (SELECT ...)` того же отсортированного, обрезанного, `.distinct()`/сгруппированного `SELECT`. Фильтр по агрегатному вычисляемому значению (`HAVING`, в том числе через `.alias()`/`.exclude()`) идёт через тот же подзапрос, поэтому удаляются только подходящие строки. |
| `hard_delete()` | await | Удаляет все подходящие строки по-настоящему, даже если задано `Meta.soft_delete_field`, — в том числе уже мягко удалённые, если запрос их видит (`Model.objects.only_deleted().hard_delete()` очищает корзину). Связанные строки следуют своему `on_delete` так же, как при `delete()` модели без мягкого удаления; у модели без `Meta.soft_delete_field` это то же, что `delete()`. Результат ожидания — число строк. |
| `restore(*, cascade=False)` | await | Отменяет мягкое удаление строк запроса — тех из них, что мягко удалены, при любой видимости (`Model.objects.filter(...).restore()` читает удалённые строки); возвращает число восстановленных строк. Один `UPDATE` — поля `auto_now` и `Meta.optimistic_lock_field` меняются как у `update()`. `cascade=True` восстанавливает и строки, удалённые мягким удалением каждой из них вместе с ней (те, у которых ещё стоит её время удаления, как у [`Model.restore(cascade=True)`](../models/model-methods.ru.md)), в одной транзакции; у модели с переопределённым `restore()` он вызывается для каждой строки. `QueryError` для модели без `Meta.soft_delete_field`, запроса `values()`, `union()` или `sample()`. Только строки активного арендатора, если не `all_tenants()`. |
| `update(**kwargs)` | await | `UpdateQuery`, возвращает число строк. Не принимает в `kwargs` `Meta.soft_delete_field`/`Meta.optimistic_lock_field` (`QueryError`) — вместо этого `optimistic_lock_field` каждой найденной строки увеличивается автоматически (`SET version = version + 1`), если `kwargs` не пуст, и каждое поле `auto_now` получает одно и то же «сейчас», названо оно в `kwargs` или нет, — так же, как это делает `save()`. В отличие от `save()`, проверки устаревания нет: у `.update()` нет ранее загруженного объекта, с версией которого можно сравнить, поэтому он никогда не даёт `StaleObjectError`. На запросе со срезом (и с `.distinct(<поля>)` или фильтром по агрегатному вычисляемому значению) обновляются ровно строки, которые возвращает `await qs`, как в `delete()`; `bulk_update()` на таком запросе записывает только объекты, строки которых ему соответствуют. Значение-агрегат (`Sum("qty")`) или значение, читающее агрегатное вычисляемое значение (`F("n")` после `annotate(n=Count(...))`), даёт `FieldError`, как в Django: в `UPDATE` нет групп для агрегата; `Subquery()`, агрегирующий связанные строки, работает. |
| `update(**kwargs).returning(*fields)` / `delete().returning(*fields)` / `hard_delete().returning(*fields)` | await | Запись, возвращающая записанные строки — словарь полей `fields` на каждую строку или объекты модели, если поля не названы. См. [Записанные строки](#returning). |
| `count()` | await | Возвращает `int` — число строк, которое возвращает `await qs`, в том числе с агрегатными вычисляемыми значениями, фильтром `HAVING`, `.distinct()` или сортировкой через связь «ко многим» (её `JOIN` возвращает строку на каждую связанную строку). Запрос с `.distinct()`, выбирающий вычисляемое значение через связь «ко многим» (`F("books__name")`), возвращает строку на каждое различное значение, и `count()` тоже. `.group_by()` на него не влияет — см. `group_by()`; с `.distinct(<поля>)` он считает строки, которые выбирает `DISTINCT ON`. |
| `aggregate(**kwargs)` | await | Один словарь с ключом по имени каждого аргумента, по всему запросу (после `.group_by()` — по сгруппированным строкам, см. `group_by()`). Как в Django, запрос со срезом (`qs.order_by("-rating")[:10].aggregate(...)`) агрегирует строки среза, ограниченные по их первичному ключу; несортированный срез содержит первые строки по первичному ключу — те, что читают `first()`/`last()`. Срез с `.distinct()` может фильтровать через связь «ко многим» (`filter(tags__in=[1, 2]).distinct().order_by("id")[:2].aggregate(...)`): его строки сводятся к одной на первичный ключ до подсчёта, как у `.distinct()` без среза. Любой другой срез, строки которого могут повторять первичный ключ (фильтр, вычисляемое значение или сортировка через связь «ко многим»), и модель с составным первичным ключом дают `QueryError` — агрегируйте запрос `.values()`/`.values_list()` со срезом. |
| `exists()` | await | Возвращает `bool` — вернёт ли `await qs` хотя бы одну строку, с учётом среза. |
| `contains(obj)` | await | `ContainsQuery` — есть ли этот объект (по первичному ключу) в результате запроса? `QueryError`, если у `obj` нет первичного ключа. |
| `all()` | цепочка | Копия запроса без изменений. |
| `raw(sql, parameters=())` | await | Выполняет SQL как есть; `parameters` подставляются как настоящие параметры запроса на место `%s` (защита от SQL-инъекций: значения никогда не вставляются в текст запроса). `.sql()` возвращает исходную строку без изменений, с неподставленными `%s`. |
| `first()` / `last()` | конечный | `LIMIT 1`; без `order_by()` и без `Meta.ordering` `first()` сортирует по первичному ключу по возрастанию (у запроса с `.group_by()`/`.distinct(<поля>)` остаётся несортированным); `last()` точно обращает текущую сортировку — и направление, и явное место `NULL` (или сортирует по первичному ключу по убыванию, если сортировки нет; у модели без первичного ключа и без сортировки последней строки нет, и берётся любая). На срезе `first()`/`last()` берут из строк среза; несортированный срез для обоих содержит первые строки по первичному ключу. Строку, взятую из среза (`qs[2:5].first()`, `qs[3]`, а также `last()`/`latest()`/`earliest()`/`get()` среза), нельзя фильтровать, пересортировать или вызывать у неё `distinct()` (`QueryError`), как и у самого среза; `first()` запроса без среза — можно. На запросе с `.distinct(<поля>)` `last()`/`latest()`/`earliest()`/`get()` выбирают среди строк, которые `DISTINCT ON` возвращает для исходной сортировки. |
| `latest(*orderings)` / `earliest(*orderings)` | конечный | Сортируют по убыванию/возрастанию по данным полям — без них по `Meta.get_latest_by` модели, — затем `first()`; `NULL` никогда не побеждает (`NULLS LAST` на любом диалекте — см. [Порядок NULL при сортировке](#null-ordering)). `FieldError`, если нет ни того, ни другого. |
| `reverse()` | цепочка | Сортировка, развёрнутая точно — и направление, и явное место `NULL`: заданная `order_by()`, иначе `Meta.ordering`; неупорядоченный QuerySet остаётся неупорядоченным. `QueryError` на срезе и на `union()`. |
| `dates(field_name, trunc_type, order="ASC")` | цепочка | Различающиеся значения `DateField`/`DatetimeField`, усечённые до `trunc_type` (`year`, `quarter`, `month`, `week` — с понедельника — или `day`), как `datetime.date`; у даты-времени — в текущем поясе; `NULL` не попадают; в порядке `order` (`ASC`/`DESC`); QuerySet `values_list(flat=True)`, его можно фильтровать и срезать как обычно. |
| `datetimes(field_name, trunc_type, order="ASC", tzinfo=None)` | цепочка | То же для `DatetimeField`, как `datetime` с часовым поясом; `trunc_type` также `hour`, `minute` или `second`; усечение в поясе `tzinfo` (имя IANA или `ZoneInfo`; по умолчанию текущий пояс). Другое поле, единица или порядок дают `FieldError`. |
| `get(*args, does_not_exist_exception=..., multiple_objects_returned_exception=..., **kwargs)` | конечный | Единственный подходящий объект. `get(**kwargs)` — это `filter(**kwargs).get()`: на запросе с `.distinct(<поля>)` условия применяются до того, как `DISTINCT ON` выберет строку на группу, как в `filter()`; на запросе со срезом работает только вызов без аргументов (он читает строки самого среза). `does_not_exist_exception` — если ничего не найдено — и `multiple_objects_returned_exception` — если найдено больше одного: по умолчанию бросаются `DoesNotExist` / `MultipleObjectsReturned`; класс исключения (создаётся без аргументов) или уже созданный объект бросается вместо них; `None` выключает проверку — без совпадений возвращается `None` (тип результата `Model | None`), при нескольких совпадениях — одно из них, прочитанное через `LIMIT 1` без подсчёта остальных (какое именно — не определено; определённое берёт `first()`). Любое другое значение — `TypeError`. |
| `create(**kwargs)` | `async def` | Создаёт строку и возвращает её объект — `Model(**kwargs)`, сохранённый на подключении запроса (`Model.objects.using("replica").create(...)`); фильтры запроса не участвуют. `QueryError` для значения `F()`/выражения, а также по правилам [`Meta.tenant_field`](../soft-delete-versions-tenants/multi-tenancy.ru.md), когда переданный арендатор отличается от активного. |
| `get_or_create(defaults=None, **kwargs)` | `async def` | Объект, подходящий под `kwargs` среди строк запроса, либо новый, созданный из `kwargs` и `defaults`, — `(объект, создан)`. Проверка существования читает на подключении для записи, поэтому отстающая реплика не приведёт к дубликату; строка, созданная параллельно между проверкой и вставкой, читается, а не вызывает ошибку, — её выдаёт конфликт ограничения уникальности при вставке, поэтому на базе без ограничений уникальности (`Features.supports_unique_constraints`) два параллельных вызова могут вставить обе строки. `QueryError`, если строка создаётся, а `defaults` противоречит `kwargs`. |

| `bulk_create(objects, batch_size=None, *, ignore_conflicts=False, update_fields=None, on_conflict=None, on_conflict_constraint=None, conflict_where=None, returning=None, use_copy=False)` | await | Сгенерированные первичные ключи, колонки `GeneratedField` и пропущенные колонки с `db_default` **не** записываются обратно в объекты, если не передан `returning=True` (только PostgreSQL, через `RETURNING`; в SQLite не поддерживается, потому что порядок строк многострочного `RETURNING` там не обязан совпадать с порядком вставки). При `None` (по умолчанию) берётся `Meta.returning` (по умолчанию `False`) — задайте его на общей базовой модели, чтобы не передавать `returning=True` в каждом вызове; явные `True`/`False` здесь всегда важнее, а значение, **унаследованное** от `Meta.returning`, вместе с `use_copy=True` или на SQLite молча уступает, а не вызывает ошибку. `use_copy=True` загружает строки через протокол `COPY` PostgreSQL вместо `INSERT` с параметрами — быстрее для больших партий, но несовместимо с явным `returning=True` и со всеми аргументами обработки конфликтов (у `COPY` нет `RETURNING`/`ON CONFLICT`) и не поддерживается в SQLite. На ClickHouse `bulk_create()` загружает строки одной двоичной вставкой и с `use_copy=True`, и без него — см. [Массовая загрузка](../dialects/clickhouse/differences.ru.md#bulk-loads). `COPY` не поддерживает в модели поля массивов и диапазонов и поля расширений PostgreSQL (`CitextField`, `PostGISField`, `TSVectorField`) ни на одном драйвере — даёт `UnSupportedError` с именем поля, проверяется одинаково на стороне Python до обращения к драйверу; для такой модели используйте `use_copy=False`. `update_fields`/`on_conflict` принимают имена полей: колонка `source_field` определяется сама, имя прямой связи означает колонки её ключа (`owner` → `owner_id`), неизвестное имя даёт `FieldError`; генерируемое поле, `Meta.tenant_field`, `Meta.optimistic_lock_field` или `Meta.soft_delete_field` в `update_fields` дают `QueryError`. У конфликтующей строки обновляются и поля `auto_now` (и увеличивается `Meta.optimistic_lock_field`); конфликтующая мягко удалённая строка обновляется, но остаётся удалённой. Поле из `update_fields`, значение которого у всех объектов оставлено на `db_default`, всё равно обновляется — значением по умолчанию из базы. С `returning=True` объект с явно заданным первичным ключом тоже получает свои колонки `GeneratedField`/пропущенные `db_default`, вставка-или-обновление модели с `Meta.optimistic_lock_field` читает увеличенную версию строки, а при `ignore_conflicts=True` из нескольких объектов с одним ключом конфликта в одном вызове сохранённым остаётся только первый (тот, чья строка вставлена). С `update_fields` несколько объектов с одним ключом конфликта в одном вызове записываются по порядку на любом драйвере, поэтому побеждают значения последнего; с `returning=True` каждый из них получает первичный ключ строки. Каждый объект должен быть объектом именно этой модели (другая модель, модель с той же абстрактной базой или подкласс со своей таблицей дают `QueryError`), а объект, загруженный через `.only()`/`.defer()`, должен содержать все колонки, которые записывает вставка (`IncompleteInstanceError`). Собственные дополнительные параметры команды (область арендатора и увеличение версии при вставке-или-обновлении) учитываются в ограничении на число параметров при выборе размера партии. Модель, все колонки которой берутся из значений по умолчанию базы, записывается одним `INSERT ... SELECT FROM generate_series(...)` в PostgreSQL (одним `DEFAULT VALUES` на объект в SQLite). Если `bulk_create()` завершился ошибкой, объекты остаются такими, какими были до вызова (первичный ключ, возвращённые колонки, признак сохранённости), даже если более ранние партии уже были записаны и затем откачены. С `use_copy=True` несколько команд `COPY` (объекты с явным первичным ключом и без него загружаются отдельно, как и партии `batch_size`) тоже выполняются в одной транзакции — на обоих драйверах PostgreSQL; внутри `Transactions.atomic()` каждая `COPY` выполняется на соединении транзакции и фиксируется или откатывается вместе с ней, в том числе при откате точки сохранения. `on_conflict_constraint` не поддерживается в SQLite. `conflict_where` (только PostgreSQL) — `Q` по полям модели или `RawSQLTerm` сырого SQL — повторяет условие `WHERE` частичного уникального индекса, чтобы `ON CONFLICT (...) WHERE <conflict_where>` мог на него указать; несовместимо с `on_conflict_constraint` и требует, чтобы `on_conflict` называл колонки этого индекса. |

## <a id="null-ordering"></a>Порядок NULL при сортировке

SQLite и PostgreSQL по-разному решают, где окажется `NULL`, а простая строка сортировки оставляет
это диалекту: SQLite считает `NULL` самым малым значением (первым при `ASC`, последним при `DESC`),
PostgreSQL — самым большим (последним при `ASC`, первым при `DESC`). Если в `Player(name, score)`
лежат `a:1, b:NULL, c:2, d:3, e:NULL`, то `order_by("score", "name")` вернёт `b, e, a, c, d` в SQLite и
`a, c, d, b, e` в PostgreSQL. Это поведение по умолчанию сохраняется и действует для
`order_by("field")`/`order_by("-field")`, строк `Meta.ordering`, `first()`/`last()` и строк в
`Window(order_by=[...])`.

Чтобы место `NULL` было одинаковым на любом диалекте, передайте вместо строки `Ordering`, построенный
из `F(...)`:

```python
from hare.query.expressions import F

await Player.objects.all().order_by(F("score").desc(nulls_last=True), "name")   # 3, 2, 1, затем NULL
await Player.objects.all().order_by(F("score").asc(nulls_first=True), "name")   # сначала NULL, затем 1, 2, 3
await Employee.objects.all().order_by(F("manager__name").asc(nulls_last=True))  # в том числе NULL из LEFT JOIN
```

`F(name).asc()` / `F(name).desc()` принимают только именованные флаги `nulls_first` / `nulls_last`
(оба `True` дают `QueryError`; ни одного — оставляют поведение диалекта). `Ordering` и строки можно
свободно смешивать, и `Ordering` принимается везде, где принимается сортировка: `order_by()` (и у
`union()`), `latest()`/`earliest()`, `Meta.ordering`, `Window(order_by=[...])`, `distinct(...)` вместе
с `order_by()` (PostgreSQL), `values()`/`values_list()`, `stream()`/`iterator()`. Всё, что не строка и
не `Ordering`, даёт `QueryError`. В SQL получается `ORDER BY ... NULLS FIRST|LAST` (SQLite 3.30+).

- **`latest()` / `earliest()` не выбирают `NULL`.** Для простого имени поля на любом диалекте
  добавляется `NULLS LAST`, поэтому `NULL` никогда не побеждает: `latest("score")` — строка с
  наибольшим значением, не равным `NULL`, а `earliest("score")` — с наименьшим. Если все значения
  `NULL`, строка с `NULL` всё равно возвращается (а не `None`). Колонка, которая не может хранить
  `NULL`, сохраняет простое направление, чтобы по-прежнему работал просмотр по индексу; сортировка
  `related__field` и вычисляемое значение считаются допускающими `NULL`. Явный `Ordering`
  соблюдается: `earliest()` использует его как задано, `latest()` обращает его, как `last()`.
- **`last()` обращает сортировку точно.** Обращаются и направление, и явное место `NULL`
  (`ASC NULLS LAST` становится `DESC NULLS FIRST`), поэтому `last()` — всегда последняя строка той же
  сортировки при чтении с начала. Без явного места `NULL` поведение диалекта обращается вместе с
  направлением.
- **`after_cursor()` / `before_cursor()` / `iterator()`** следуют месту `NULL` в самой сортировке:
  явный `nulls_first`/`nulls_last` определяет, какие строки лежат после (или до) курсора (включая
  границу со значением `NULL`), иначе это определяет диалект, поэтому страницы ни в одном случае не
  теряют и не повторяют строк. `before_cursor()` при обращении сортировки отражает и место `NULL`
  (`ASC NULLS FIRST` выполняется как `DESC NULLS LAST`).
- **Планы команд** учитывают место `NULL`, поэтому два запроса, отличающиеся только им, никогда
  не делят один план.

## <a id="prefetch"></a>`Prefetch`

```python
class Prefetch:
    def __init__(self, relation: str, queryset: QuerySet, to_attribute: str | None = None) -> None
```

К `queryset` уже могут быть применены `.filter()`/`.only()`/`.order_by()`; это должен быть запрос к
модели — запрос `.values()`/`.values_list()` даёт `QueryError`. `to_attribute` не может совпадать с
именем поля, связи, колонки ключа (`author_id`) или другого атрибута модели, которой принадлежит
загружаемая связь, — это даёт `QueryError`, а не перезаписывает атрибут в каждом объекте.
Вложенная предзагрузка поддерживается двумя способами:

```python
# путь через связи внутри Prefetch
await Team.objects.all().prefetch_related(Prefetch("events__reporter", queryset=User.objects.filter(is_active=True)))

# .prefetch_related() прямо у запроса, переданного в Prefetch
await Team.objects.all().prefetch_related(
    Prefetch("events", queryset=Event.objects.filter(status="open").prefetch_related("reporter"))
)
```

Как в Django, путь через связь (`"events__reporter"`) загружает собственный атрибут связи
(`team.events`), даже если рядом передан `Prefetch` той же связи с `to_attribute=` — тот загружает только
свой атрибут. Путь попадает в результаты `to_attribute`, когда начинается с имени `to_attribute`; задающий его
`Prefetch` может стоять дальше в том же вызове или в более раннем вызове `prefetch_related()`:

```python
teams = await Team.objects.all().prefetch_related(
    Prefetch("events", queryset=Event.objects.filter(status="open"), to_attribute="open_events"),
    "open_events__reporter",  # reporter у каждого события из team.open_events
    "events",  # team.events — все события команды
)
```

Первое имя, которое не является ни связью модели, ни таким `to_attribute`, даёт `FieldError`.

### <a id="sliced-prefetch"></a>Срез у запроса `Prefetch`

Срез у запроса `Prefetch` (`[:3]`, `[2:5]`, `.limit()`, `.offset()`) берётся из строк **каждого
родителя** — три новых комментария к каждому посту, а не три комментария всего:

```python
posts = await Post.objects.prefetch_related(
    Prefetch("comments", queryset=Comment.objects.order_by("-id")[:3], to_attribute="latest_comments")
)
```

Строки нумеруются внутри каждого родителя через `ROW_NUMBER() OVER (PARTITION BY <ключ родителя>
ORDER BY <сортировка запроса>)`, и номер сравнивается с границами среза — один запрос для обратного
внешнего ключа; для связи «многие-ко-многим», где строка может принадлежать нескольким родителям и
попадать в срез каждого отдельно, сначала читаются пронумерованные пары (родитель, строка), затем
сами строки. Сортировка — `order_by()` запроса, иначе `Meta.ordering` модели, иначе первичный ключ.
Составные ключи, `to_attribute` и вложенная предзагрузка строк среза работают так же, как без среза. У
прямой связи и обратной «один-к-одному» у родителя не больше одной строки: срез, начинающийся с неё,
её оставляет, срез после неё даёт `None`.

## <a id="stream"></a>`stream()` — настоящий курсор на стороне сервера

```python
async def stream(self, chunk_size: int = 1000) -> AsyncIterator[TModel]
```

В отличие от `iterator()` (который для каждой страницы выполняет новый `SELECT` через
`LIMIT`/`OFFSET` или по курсору), `stream()` открывает ровно **один** курсор на стороне сервера на
весь проход — один согласованный снимок данных на весь перебор. Строка, уже попавшая в поток курсора,
не зависит от одновременного `DELETE`/`UPDATE` посреди перебора, а ещё не прочитанные строки
читаются по снимку, сделанному при открытии курсора, а не по тому, как таблица выглядит в момент
чтения каждой строки.

```python
async with Transactions.atomic():
    async for widget in Widget.objects.filter(category="archived").stream():
        ...
```

Требует активного блока `Transactions.atomic()` на обоих драйверах PostgreSQL. Строго это
нужно только `Connection.cursor()` в `asyncpg` (он по устройству привязан к времени жизни своей
транзакции); курсору `rust_pg` самому это не нужно, но `stream()` применяет то же правило, чтобы
поведение не зависело от драйвера, — и в SQLite, где курсор читается на соединении транзакции:
по `chunk_size` строк за обращение `fetchmany()` к рабочему потоку aiosqlite, весь результат в памяти
никогда не держится, а курсор закрывается, когда перебор закончен, прерван или отменён. Вне транзакции
даёт `QueryError`, а на базе без `features.supports_streaming` (без транзакций) — `UnSupportedError`.
`chunk_size` — сколько строк забирать за одно обращение; его учитывают
`Connection.cursor(prefetch=...)` в `asyncpg` и партии SQLite, а курсор `rust_pg` и так передаёт
строки по одной и его не использует. Пока поток открыт, в той же транзакции можно выполнять другие запросы — из тела
цикла или из соседних задач (`asyncio.gather()`), разделяющих транзакцию; каждое чтение курсора ждёт
своей очереди на соединении транзакции.

В ClickHouse (`features.streams_without_transaction`) `stream()` работает и вне транзакции: сервер
отдаёт строки по мере вычисления блоками, которые драйверы читают по одному, а выход из цикла —
`break`, ошибка, отмена — закрывает поток и возвращает соединение.

Если перебор заканчивается раньше — исключение, отмена или `aclose()` генератора (простой `break`
закрывает его, только когда генератор соберёт сборщик мусора; оберните его в `contextlib.aclosing()`,
чтобы закрыть на `break`), — поток сразу останавливается, не читая оставшиеся строки; у `rust_pg` его
курсор сбрасывается сразу, поэтому следующая команда транзакции не ждёт непрочитанных строк.
`COMMIT`/`ROLLBACK` самой транзакции тоже закрывают ещё открытый на ней поток; чтение из него после
этого даёт `TransactionManagementError`. У `rust_pg` `ROLLBACK`, на который нет ответа в течение 30 с,
вместо этого закрывает соединение — сервер всё равно откатывает транзакцию, а соединение не
возвращается в пул.

## <a id="recursive"></a>Рекурсивные запросы и CTE

### <a id="with_recursive-walking-a-relation-of-a-model-to-itself"></a>`with_recursive()` — обход связи модели с самой собой

```python
def with_recursive(self, relation: str, *, max_depth: int | None = None) -> QuerySet[TModel, TModel]
```

`with_recursive()` берёт строки запроса как начало и идёт от них по связи `relation` снова и снова:
строки на шаг дальше, потом строки на шаг дальше от них и так далее. Результат — запрос строк модели,
до которых дошёл обход, вместе с начальными строками; он строится одним запросом `WITH RECURSIVE`, без
обращения к базе на каждый уровень.

```python
class Employee(Model):
    name = fields.CharField(max_length=50)
    manager = fields.ForeignKeyField("models.Employee", related_name="team_members", null=True)
    talks_to = fields.ManyToManyField("models.Employee", related_name="gets_talked_to")

ceo = await Employee.objects.get(name="CEO")
# Директор и все ниже него: обратная связь, вниз по дереву.
everyone = await Employee.objects.filter(pk=ceo.pk).with_recursive("team_members")
# Сотрудник и его руководители до самого верха: прямая связь, вверх по дереву.
chain = await Employee.objects.filter(name="Ann").with_recursive("manager")
# Только два уровня вниз — прямые подчинённые и их подчинённые.
nearby = await Employee.objects.filter(pk=ceo.pk).with_recursive("team_members", max_depth=2)
# Все, до кого Ann доходит по графу «многие ко многим».
reached = await Employee.objects.filter(name="Ann").with_recursive("talks_to")
```

- **`relation`** — прямая (`ForeignKeyField`, `OneToOneField`), обратная или «многие-ко-многим» связь,
  связанная модель которой — сама модель. Всё остальное — обычное поле, связь с другой моделью, путь
  через `__` — даёт `FieldError` при выполнении запроса.
- **`max_depth`** — сколько шагов от начальных строк: `0` — только они, `1` — ещё их прямые соседи,
  `None` (по умолчанию) — обход идёт, пока появляются новые строки. `int` от `0` до `100_000`; другое
  значение (отрицательное или большее число, `True`, `2.0`, строка) — `QueryError` при вызове.
- **Циклы заканчиваются.** Шаги обхода объединяются через `UNION`, поэтому строка, достигнутая второй
  раз — по циклу в данных (`a.manager = b`, `b.manager = a`) или двумя путями, — не добавляет новой
  строки, и обход останавливается. С `max_depth` строка, достигнутая на двух глубинах, остаётся одна.
- **Начальные строки** — любой запрос: фильтр, несколько строк, срез, запрос с сортировкой или
  вычисляемыми значениями (читаются только первичные ключи). Пустое начало — пустой результат.
- **Видимость строк.** Обход идёт по строкам, которые показывает область видимости модели по
  умолчанию: мягко удалённая строка (`Meta.soft_delete_field`) или строка другого арендатора
  (`Meta.tenant_field`) не возвращается и не проходится, поэтому строки под удалённой строкой сверху
  не достигаются. `include_deleted()` / `all_tenants()` до `with_recursive()` проводят обход через все
  строки, и результат сохраняет эту видимость.
- **Составные первичные ключи** работают так же, как ключи из одной колонки: обход сравнивает все
  колонки ключа.
- **Результат** — обычный запрос модели на том же подключении: его можно фильтровать, сортировать,
  брать срез, `count()`, читать `values()`, предзагружать связи или передавать значением `__in`
  (`Employee.objects.exclude(pk__in=everyone_below)`). Порядок по умолчанию — порядок модели, порядок
  обхода не сохраняется; глубина не входит в колонки строк.
- Объединённый запрос (`union()`/`intersection()`/`difference()`) даёт `QueryError` — вызывайте
  `with_recursive()` у ветки.

Запрос обходит первичные ключи строк в CTE и читает по ним строки модели:

```sql
SELECT ... FROM "employee" WHERE "id" IN (
  WITH RECURSIVE "hare_recursive_rows"("id") AS (
    SELECT "hare_recursive_start"."id" FROM "employee" "hare_recursive_start"
    WHERE "hare_recursive_start"."id" IN (SELECT "id" FROM "employee" WHERE "id" = $1)
    UNION
    SELECT "hare_recursive_previous__team_members"."id" FROM "hare_recursive_rows"
    JOIN "employee" "hare_recursive_previous" ON "hare_recursive_rows"."id" = "hare_recursive_previous"."id"
    JOIN "employee" "hare_recursive_previous__team_members"
      ON "hare_recursive_previous"."id" = "hare_recursive_previous__team_members"."manager_id"
  )
  SELECT "id" FROM "hare_recursive_rows"
)
```

`with_recursive()` работает одинаково на PostgreSQL, SQLite и колоночной базе. Для его запроса
[план](query-plan-cache.ru.md) не хранится: шаги соединяют связанные строки с условием их видимости, а
такие значения план привязать не может.

### <a id="cterows-reading-a-querysets-rows-from-a-cte"></a>`CteRows` — строки запроса из CTE

`with_cte(name, query)` добавляет к запросу `WITH`, не меняя его `FROM`. `CteRows(name, *columns)` —
значение, которым фильтр `__in` читает строки CTE, — `SELECT <columns> FROM <name>`:

```python
from hare.query.expressions import CteRows

# Запрос как тело CTE.
large = IntFields.objects.filter(intnum__gte=40).values("id")
rows = await IntFields.objects.with_cte("large", large).filter(id__in=CteRows("large", "id"))

# Рекурсивный CTE, собранный вручную: категория и её предки.
connection = Category.get_connection()
query_class = connection.query_class
category, ancestors = Table("category"), Table("ancestors")
columns = (category.id, category.parent_id)
base = query_class.from_(category).select(*columns).where(category.id == leaf_id)
step = query_class.from_(category).join(ancestors).on(category.id == ancestors.parent_id).select(*columns)
union_all = base * step
union_all.base_query.wrap_set_operation_queries = False
path = await Category.objects.with_cte("ancestors", union_all).filter(id__in=CteRows("ancestors", "id"))

# Составной первичный ключ: колонки CTE в порядке ключа.
picked = Node.objects.filter(name="child").values("a", "b")
rows = await Node.objects.with_cte("picked", picked).filter(pk__in=CteRows("picked", "a", "b"))
```

`CteRows` требует имя и хотя бы одну колонку — непустые строки, иначе `QueryError`. Составной
`pk__in` сравнивает столько колонок, сколько их в ключе, в порядке ключа. В отличие от `RawSQL`,
`CteRows` экранирует имена так, как принято в базе, и сохраняет [план](query-plan-cache.ru.md) запроса.

## <a id="sample"></a>Выборка из таблицы

```python
def sample(
    self, percent: float, *, method: TableSampleMethod | str = TableSampleMethod.BERNOULLI, seed: int | None = None
) -> Self
```

`sample()` читает случайную выборку таблицы модели вместо всей таблицы — `TABLESAMPLE` во `FROM`.
Сначала из таблицы берётся выборка, а уже к её строкам применяются фильтры, соединения, группировка и
сортировка запроса. Это дешёвый способ оценить что-то по большой таблице: количество, среднее,
несколько строк для просмотра.

```python
from hare.query.enums import TableSampleMethod

# Около 1% строк — каждая строка остаётся с вероятностью 1%.
rough = await Event.objects.sample(1).count() * 100
# Одни и те же строки при каждом запросе, пока таблица не меняется.
preview = await Event.objects.sample(5, seed=42).filter(status="open").order_by("id")[:20]
# Быстрее на огромной таблице: остаются или пропускаются целые блоки хранения.
average = await Event.objects.sample(0.5, method=TableSampleMethod.SYSTEM).aggregate(avg=Avg("price"))
```

```sql
SELECT ... FROM "event" TABLESAMPLE BERNOULLI (5) REPEATABLE (42) WHERE "status" = $1 ORDER BY "id" LIMIT 20
```

- **`percent`** — вероятность, с которой остаётся каждая строка (или блок), `int` или `float` от `0`
  до `100`: `100` читает все строки, `0` — ни одной. Число прочитанных строк случайно и близко к
  `percent` от таблицы, но не равно ему точно.
- **`method`** — `TableSampleMethod.BERNOULLI` (по умолчанию) читает всю таблицу и оставляет каждую
  строку отдельно; `TableSampleMethod.SYSTEM` оставляет или пропускает целые блоки хранения — намного
  быстрее на большой таблице, но строки одного блока приходят вместе, поэтому выборка менее равномерна.
  Имя принимается и строкой в любом регистре (`"system"`).
- **`seed`** — `int` от `0` до `2_147_483_647` (`REPEATABLE`): одно и то же значение читает одни и те же
  строки, пока таблица не меняется; `None` (по умолчанию) — каждый раз новая выборка.
- Неверный аргумент — отрицательный или больший процент, `True`, `"10"`, `nan`, другой метод,
  отрицательное значение `seed`, `1.0` как `seed` — даёт `QueryError` при вызове.
- **Где работает.** Строки модели, `values()`/`values_list()`, `count()`, `exists()`, `aggregate()`,
  группы `group_by()`/`annotate()`, `select_related()` (выборка — из таблицы модели, связанные строки
  присоединяются к ней полностью) и запрос как значение подзапроса
  (`filter(pk__in=Event.objects.sample(10))`).
- **Запись.** `update()`, `delete()` и `hard_delete()` у выборки дают `QueryError`: `TABLESAMPLE` есть
  только в `SELECT`. Записывайте выбранные строки через их ключи:
  `Event.objects.filter(pk__in=Event.objects.sample(10, seed=1)).delete()`.
- `Meta.manager`, у которого `get_queryset()` возвращает выборку, даёт `ConfigurationError`, когда
  связи нужна его область видимости как условие `JOIN`, — как и `with_cte()`. Объединённый запрос
  (`union()`/...) даёт `QueryError` — берите выборку у ветки.
- PostgreSQL и ClickHouse (`features.supports_table_sample`): на другой базе запрос даёт
  `UnSupportedError` до отправки SQL. Для его запроса [план](query-plan-cache.ru.md) не хранится:
  процент и `seed` записаны во `FROM`.
- ClickHouse делает выборку по ключу выборки таблицы — `SAMPLE <доля>`, без метода и `seed`: см.
  [его выборку](../dialects/clickhouse/query-modifiers.ru.md#sample).

## <a id="returning"></a>Записанные строки

`update(...)`, `delete()` и `hard_delete()` возвращают число записанных строк. `.returning()` у них
возвращает сами строки — записанные один раз и прочитанные той же командой:

```python
# Названные поля каждой обновлённой строки в записанном виде — словарь на строку.
rows = await Product.objects.filter(stock__lt=5).update(price=F("price") * 1.1).returning("id", "price")
# [{"id": 3, "price": Decimal("11.00")}, {"id": 8, "price": Decimal("5.50")}]

# Объекты модели — со всеми полями, сохранённые.
products = await Product.objects.filter(category=old).update(category=new).returning()

# Удалённые строки.
gone = await Session.objects.filter(expires_at__lt=now).delete().returning("id", "user")
```

```sql
UPDATE "product" SET "price"="price"*$1 WHERE "stock"<$2 RETURNING "id","price"
```

- **Поля.** Обычное поле модели, прямая связь (`"user"` — её ключ, кортеж для составного) или `"pk"`
  (кортеж для составного первичного ключа); значения раскодируются так, как их читает поле. Путь
  через связь, обратная связь или «многие-ко-многим», неизвестное имя или имя, названное дважды, дают
  `FieldError` при вызове `returning()`.
- **Без полей** возвращаются объекты модели: запись возвращает первичные ключи, а строки читаются по
  ним в транзакции записи — у каждого объекта загружены все поля, как у обычного запроса.
- **Обновление** возвращает каждую строку в записанном виде: новые значения, поля `auto_now` и
  увеличенную версию `Meta.optimistic_lock_field`. Значение, записанное из выражения и проверенное в
  Python (целое или десятичное в SQLite), возвращается таким, каким сохранено. Фильтр через связь, срез
  и сортировка работают так же, как у `update()`.
- **Удаление** возвращает каждую строку такой, какой она была при удалении. Обычный `DELETE`, который
  база выполняет сама, возвращает названные поля собственным `RETURNING`. Удаление, которое hare
  выполняет в Python, — `on_delete`, который база не обеспечивает, модель с циклом каскада, объекты —
  сначала читает подходящие строки и удаляет их в одной транзакции. Мягкое удаление
  (`Meta.soft_delete_field`) возвращает строки после него: с заполненным временем удаления; уже мягко
  удалённая строка повторно не удаляется и не возвращается (`include_deleted().delete()`).
  `hard_delete().returning()` удаляет по-настоящему.
- Ни одна строка не подошла — пустой список. `none()` и `limit(0)` не отправляют команду.
- Порядок строк — порядок базы (`RETURNING`), иначе порядок, в котором удаление их нашло.
- `returning()` требует `features.supports_returning` (PostgreSQL и SQLite 3.35+): на другой базе даёт
  `UnSupportedError` до отправки SQL. Команда сохраняет свой [план](query-plan-cache.ru.md), а
  возвращаемые поля входят в его ключ.
- **Значения до обновления.** `update(...).returning(*fields, old=(...))` возвращает ещё и поля из
  `old` такими, какими они были до обновления, под ключом `"old"` — изменение каждой строки в той же
  команде (PostgreSQL 18, `RETURNING old.column`):

    ```python
    rows = await Account.objects.filter(id__in=ids).update(balance=F("balance") - fee).returning(
        "id", "balance", old=("balance",)
    )
    # [{"id": 7, "balance": Decimal("90.00"), "old": {"balance": Decimal("100.00")}}, ...]
    ```

    `old` принимает те же имена, что и поля, и требует названных полей (у объектов модели нет места для
    старых значений); `"old"` тогда не может быть среди названных полей. Сервер без
    `features.supports_returning_old_new` (PostgreSQL до 18, SQLite) даёт `UnSupportedError` до
    отправки SQL; `merge().returning()` принимает `old=` так же.

## <a id="insert-from"></a>Вставка строк запроса

```python
def insert_from(self, queryset: QuerySet, *, fields: Sequence[str]) -> InsertFromQuery
```

`insert_from()` записывает строки, которые выбирает запрос, в таблицу модели одной командой — строки
не попадают в Python. Возвращает число записанных строк:

```python
written = await Archive.objects.insert_from(
    Event.objects.filter(finished=True).values("name", "tournament_id", archived=F("modified")),
    fields=["title", "tournament", "archived_at"],
)
```

```sql
INSERT INTO "archive" ("title","tournament_id","archived_at","created")
SELECT "name","tournament_id","modified",$1 FROM "event" WHERE "finished"=$2
```

- **`fields`** — записываемые поля в том порядке, в каком источник выбирает колонки: обычное поле или
  прямая связь с ключом из одной колонки (`"tournament"` записывает колонку её ключа). Связь с
  составным ключом записывается через поля её ключа; неизвестное, вычисляемое базой или «многие ко
  многим» поле, а также поле, названное дважды, дают `FieldError` при вызове.
- **Источник** — запрос `values()`/`values_list()`, выбирающий по одной колонке на поле (в том числе
  выражения и вычисляемые значения, `values(total=F("price") * F("quantity"))`), запрос объектов модели
  (он выбирает свои поля с теми же именами) или `union()` таких запросов. Фильтры, соединения,
  сортировка, срезы и `distinct()` работают как при чтении. Источник, выбирающий другое число колонок,
  даёт `QueryError` до отправки SQL. Источник выполняется на подключении целевой модели.
- **Неназванные поля** получают значение по умолчанию базы (`db_default`, автоинкрементный ключ). Поле
  `auto_now`/`auto_now_add` получает момент вставки — один на все строки. Python-значение `default=`
  (функция, константа) не вычисляется — назовите поле или задайте ему `db_default`.
- **Арендаторы.** Неназванное `Meta.tenant_field` записывается как активный арендатор (`QueryError`, если
  область видимости не из одного арендатора, как у `create()`). При активной области арендатор нельзя
  читать из строк источника, как и связь с моделью с арендаторами — вставка не может проверить их по
  строкам, — это даёт `QueryError`; при `all_tenants()` у целевой модели строки источника записываются
  как есть.
- Строки обратно не читаются: объекты не создаются, `save()` не вызывается, сигналы объектов модели не
  отправляются; наблюдатель `RowsChanged` получает вставку без ключей.
- Объединённый целевой запрос (`union()`/...) даёт `QueryError`. Для команды
  [план](query-plan-cache.ru.md) не хранится.

## <a id="merge"></a>Слияние строк

```python
def merge(self, source, *, on: str | Sequence[str] | Mapping[str, str]) -> MergeQuery
```

`merge()` сопоставляет строки источника со строками модели и записывает их одной командой `MERGE` —
по веткам, в порядке их добавления: найденная строка обновляется, удаляется или остаётся как есть,
строка источника без пары вставляется или пропускается, а (PostgreSQL 17+) строка модели, которой не
нашлось пары в источнике, обновляется, удаляется или остаётся как есть. Возвращает число записанных
строк.

```python
from hare.query.expressions import F, Q

written = await (
    Stock.objects.merge(
        [{"sku": "A-1", "count": 5}, {"sku": "B-7", "count": 2}],
        on="sku",
    )
    .when_matched(delete=True, condition=Q(count__lte=F("merge_source__count")) & Q(merge_source__count__lt=0))
    .when_matched(update={"count": F("count") + F("merge_source__count")})
    .when_not_matched(insert={"sku": F("merge_source__sku"), "count": F("merge_source__count")})
)
```

```sql
MERGE INTO "stock" USING (SELECT column1 AS "sku", column2 AS "count"
  FROM (VALUES (CAST($1 AS VARCHAR), CAST($2 AS INTEGER)), (...)) AS "hare_merge_values") AS "hare_merge_source"
ON "stock"."sku"="hare_merge_source"."sku"
WHEN MATCHED AND ... THEN DELETE
WHEN MATCHED THEN UPDATE SET "count" = "stock"."count"+"hare_merge_source"."count", "version" = "stock"."version"+$3
WHEN NOT MATCHED THEN INSERT ("sku", "count") VALUES ("hare_merge_source"."sku", "hare_merge_source"."count")
```

- **Источник** — список словарей с одинаковыми ключами (каждый ключ — колонка; ключ с именем поля
  модели приводится к его типу, связанный объект записывается своим ключом), запрос `values()` (его
  имена — колонки), запрос объектов модели (все его поля) или `union()` запросов `values()`. Запрос
  `values_list()` даёт `QueryError` — у его колонок нет имён. Пустой список ничего не записывает и не
  отправляет команду.
- **`on`** — сопоставляемые поля: имя поля, список имён или словарь «поле модели → колонка источника»
  (`on={"sku": "code"}`). Поле — обычное поле или прямая связь с ключом из одной колонки.
- **Строка источника** читается как `merge_source__<колонка>` — в значениях ветки
  (`F("merge_source__count")` и выражения от него) и в её условии (`Q(merge_source__count__gt=0)`, любой
  оператор фильтра). `F("<поле>")` и обычные ключи `Q` читают строку модели. Колонка, которой нет в
  источнике, даёт `FieldError`; модель с полем `merge_source` даёт `QueryError`.
- **Ветки** — `when_matched(update=... | delete=True | do_nothing=True, condition=Q)`,
  `when_not_matched(insert=... | do_nothing=True, condition=Q)`,
  `when_not_matched_by_source(update=... | delete=True | do_nothing=True, condition=Q)`: ровно одно
  действие в каждой. Строка попадает в первую ветку, условие которой выполняется; `do_nothing` не даёт
  взять её следующим веткам. Значения — обычные значения, связанные объекты, `F()` и выражения; значение
  приводится и проверяется полем так же, как у `update()`.
- **Читаемые строки модели** — строки целевого запроса: его фильтры
  (`Stock.objects.filter(warehouse=w).merge(...)`) и область видимости по умолчанию (мягко удалённые
  строки, строки других арендаторов) ограничивают строки, с которыми может совпасть строка источника,
  — скрытая строка считается отсутствующей, и её строка источника идёт в `when_not_matched()`.
  `when_not_matched_by_source()` тоже берёт только эти строки. Целевой запрос не может вычислять
  значения, брать срез, `distinct()`, `group_by()`, `sample()` и `with_cte()`, а фильтр — проходить
  через связь (`QueryError`).
- **Что заполняется само.** Обновление ставит полям `auto_now` момент команды и увеличивает
  `Meta.optimistic_lock_field`; вставка заполняет поля `auto_now`/`auto_now_add` и, при области
  видимости из одного арендатора, `Meta.tenant_field`. Python-значение `default=` при вставке не
  вычисляется — назовите поле или задайте ему `db_default`. Обновление первичного ключа даёт
  `QueryError`.
- **Арендаторы.** При активной области арендатор, записываемый из выражения, обновление, выводящее
  строку из области, или связь с моделью с арендаторами, записываемая из выражения, дают `QueryError`;
  связанные объекты, записанные обычными значениями, проверяются по области их модели. При
  `all_tenants()` у целевой модели значения записываются как есть.
- **Удаление** выполняет сама база: модель с `Meta.soft_delete_field`, `on_delete`, который база не
  обеспечивает, или `PROTECT` дают `QueryError` для ветки `delete=True` — используйте `delete()`.
- **`.returning(*fields)`** (PostgreSQL 17+) возвращает записанные строки: словарь названных полей и
  `"merge_action"` — `"insert"`, `"update"` или `"delete"` (удалённая строка — такой, какой была). Нужно
  назвать хотя бы одно поле. `old=("count",)` добавляет эти поля такими, какими они были до слияния, под
  ключом `"old"` — None у вставленной строки (PostgreSQL 18, [как у `update()`](#returning)).
- PostgreSQL 15+ (`features.supports_merge`); `when_not_matched_by_source()` и `returning()` требуют
  PostgreSQL 17 (`supports_merge_not_matched_by_source`, `supports_merge_returning`). На другой базе
  или более старом сервере слияние даёт `UnSupportedError` до отправки SQL. Слияние без веток даёт
  `QueryError`. Для команды [план](query-plan-cache.ru.md) не хранится.
