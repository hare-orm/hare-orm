# Методы QuerySet

## Список методов {: #method-reference }

Обозначения: **цепочка** — возвращает новый `QuerySet` (ничего ещё не выполняется); **await** —
возвращает особый объект, который нужно дождаться через `await`; **конечный** — сам
`QuerySet`/`QuerySetSingle` становится объектом для `await`.

Запрос, не закреплённый за подключением через `using()`, выбирает подключение при
каждом выполнении. Поэтому один и тот же объект запроса можно снова выполнить после окончания
транзакции, внутри другой транзакции или из другой задачи — каждый раз используется подключение (или
открытая транзакция), текущее в этот момент.

| Метод | Вид | Что делает |
|---|---|---|
| <code>filter(&#42;args: Q &#124; Exists, &#42;&#42;kwargs)</code> | цепочка | Копирует запрос и добавляет условия через AND. Поддерживает `related__field=...`, позиционные объекты `Q` и условия `Exists(...)`. Как в Django, запрос со срезом (`.limit()`/`.offset()`/`qs[a:b]`) фильтровать нельзя: `filter()`/`exclude()`/`get(**kwargs)`/`get_or_none(**kwargs)` на нём дают `QueryError("Cannot filter a query once a slice has been taken.")` — сначала фильтр, потом срез. Запрос `.values()`/`.values_list()` (или операция над множествами) в роли значения фильтра (`id__in=...`) должен выбирать одну колонку — если больше, будет `QueryError("Cannot use multi-field values as a filter value...")`, а не ошибка базы. |
| <code>exclude(&#42;args: Q &#124; Exists, &#42;&#42;kwargs)</code> | цепочка | То же, но отбрасывает строки, которые подходят под **все** условия вызова вместе, как в Django: `exclude(a=1, b=2)` — это `NOT (a = 1 AND b = 2)`, то же, что `exclude(Q(a=1, b=2))`. Для связи «ко многим» hare ведёт себя иначе, чем Django: условия одного вызова `exclude()` (или одного `~Q(...)`) относятся к **одной и той же** связанной строке, как в `filter()` — `exclude(books__name="a", books__rating=5)` отбрасывает автора, только если одна книга подходит под оба условия, и оставляет автора, у которого одна книга называется «a», а другая имеет оценку 5. В Django условия одного `exclude()` не обязательно относятся к одной строке, поэтому такой автор тоже отбрасывается; чтобы получить это в hare, используйте отдельные вызовы — `.exclude(books__name="a").exclude(books__rating=5)` отбрасывает авторов, у которых любая книга подходит под любое из условий. Каждый отдельный `.exclude()` отбрасывает свои строки. `exclude()` через связь «ко многим» — это подзапрос `NOT EXISTS`, поэтому он не добавляет в запрос `JOIN`: следующий `.filter(books__...)` всё равно строит `JOIN`, который читают `values("books__...")`, `order_by("books__...")` и `Count("books")`. Пустой `Q()` здесь, как и везде, ничего не делает — `~Q()` и `exclude(Q())` подходят под каждую строку. Как обрабатываются колонка или значение `NULL` — см. [Как работает NULL](filters.ru.md#null-semantics) ниже. |
| <code>annotate(&#42;&#42;kwargs: Expression &#124; Term)</code> | цепочка | Добавляет в `SELECT` вычисляемые значения и агрегаты и регистрирует для них операторы фильтра, чтобы потом по ним можно было вызывать `.filter()`/`.exclude()` (условие попадает в `HAVING`, если в нём есть агрегат, — в том числе в выражении, смешивающем агрегат с колонкой, вроде `Count("books") + F("id")`, или когда поле сравнивается с агрегатным вычисляемым значением, `budget__lt=F("total")`; иначе — в `WHERE`). Имя, совпадающее с полем модели (или `pk`), даёт `FieldError`, как и такое имя для выражения в `alias()`/`values()`/`values_list()`: иначе все остальные обращения к нему читали бы вычисляемое значение вместо поля. Значение, которое не является выражением (например, просто строка с именем поля — используйте `F("field")`), даёт `TypeError`, и в `alias()` тоже. Как в Django, `.alias()`, которое ничто не читает — ни фильтр, ни сортировка, ни группировка, ни другое вычисляемое значение, ни поле `values()`, — в запрос не попадает, поэтому его `JOIN` «ко многим» не размножает строки. |
| `alias(**kwargs)` | цепочка | Как `annotate()` — выражение можно использовать в `.filter()`/`.order_by()`, — но в `SELECT` оно попадает, только если `.values()`/`.values_list()` попросят его по имени. `FieldError`, если имя совпадает с полем модели или с `pk`. |
| <code>order&#95;by(&#42;orderings: str &#124; Ordering)</code> | цепочка | `'-field'` — по убыванию (`DESC`); путь внутрь поля JSON или вычисляемого значения (`'-data__score'`) сортирует по значению JSON, в порядке `jsonb` на любой базе; [часть даты](values.ru.md#date-part-paths) (`'-created__month'`) сортирует по этой части; `F('field').asc()`/`.desc()` с `nulls_first=True`/`nulls_last=True` задают, где окажутся `NULL`, — см. [Порядок NULL при сортировке](#null-ordering). Поддерживает `related__field`; имя прямой связи (`'tournament'`), в том числе в конце пути через связь (`'event__tournament'`), сортирует по колонкам её ключа (`tournament_id`, `event__tournament_id`), и в `Meta.ordering` тоже; имя связи «ко многим» или обратной «один-к-одному» (`'events'`, `'-tags'`) сортирует по первичному ключу связанной модели (по строке на каждую связанную строку), а `pk` в конце пути (`'author__pk'`, `'tags__pk'`) — по полям первичного ключа, как в Django, — см. [связи и `pk` в путях к полям](values.ru.md#relation-field-paths). Нельзя вызывать после `.after_cursor()`. Как в Django, запрос со срезом (`qs[a:b]`, `.limit()`, `.offset()`, индекс) нельзя пересортировать — `QueryError("Cannot reorder a query once a slice has been taken.")`; сначала сортировка, потом срез (`order_by("name").limit(2)`). То же относится к `union()` и к операции над множествами из `.values()`/`.values_list()`. `order_by()` без аргументов убирает всю сортировку, включая `Meta.ordering`. |
| `orderings -> tuple[tuple[str, Order], ...]` | свойство | Сортировка, заданная через `order_by()`, — по одной паре `(путь, Order)` на каждую колонку сортировки: `pk` означает все поля первичного ключа, прямая связь — колонки её ключа (`"tournament"` → `"tournament_id"`), `F("score").desc(nulls_last=True)` — `("score", Order.DESC_NULLS_LAST)`. Пусто без `order_by()` (тогда запрос сортируется по `Meta.ordering`, которая сюда не входит, — читайте `Model._meta.ordering`) и после `order_by()` без аргументов, который оставляет запрос несортированным. `before_cursor()` оставляет его как задано; копия запроса его сохраняет, следующий `order_by()` заменяет. `Order` находится в `hare.sql`. |
| `after_cursor(*values)` | цепочка | Постраничный вывод по курсору (по значениям ключа сортировки) вместо `OFFSET` — нужен `.order_by()`; поддерживает `related__field` в сортировке (связь соединяется так же, как в `order_by`), но не вычисляемое значение. У запроса с `.distinct(<поля>)` граница применяется к строкам, которые выбирает `DISTINCT ON` (через `pk IN (SELECT ...)`), как и у `before_cursor()`. |
| `before_cursor(*values)` | цепочка | Предыдущая страница: строки строго **до** значений. Выполняется в точно обратной сортировке (поэтому `.limit(n)` берёт `n` строк, ближайших к курсору) и возвращает строки в исходном порядке `.order_by()` — для объектов, `values()` и `values_list()` одинаково; `first()`/`get()` берут строку прямо перед курсором. Ошибки те же, что у `after_cursor()`. Вместе с `after_cursor()` (в любом порядке) задаёт окно; повторный вызов любого из них заменяет только свою границу. Не поддерживается в `iterator()`/`stream()`. |
| `cursor_values(instance) -> tuple` | синхронно | Значения курсора объекта `instance` для текущего `.order_by()` — передавайте их в `after_cursor()`/`before_cursor()`. Сортировка `related__field` требует загруженной связи (`select_related()`), иначе `QueryError`; связь `NULL` даёт `None`; сортировка по внешнему ключу или «один-к-одному» (`'city__country'`) даёт значение ключа, а не связанный объект; связь «ко многим» или вычисляемое значение дают `FieldError`. |
| `none()` | цепочка | Заведомо пустой запрос — ничего не отправляет в базу (`count`/`exists`/`values`/`delete`/`update`/... отвечают без запроса). |
| `limit(n)` / `offset(n)` | цепочка | `QueryError` при отрицательном значении. `qs[start:stop]` — то же, что `.offset(start).limit(stop-start)` (шаг только `1`/`None`, `start`/`stop` не отрицательные); `stop`, не превышающий `start` (`qs[3:3]`, `qs[4:2]`), не выбирает строк, как срез списка. Смещение без ограничения записывается в SQLite как `LIMIT -1 OFFSET n` (SQLite не принимает `OFFSET` без `LIMIT`), и для запросов, и для объединений. `qs[i]` — один объект с индексом `i`; если его нет, при `await` будет `IndexError`; отрицательный индекс даёт `QueryError`. Объединение принимает срезы и индекс так же. |
| `distinct(*fields)` | цепочка | Без аргументов — обычный `DISTINCT`. С аргументами (**только PostgreSQL**) — `DISTINCT ON (поля)`: поле, вычисляемое значение или [часть даты](values.ru.md#date-part-paths) (`"created__date"`): `order_by` должен начинаться с тех же полей в том же порядке; `count()`/`exists()` (и со срезом) считают строки, которые он выбирает. Как в Django, `distinct()` (с полями или без) на запросе со срезом даёт `QueryError("Cannot create distinct fields once a slice has been taken.")` — вызывайте его до среза. |
| `union(*other_qs, all=False)` | цепочка | Возвращает QuerySet объединённых строк — тот же класс `QuerySet`, поэтому всё описанное ниже — обычный API QuerySet. Цепочка вызовов `union()`/`union(all=True)`/`intersection()`/`difference()` объединяет каждую новую ветку со всем результатом, полученным до неё, в порядке вызовов: `a.union(b).union(c, all=True)` — это `(a UNION b) UNION ALL c` (повторы, которые приносит `c`, остаются), `a.union(b, all=True).union(c)` убирает все повторы, а `a.union(b).intersection(c)` — это `(a UNION b) INTERSECT c` на любой базе (производная таблица не даёт более высокому приоритету `INTERSECT` в PostgreSQL изменить смысл). У каждой ветки может быть свой `.annotate()`, если имя не совпадает с настоящим полем модели. Вычисляемое значение раскодируется через поле первой ветки, у которой оно есть, как в Django: у ветки с `Value(None)` поля нет, и она ничего не меняет (`date` в SQLite остаётся `date`), а не раскодированным значение остаётся, только если у значения другой ветки поля нет вовсе (например, `Value("text")`). `.order_by()` у объединения ссылается на выбранные колонки по номеру, поэтому работает на любой базе и с ветками, соединяющими связь или группирующими по агрегату. `select_related()`/`prefetch_related()` у отдельной ветки (до `.union()`/`.intersection()`/`.difference()`) по-прежнему дают `QueryError`: загруженная связь не переживёт слияния в общий результат. Вызывайте `.prefetch_related()` у самого объединённого QuerySet: он выполняет предзагрузку пачкой по уже полученному списку результата через `prefetch_related_objects()`, после выполнения, и принимает то же (`str`/`Prefetch(...)`), что `QuerySet.prefetch_related()`. Ветка сама может быть операцией над множествами — `a.union(b.intersection(c))` объединяет `b INTERSECT c` целиком. Ветку — и вложенную операцию тоже — можно отсортировать и взять у неё срез (`a.order_by("-rank")[:3].union(b)`): она объединяется как производная таблица своих строк. Все ветки выполняются на одном соединении — ветка, чья модель или роутер выбирает другое соединение, чем у первой ветки, даёт `QueryError`. Объединение работает как значение `__in`, как запрос: `filter(pk__in=a.union(b))`, `filter(author__in=a.union(b))` сравнивают с первичным ключом его строк. Получение результата работает, как у запроса: `count()`, `exists()` (со срезом), `first()`/`last()` (без сортировки — по первичному ключу; `last()` у объединения со срезом даёт `QueryError`), `get(*args, exception=None, **kwargs)`/`get_or_none(*args, **kwargs)` (`DoesNotExist`/`MultipleObjectsReturned`, как обычно), `iterator(chunk_size=1000)` (страницы через `OFFSET`, в порядке `order_by()`, а затем всех выбранных колонок — и для объединения нескольких моделей ещё и модели — чтобы равные строки шли в постоянном порядке; срез ограничивает перебор; `prefetch_related()` выполняется для каждой страницы) и `stream(chunk_size=1000)` (курсор на стороне сервера, как [`QuerySet.stream()`](#stream), — только PostgreSQL, внутри транзакции, без `prefetch_related()`). В отличие от Django, который не принимает там условий, `get()`/`get_or_none()` их принимают: условия применяются к каждой ветке до объединения (условие на строку оставляет те же строки до и после `UNION`/`INTERSECT`/`EXCEPT`), а на объединении со срезом дают `QueryError` — его строки зависят от строк, которые условие отбрасывает. `aggregate()` считает по объединённым строкам. Методы, меняющие то, какие строки выбирает запрос, — `filter()`/`exclude()`/`annotate()`/`alias()`/`distinct()`/`group_by()`/`only()`/`defer()`/`select_related()`/`select_for_update()`/`with_cte()`/курсоры/`all_tenants()`/`include_deleted()`/`only_deleted()` — и записи (`update()`/`delete()`/`hard_delete()`/`create()`/...) у самого объединения дают `QueryError`, как в Django, — применяйте их к веткам. Запросы к моделям объединяются с запросами к моделям, а запросы `.values()`/`.values_list()` — друг с другом (смесь — `QueryError`, см. [Запросы `values()` / `values_list()`](values.ru.md)); `.values()`/`.values_list()` у объединения запросов к моделям превращают его в объединение значений. |
| `with_cte(name, query)` | цепочка | Добавляет именованный `WITH` (общее табличное выражение, CTE), не меняя собственный `FROM` запроса. |
| `select_for_update(nowait=False, skip_locked=False, of=(), no_key=False)` | цепочка | `SELECT ... FOR UPDATE`. Если запрос выполняется на базе без `FOR UPDATE` (`features.supports_select_for_update` ложно, например SQLite), даёт `UnSupportedError`: молча пропустить вызов значило бы позволить вызывающему думать, что строки заблокированы, хотя это не так. На базе, которая это умеет, даёт `QueryError`, если запрос выполняется вне блока `Transactions.atomic()`: иначе блокировка была бы взята и тут же снята (автоматическая фиксация), не давая настоящей защиты, но создавая её видимость. `of` принимает `"self"` (или имя таблицы самой модели) и пути прямых связей в том виде, в каком их принимает `select_related()` (`"author"`, `"author__country"`); в SQL они становятся псевдонимами, под которыми запрос соединяет таблицы. Связь, названная в `of`, соединяется через `INNER JOIN` вместо `LEFT OUTER JOIN` (PostgreSQL не может блокировать сторону внешнего соединения, допускающую `NULL`), поэтому каждый шаг её пути должен быть внешним ключом `NOT NULL` с `db_constraint=True` и без условий мягкого удаления, арендатора или `Select(extra_condition=...)`; иначе, а также для имени, которое не является таким путём или не соединяется запросом, будет `QueryError`. Без `of` запрос с любым `JOIN` блокирует только строки самой модели. Запрос с агрегатным вычисляемым значением или `GROUP BY` даёт `QueryError`: сгруппированная строка обозначает несколько строк таблицы, которые SQL заблокировать не может, — блокируйте строки отдельным запросом. То же относится к запросу с `.distinct()`/`.distinct(<поля>)`, к запросу, читающему оконную функцию (`Window(...)`), и к ветке `union()`/`intersection()`/`difference()` — в том числе запросу `.values()`/`.values_list()`, — их PostgreSQL тоже заблокировать не может. |
| `group_by(*fields)` | цепочка | До или после `.values()`/`.values_list()`, которые затем возвращают по строке на группу. Объекты моделей всегда группируются по первичному ключу, поэтому на запросе объектов строки не меняются — `await qs`, `count()`, `exists()`, `contains()`, `update()` и `delete()` видят по строке на объект. `aggregate()` работает над сгруппированными строками (теми, что вернул бы `.values()`) и может читать только поля группировки и вычисляемые значения (иначе `QueryError`): `.annotate(n=Count("id")).group_by("author_id").aggregate(most=Max("n"))` — наибольшее число на одного автора, как `values().annotate().aggregate()` в Django. Сгруппированный запрос `.values()`/`.values_list()` не учитывает `Meta.ordering` (её колонки не сгруппированы) — без сортировки он упорядочен по ключу группировки. |
| `values_list(*fields, flat=False, named=False, **expressions)` | цепочка | QuerySet кортежей (отдельных значений с `flat=True`, именованных кортежей с `named=True`) — см. [Запросы `values()` / `values_list()`](values.ru.md). Несовместим с `.only()`/`.defer()`. Без аргументов — все поля и вычисляемые значения. Имя может быть путём внутрь поля JSON или вычисляемого значения (`"data__owner__name"`), читаемым так же, как его читает `F()`, или [частью даты](values.ru.md#date-part-paths) (`"created__year"`). `named=True` возвращает каждую строку как именованный кортеж с атрибутом на каждое выбранное имя (имя, которое не является допустимым идентификатором, становится `_<номер>`); `flat` вместе с `named`, позиционный аргумент не-строка или именованный аргумент, который не является выражением, дают `QueryError`. Полноценный запрос, возвращающий кортежи, — см. [Запросы `values()` / `values_list()`](values.ru.md). |
| `values(*args, **kwargs)` | цепочка | QuerySet словарей — см. [Запросы `values()` / `values_list()`](values.ru.md). `kwargs` — пары `псевдоним="имя_поля"` или `псевдоним=<выражение>`; любое другое значение даёт `QueryError`. Имя может быть путём внутрь поля JSON или вычисляемого значения (`"data__owner__name"`), читаемым так же, как его читает `F()`, или [частью даты](values.ru.md#date-part-paths) (`"created__year"`). Несовместим с `.only()`/`.defer()`. Полноценный запрос, возвращающий словари, — см. [Запросы `values()` / `values_list()`](values.ru.md). |
| `delete()` | await | `DeleteQuery`, возвращает число строк. Каскад в Python идёт пачками в одной транзакции: каждая волна затронутых строк стоит одного запроса на связь и модель (больше — только сверх ограничения базы на число параметров), а не запроса на строку, и все строки, которые он мягко удаляет, получают одно и то же `deleted_at`. Результат ожидания — число строк. |
| `update(**kwargs)` | await | `UpdateQuery`, возвращает число строк. Запрос с `.distinct()`, выбирающий вычисляемое значение через связь «ко многим» (`F("books__name")`), возвращает строку на каждое различное значение, и `count()` тоже. `.group_by()` на него не влияет — см. `group_by()`. `QueryError` для `.distinct(<поля>)`. |

Любой другой срез, строки которого могут повторять первичный ключ (фильтр, вычисляемое значение или сортировка через связь «ко многим»), и модель с составным первичным ключом дают `QueryError` — агрегируйте запрос `.values()`/`.values_list()` со срезом. |

| `bulk_create(objects, batch_size=None, ignore_conflicts=False, update_fields=None, on_conflict=None, on_conflict_constraint=None, conflict_where=None, returning=None, use_copy=False)` | await | Сгенерированные первичные ключи, колонки `GeneratedField` и пропущенные колонки с `db_default` **не** записываются обратно в объекты, если не передан `returning=True` (только PostgreSQL, через `RETURNING`; в SQLite не поддерживается, потому что порядок строк многострочного `RETURNING` там не обязан совпадать с порядком вставки). При `None` (по умолчанию) берётся `Meta.returning` (по умолчанию `False`) — задайте его на общей базовой модели, чтобы не передавать `returning=True` в каждом вызове; явные `True`/`False` здесь всегда важнее, а значение, **унаследованное** от `Meta.returning`, вместе с `use_copy=True` или на SQLite молча уступает, а не вызывает ошибку. `use_copy=True` загружает строки через протокол `COPY` PostgreSQL вместо `INSERT` с параметрами — быстрее для больших пачек, но несовместимо с явным `returning=True` и со всеми аргументами обработки конфликтов (у `COPY` нет `RETURNING`/`ON CONFLICT`) и не поддерживается в SQLite. `COPY` не поддерживает в модели поля массивов и диапазонов и поля расширений PostgreSQL (`CitextField`, `PostGISField`, `TSVectorField`) ни на одном драйвере — даёт `UnSupportedError` с именем поля, проверяется одинаково на стороне Python до обращения к драйверу; для такой модели используйте `use_copy=False`. `update_fields`/`on_conflict` принимают имена полей: колонка `source_field` определяется сама, имя прямой связи означает колонки её ключа (`owner` → `owner_id`), неизвестное имя даёт `FieldError`; генерируемое поле, `Meta.tenant_field`, `Meta.optimistic_lock_field` или `Meta.soft_delete_field` в `update_fields` дают `QueryError`. У конфликтующей строки обновляются и поля `auto_now` (и увеличивается `Meta.optimistic_lock_field`); конфликтующая мягко удалённая строка обновляется, но остаётся удалённой. Поле из `update_fields`, значение которого у всех объектов оставлено на `db_default`, всё равно обновляется — значением по умолчанию из базы. С `returning=True` объект с явно заданным первичным ключом тоже получает свои колонки `GeneratedField`/пропущенные `db_default`, вставка-или-обновление модели с `Meta.optimistic_lock_field` читает увеличенную версию строки, а при `ignore_conflicts=True` из нескольких объектов с одним ключом конфликта в одном вызове сохранённым остаётся только первый (тот, чья строка вставлена). С `update_fields` несколько объектов с одним ключом конфликта в одном вызове записываются по порядку на любом драйвере, поэтому побеждают значения последнего; с `returning=True` каждый из них получает первичный ключ строки. Каждый объект должен быть объектом именно этой модели (другая модель, модель с той же абстрактной базой или подкласс со своей таблицей дают `QueryError`), а объект, загруженный через `.only()`/`.defer()`, должен содержать все колонки, которые записывает вставка (`IncompleteInstanceError`). Собственные дополнительные параметры команды (область арендатора и увеличение версии при вставке-или-обновлении) учитываются в ограничении на число параметров при выборе размера пачки. Модель, все колонки которой берутся из значений по умолчанию базы, записывается одним `INSERT ... SELECT FROM generate_series(...)` в PostgreSQL (одним `DEFAULT VALUES` на объект в SQLite). Если `bulk_create()` завершился ошибкой, объекты остаются такими, какими были до вызова (первичный ключ, возвращённые колонки, признак сохранённости), даже если более ранние пачки уже были записаны и затем откачены. С `use_copy=True` на `asyncpg` несколько команд `COPY` (объекты с явным первичным ключом и без него загружаются отдельно, как и пачки `batch_size`) тоже выполняются в одной транзакции. `COPY` драйвера `rust_pg` не может участвовать в транзакции: объекты с явным первичным ключом и без него в одном вызове `use_copy=True` дают `UnSupportedError` ещё до записи, а пачки `batch_size` фиксируются по одной — после ошибки объекты уже записанных пачек остаются помеченными как сохранённые, остальные — как были. `on_conflict_constraint` не поддерживается в SQLite. `conflict_where` (только PostgreSQL) повторяет условие `WHERE` частичного уникального индекса, чтобы `ON CONFLICT (...) WHERE <conflict_where>` мог на него указать; несовместимо с `on_conflict_constraint` и требует, чтобы `on_conflict` называл колонки этого индекса. |
| `bulk_update(objects, fields, batch_size=None, returning=None)` | await | Не поддерживает поля «многие-ко-многим» и обратных связей и значения `F()`/выражения (`QueryError` — используйте `.update()` или `save()`); требует первичный ключ у каждого объекта. `returning=True` добавляет `RETURNING`, возвращающий свежее, пересчитанное базой значение каждой колонки `GeneratedField` в каждый успешно обновлённый объект; строки сопоставляются по первичному ключу, а не по позиции, поэтому (в отличие от `bulk_create()`) это работает на любом диалекте, а не только в PostgreSQL. На модели с `Meta.optimistic_lock_field` версия в памяти увеличивается у каждого объекта, строка которого действительно записалась (а при `track_dirty_fields` сбрасывается его снимок изменений), и только потом даётся `StaleObjectError` для строк пачки, которые не записались. Сочетается с `include_deleted()`/`only_deleted()` в любом порядке. |
| `explain(output_format=None, **options)` | `async def` | Выполняет команду, которую возвращает `sql(explain=True)` (`EXPLAIN QUERY PLAN` в SQLite), и возвращает строки плана. `output_format=` и дополнительные `**options` есть только в PostgreSQL — SQLite даёт для них `UnSupportedError`, но не для самого `.explain()`. |
| `using(alias_or_client)` | цепочка | Закрепляет запрос за конкретным подключением — по имени подключения (`"replica"`) или по клиенту (клиент транзакции, `Connections.get(alias)`); `None` снимает закрепление — см. [Несколько баз данных](../connections/multiple-databases.ru.md#using-db). |
| `get_connection(for_write=False)` | синхронно | Подключение, на котором запрос выполнился бы сейчас: закреплённое через `using()`, иначе выбор маршрутизатора (с арендатором, для которого построен запрос), иначе подключение объекта, от которого получен связанный менеджер, иначе подключение модели по умолчанию; внутри открытой на нём транзакции — клиент транзакции. Ничего не закрепляет — пример с блокировкой см. в [`Model.get_connection()`](../models/model-methods.ru.md#classmethods). |
| `iterator(chunk_size=1000)` | асинхронный генератор | Без `.order_by()` страницы идут по `Meta.ordering`, иначе по первичному ключу (по всем частям составного), как в Django; к сортировке, в которой возможны равные значения (нет первичного ключа, нет уникального поля без `NULL` и нет `UniqueConstraint` по полям без `NULL`), добавляется первичный ключ, чтобы между страницами ни одна строка не пропала и не повторилась — строки с равными значениями сортировки идут по первичному ключу. Колонка сортировки, которую `.only()`/`.defer()` не загружают, всё равно читается для курсора страницы и остаётся незагруженной в выдаваемых объектах. Использует постраничный вывод по курсору (безопасен при одновременных удалениях), когда каждое поле `order_by()` — обычная колонка этой модели; иначе переходит на `LIMIT`/`OFFSET` (НЕ безопасен при одновременных удалениях: удалённая уже выданная строка сдвигает следующие, и одна пропускается), если в сортировке есть поле связанной модели или вычисляемое значение, либо вычисляемое значение — оконная функция (условие по курсору изменило бы строки, по которым она считается). Учитывает собственные `.limit()`/`.offset()`/срез запроса и `.after_cursor()`. Запрос, который может вернуть один первичный ключ несколько раз — фильтр или вычисляемое значение (`F()`, функция, `Case`, арифметика) через связь «ко многим» или `.distinct()`, выбирающий такое вычисляемое значение, — идёт через `OFFSET` с сортировкой по этим вычисляемым значениям после первичного ключа, чтобы ни одна повторённая строка не пропала. Запрос с `.distinct(<поля>)` перебирает строки, которые выбирает `DISTINCT ON`. Страница запрашивается с одной строкой сверх `chunk_size`: по ней видно, есть ли следующая страница, и результат, который кончается на границе страницы, не требует пустого запроса после неё. |
| `stream(chunk_size=1000)` | асинхронный генератор | Настоящий курсор на стороне сервера (только PostgreSQL — в SQLite `UnSupportedError`). См. ниже. |
| `sql(params_inline=False, *, explain=False, output_format=None, **explain_options)` | синхронно | Возвращает SQL, который запрос выполнит на своём подключении, — с местами для параметров или с подставленными значениями; `explain=True` возвращает вместо него команду `EXPLAIN`. Несколько команд (массовая запись) соединяются через `;`. |

`await qs` возвращает `list[Model]` (или `Model | None`, если `.first()`/`.get()`/... сузили результат
до одной строки); `async for x in qs` тоже работает.

## Порядок NULL при сортировке {: #null-ordering }

SQLite и PostgreSQL по-разному решают, где окажется `NULL`, а простая строка сортировки оставляет
это диалекту: SQLite считает `NULL` самым малым значением (первым при `ASC`, последним при `DESC`),
PostgreSQL — самым большим (последним при `ASC`, первым при `DESC`). Если в `Player(name, score)`
лежат `a:1, b:NULL, c:2, d:3, e:NULL`, то `order_by("score", "name")` вернёт `b, e, a, c, d` в SQLite и
`a, c, d, b, e` в PostgreSQL. Это поведение по умолчанию сохраняется и действует для
`order_by("field")`/`order_by("-field")`, строк `Meta.ordering`, `first()`/`last()` и строк в
`Window(order_by=[...])`.

Чтобы место `NULL` было одинаковым на любом диалекте, передайте вместо строки `Ordering`, построенный
из `F(...)`:

```python
from hare.query.expressions import F

await Player.objects.all().order_by(F("score").desc(nulls_last=True), "name")   # 3, 2, 1, затем NULL
await Player.objects.all().order_by(F("score").asc(nulls_first=True), "name")   # сначала NULL, затем 1, 2, 3
await Employee.objects.all().order_by(F("manager__name").asc(nulls_last=True))  # в том числе NULL из LEFT JOIN
```

`F(name).asc()` / `F(name).desc()` принимают только именованные флаги `nulls_first` / `nulls_last`
(оба `True` дают `QueryError`; ни одного — оставляют поведение диалекта). `Ordering` и строки можно
свободно смешивать, и `Ordering` принимается везде, где принимается сортировка: `order_by()` (и у
`union()`), `latest()`/`earliest()`, `Meta.ordering`, `Window(order_by=[...])`, `distinct(...)` вместе
с `order_by()` (PostgreSQL), `values()`/`values_list()`, `stream()`/`iterator()`. Всё, что не строка и
не `Ordering`, даёт `QueryError`. В SQL получается `ORDER BY ... NULLS FIRST|LAST` (SQLite 3.30+).

- **`latest()` / `earliest()` не выбирают `NULL`.** Для простого имени поля на любом диалекте
  добавляется `NULLS LAST`, поэтому `NULL` никогда не побеждает: `latest("score")` — строка с
  наибольшим значением, не равным `NULL`, а `earliest("score")` — с наименьшим. Если все значения
  `NULL`, строка с `NULL` всё равно возвращается (а не `None`). Колонка, которая не может хранить
  `NULL`, сохраняет простое направление, чтобы по-прежнему работал просмотр по индексу; сортировка
  `related__field` и вычисляемое значение считаются допускающими `NULL`. Явный `Ordering`
  соблюдается: `earliest()` использует его как задано, `latest()` обращает его, как `last()`.
- **`last()` обращает сортировку точно.** Обращаются и направление, и явное место `NULL`
  (`ASC NULLS LAST` становится `DESC NULLS FIRST`), поэтому `last()` — всегда последняя строка той же
  сортировки при чтении с начала. Без явного места `NULL` поведение диалекта обращается вместе с
  направлением.
- **`after_cursor()` / `before_cursor()` / `iterator()`** следуют месту `NULL` в самой сортировке:
  явный `nulls_first`/`nulls_last` определяет, какие строки лежат после (или до) курсора (включая
  границу со значением `NULL`), иначе это определяет диалект, поэтому страницы ни в одном случае не
  теряют и не повторяют строк. `before_cursor()` при обращении сортировки отражает и место `NULL`
  (`ASC NULLS FIRST` выполняется как `DESC NULLS LAST`).
- **Планы команд** учитывают место `NULL`, поэтому два запроса, отличающиеся только им, никогда
  не делят один план.

## `Prefetch` {: #prefetch }

```python
class Prefetch:
    def __init__(self, relation: str, queryset: QuerySet, to_attr: str | None = None) -> None
```

К `queryset` уже могут быть применены `.filter()`/`.only()`/`.order_by()`; это должен быть запрос к
модели — запрос `.values()`/`.values_list()` даёт `QueryError`. `to_attr` не может совпадать с
именем поля, связи, колонки ключа (`author_id`) или другого атрибута модели, которой принадлежит
загружаемая связь, — это даёт `QueryError`, а не перезаписывает атрибут в каждом объекте.
Вложенная предзагрузка поддерживается двумя способами:

```python
# путь через связи внутри Prefetch
await Team.objects.all().prefetch_related(Prefetch("events__reporter", queryset=User.objects.filter(is_active=True)))

# .prefetch_related() прямо у запроса, переданного в Prefetch
await Team.objects.all().prefetch_related(
    Prefetch("events", queryset=Event.objects.filter(status="open").prefetch_related("reporter"))
)
```

Как в Django, путь через связь (`"events__reporter"`) загружает собственный атрибут связи
(`team.events`), даже если рядом передан `Prefetch` той же связи с `to_attr=` — тот загружает только
свой атрибут. Путь попадает в результаты `to_attr`, когда начинается с имени `to_attr`; задающий его
`Prefetch` может стоять дальше в том же вызове или в более раннем вызове `prefetch_related()`:

```python
teams = await Team.objects.all().prefetch_related(
    Prefetch("events", queryset=Event.objects.filter(status="open"), to_attr="open_events"),
    "open_events__reporter",  # reporter у каждого события из team.open_events
    "events",  # team.events — все события команды
)
```

Первое имя, которое не является ни связью модели, ни таким `to_attr`, даёт `FieldError`.

## `stream()` — настоящий курсор на стороне сервера {: #stream }

```python
async def stream(self, chunk_size: int = 1000) -> AsyncIterator[TModel]
```

В отличие от `iterator()` (который для каждой страницы выполняет новый `SELECT` через
`LIMIT`/`OFFSET` или по курсору), `stream()` открывает ровно **один** курсор на стороне сервера на
весь проход — один согласованный снимок данных на весь перебор. Строка, уже попавшая в поток курсора,
не зависит от одновременного `DELETE`/`UPDATE` посреди перебора, а ещё не прочитанные строки
читаются по снимку, сделанному при открытии курсора, а не по тому, как таблица выглядит в момент
чтения каждой строки.

```python
async with Transactions.atomic():
    async for widget in Widget.objects.filter(category="archived").stream():
        ...
```

Требует активного блока `Transactions.atomic()` на обоих драйверах PostgreSQL. Строго это
нужно только `Connection.cursor()` в `asyncpg` (он по устройству привязан к времени жизни своей
транзакции); курсору `rust_pg` самому это не нужно, но `stream()` применяет то же правило, чтобы
поведение не зависело от драйвера. В SQLite даёт `UnSupportedError` (полезной потоковой передачи со
стороны сервера там нет — используйте `iterator()`), вне транзакции — `QueryError`.
`chunk_size` — сколько строк забирать за одно обращение к серверу; его учитывает
`Connection.cursor(prefetch=...)` в `asyncpg`, а курсор `rust_pg` и так передаёт строки по одной и
его не использует. Пока поток открыт, в той же транзакции можно выполнять другие запросы — из тела
цикла или из соседних задач (`asyncio.gather()`), разделяющих транзакцию; каждое чтение курсора ждёт
своей очереди на соединении транзакции.

Если перебор заканчивается раньше — исключение, отмена или `aclose()` генератора (простой `break`
закрывает его, только когда генератор соберёт сборщик мусора; оберните его в `contextlib.aclosing()`,
чтобы закрыть на `break`), — поток сразу останавливается, не читая оставшиеся строки; у `rust_pg` его
курсор сбрасывается сразу, поэтому следующая команда транзакции не ждёт непрочитанных строк.
`COMMIT`/`ROLLBACK` самой транзакции тоже закрывают ещё открытый на ней поток; чтение из него после
этого даёт `TransactionManagementError`. У `rust_pg` `ROLLBACK`, на который нет ответа в течение 30 с,
вместо этого закрывает соединение — сервер всё равно откатывает транзакцию, а соединение не
возвращается в пул.
