# Производительность

Графики и числа ниже — опубликованные замеры 0.12.0 от 2026-10-30. Раздел о текущей методике
описывает обновлённый runner и не подтверждает, что эти исторические замеры получены по новым правилам.
Новых результатов 0.13.0 на этой странице пока нет.

hare-orm против SQLAlchemy, tortoise-orm, yara-orm и Django на PostgreSQL, SQLite и ClickHouse: одни
и те же сценарии во всех ORM, написанные так, как их пишет документация каждой ORM, и параллельная
нагрузка. У каждой базы своя страница со всеми сценариями.

## <a id="summary"></a>Сводка

Во сколько раз каждая ORM в среднем медленнее hare-orm на каждой базе: отношение средних
геометрических времени по всем сценариям, которые выполняют обе, кроме запуска. hare-orm — это
его самый быстрый драйвер на этой базе; прочерк — база, на которой ORM не работает. Последняя
строка — операций в секунду у hare-orm под нагрузкой, измеренных после параллельного прогрева
вне замера.

- [SQLite](sqlite.ru.md) — 49 сценариев: таблица из 1 000 виджетов, у каждого — гаджет, метка и

## <a id="how-it-was-measured"></a>Как измерялось

| | |
|---|---|
| Дата | 2026-10-30 |
| Машина | Windows 11, 13th Gen Intel(R) Core(TM) i5-13400, 16 CPU |
| Python | 3.14.3 |
| Релиз hare-orm | 0.12.0 |
| Прогонов | 5, медиана |

В историческом прогоне обычный сценарий брал минимум из 3–5 повторов внутри каждого запуска,
а результат на графике — медиана пяти запусков. Исходные повторы не сохранялись. Задержка нагрузки
оценивалась как общее время × конкурентность / число операций, без таймера каждой операции.
Разрушающие сценарии, запуск и нагрузка имели отдельные режимы измерения.

## <a id="current-methodology"></a>Методика текущего runner

- На PostgreSQL предел пула каждой ORM — 50 подключений. Фактическое число открытых подключений
  определяет драйвер; запуск измеряется до прогрева.
- На PostgreSQL перед каждой группой сценариев и каждым нагрузочным тестом все таблицы вне замера
  проходят `VACUUM (FULL, ANALYZE)`, а autovacuum для них выключен: каждая группа начинается с
  компактных таблиц. Иначе мёртвые строки, оставленные записями, убирает autovacuum в случайный
  момент прогона, и от того, успел ли он, зависит план запроса — с параллельным сканированием или
  без.
- Перед нагрузочным тестом параллельные задачи вне замера выполняют каждую операцию нагрузки. Это
  прогрев операций без гарантии подготовки каждого физического подключения.
- Большинство сценариев повторяются 3–5 раз; в зачёт идёт медиана, все повторы сохраняются.
  Перед повтором массовой вставки или `get_or_create()` данные этого сценария удаляются вне
  замера. Последовательные вставки накапливают строки до следующей группы; обновления
  используют уже изменённые строки. Удаления, `add()` многие-ко-многим и холодный старт
  выполняются один раз.
- Каждая ORM работает в отдельном процессе. Прогоны идут по кругу, в каждом круге ORM запускаются в
  случайном порядке; результат сценария — медиана по прогонам.
- На Windows процесс прогона отключает себе энергосбережение (EcoQoS): иначе планировщик может
  перенести процесс без окна на энергоэффективные ядра гибридного процессора, где он работает вдвое
  медленнее.
- SQLAlchemy на PostgreSQL и SQLite измеряется дважды: с обычными транзакционными сессиями, где сценарии
  записи явно фиксируют изменения, и в режиме autocommit с фиксацией каждой команды. Транзакционные и
  потоковые сценарии используют транзакционные сессии.
- Явно неподдерживаемый сценарий помечен отдельно от ошибки и отсутствующего замера; в сравнение
  входят только измеренные сценарии обеих ORM.
- Запуск — это инициализация библиотеки и её первый запрос; библиотека к этому моменту уже
  импортирована. Создание таблиц не входит в замер. В среднее запуск не входит.
- JSON сохраняет исходные повторы, seed, условия и версии. Задержка под нагрузкой измеряется от
  начала до завершения каждой операции, включая ожидание подключения.
- На SQLite каждая ORM работает с одним файлом так, как работает по умолчанию; подключения
  SQLAlchemy ждут блокировку записи файла до 30 с вместо 5 с по умолчанию — иначе нагрузка с записью
  у её пула из пяти подключений обрывается ошибкой «database is locked». `select_for_update()` на
  SQLite не измеряется: блокировок строк в нём нет.
- Таблицу ClickHouse заполняет сам сервер перед сценариями; мутация (`update()`, `delete()`) в
  каждой библиотеке завершается до возврата из вызова. SQLAlchemy работает через
  clickhouse-sqlalchemy 0.3.2 с драйвером asynch 0.2.5 на SQLAlchemy 2.0.30 и Python 3.12 — на более
  новых версиях её асинхронный драйвер не запускается.
- Каждый сценарий написан так, как его пишет документация этой ORM.
