# PostgreSQL: подключение

Как hare подключается к PostgreSQL: два драйвера, URL и его параметры TLS, меняющиеся учётные данные, как
подключение переживает перезапуск сервера или обрыв соединения и что каждый драйвер делает со значениями
готового SQL.

## <a id="choosing-a-postgres-driver"></a>Драйверы

Native-драйвер отслеживает текущих предков при преобразовании списков,
JSON-контейнеров и границ диапазонов в параметры сырых запросов. Цикл вызывает
`ValueError`; повторное использование дочернего значения в разных ветках разрешено.
Один параметр допускает до 256 вложенных контейнеров или диапазонов; более глубокий
вход вызывает `RecursionError` до отправки SQL. Это защита native-стека, отдельная
от валидации ORM-полей.

Подключение выбирает драйвер через `engine` — это то же слово, что схема в адресе базы:

| `engine` / схема адреса базы | Драйвер |
|---|---|
| `postgresql` | `rust_pg`, драйвер hare на Rust, — ставится вместе с hare |
| `postgresql+asyncpg` | `asyncpg` (нужен `hare-orm[asyncpg]`) |

Схема драйвера — `<dialect>+<driver>`; простая `postgresql://` — это `rust_pg`. Схемы всех баз — в
разделе [Диалекты и возможности](../dialects-and-features.ru.md).

```python
connections = {
    "reporting": {"engine": "postgresql+asyncpg", "credentials": {"host": "db.internal", "database": "reporting"}},
    "analytics": "postgresql://user:pass@host:5432/db",
}
```

Если модуля на Rust нет — стоит универсальный wheel на платформе, для которой готовый wheel не
собирается, или рабочая копия репозитория не собрана, — подключение `postgresql` даёт
`ConfigurationError` с командой `make build_native`, которая его собирает; для `postgresql+asyncpg` он не
нужен.

### <a id="rust-pg-threads"></a>Рабочие потоки `rust_pg`

`rust_pg` работает со своими соединениями в собственных рабочих потоках — до четырёх, но не больше, чем
ядер у машины: запросы запускает один поток с циклом событий, и нескольких рабочих потоков ему хватает —
пока один разбирает большой результат, остальные обслуживают другие соединения; лишние ждали бы работы на
ядрах, которые нужны циклу событий и базе. Их число задаёт собственная переменная окружения tokio до
импорта hare:

```bash
TOKIO_WORKER_THREADS=4 python app.py
```

Native-драйвер связывает Rust futures с циклом событий вызывающего кода через `pyo3-async-runtimes`,
сохраняя контекст задачи. Отмена Python future освобождает Rust-операцию; отдельный механизм отменяет
SQL и защищает соединение на время доставки отмены. Закрывайте клиентов до закрытия их event loop.
Принудительное закрытие loop с незавершённой native-работой не позволяет доставить результат:
bridge сообщает `RuntimeError: Event loop is closed`, а Python может сохранить traceback этой ошибки
в `sys.last_exc`. Это не означает успешную отмену работы в базе.

## <a id="connection-resilience"></a>Параметры подключения

Оба драйвера принимают эти настройки как параметры адреса (`?connect_max_retries=3&...`) или как ключи
словаря `credentials` — так же, как передаётся `max_size`. Числовой текст URL преобразуется в целые
числа или секунды. Типизированные значения передаются без изменения; ограничения драйверов и библиотек
проверяются их потребителями. Неразбираемый числовой текст даёт `ConfigurationError` при настройке:

| Параметр | По умолчанию | Что задаёт |
|---|---|---|
| `connect_max_retries` | `0` | Сколько раз повторить *первое* подключение пула; пауза перед каждой следующей попыткой вдвое длиннее предыдущей (`connect_retry_backoff_base_seconds * 2**attempt`). При `0` ошибка первой попытки передаётся без изменений. |
| `connect_retry_backoff_base_seconds` | `0.1` | Начальная пауза для повторов выше. |
| `port` | `5432` | TCP-порт сервера; текст URL преобразуется в целое число. |
| `statement_cache_size` | как у драйвера | Вместимость кэша запросов драйвера — см. [`statement_cache_size`](#statement-cache-size). |
| `transaction_pooling` | `false` | Соединение идёт через пулер в режиме транзакций (PgBouncer) (см. [Пулеры соединений](../../connections/connection-poolers.ru.md)). |
| `direct_host` / `direct_port` | нет / `port` | Адрес самого сервера в обход пулера — для LISTEN и настроек сессии. Только вместе с `transaction_pooling`. |
| `read_retry_max_retries` | `0` | Сколько раз повторить запрос, прерванный обрывом соединения **посреди запроса** (переключение сервера RDS на резервный, кратковременный сбой сети), а не только при подключении — см. [`read_retry_max_retries`](#read-retry-max-retries) |
| `read_retry_backoff_base_seconds` | `0.1` | Начальная пауза для повторов выше. |
| `min_size` / `max_size` | `1` / `16` | Минимальное и максимальное число соединений; ограничения проверяет реализация пула. |
| `max_inactive_connection_lifetime` | `300` | Сколько секунд соединение пула может простаивать до закрытия, включая соединения `min_size`; при необходимости они открываются заново. `0` оставляет их открытыми. |
| `pool_acquire_timeout` | нет (ждать сколько угодно) | Сколько секунд ждать свободного соединения до `PoolTimeoutError`, наследника `DBConnectionError`. Планирование таймаута и допустимые значения определяются реализацией пула. |
| `command_timeout` | нет (выключено) | Время одной команды в секундах, ограниченное через `asyncio.timeout()` — см. [`command_timeout`](#command-timeout). |

### <a id="statement-cache-size"></a>`statement_cache_size`

Вместимость кэша запросов драйвера; hare не вводит собственного верхнего предела. Текст из URL
преобразуется в целое число, а настройку обрабатывает драйвер. `0` выключает кэш: каждая команда готовится
для одного своего выполнения
— с `rust_pg` команда, у всех значений которой свой тип (UUID, дата, время, `datetime` с часовым поясом,
`timedelta`, `Decimal`, `float`, `bytes`, `bool`, `None`), уходит вместе с ними за один сетевой круг.

Если PostgreSQL сообщает об изменении типа результата сохранённого плана, native-драйвер удаляет
план из кэша и возвращает ошибку. Он не повторяет команду автоматически: та же серверная ошибка
может возникнуть во вложенном запросе после других побочных эффектов. Следующий явный вызов
подготавливает новый план. Редактор схемы явно инвалидирует метаданные запросов и типов после DDL,
включая частично исполненные скрипты миграций. Native-соединения обновляют кэши перед следующим
использованием; asyncpg использует публичный метод перезагрузки схемы. После собственного raw DDL
приложение может вызвать `await connection.invalidate_schema_cache()`.

Для произвольных `execute()` и `execute_described()` имена колонок и число затронутых строк
берутся из метаданных драйвера и ответа PostgreSQL о завершении команды. Комментарии, строковые
литералы и CTE не разбираются для поиска записи или `RETURNING`. Даже пустой результат сохраняет
описание колонок. Число строк равно `None`, если завершение команды не было сообщено.
Ошибка подключения сохраняет исходную ошибку драйвера и цепочку причин;
её формирование не запускает дополнительных DNS-запросов или попыток аутентификации.

### <a id="read-retry-max-retries"></a>`read_retry_max_retries`

Сколько раз повторить запрос, прерванный обрывом соединения **посреди запроса** (переключение сервера RDS
на резервный, кратковременный сбой сети), а не только при подключении. Паузы растут так же, число
повторов считается отдельно. Повторяется только команда с явным разрешением безопасного чтения
(`execute(..., retry_read=True)`), и только **вне** явной транзакции: запись вслепую не повторяется никогда
(она могла уже выполниться), запрос внутри `Transactions.atomic()` — тоже (повторять пришлось бы всю
транзакцию, а не одну команду). Повтор вызывает только `DBConnectionError`, но не `OperationalError`:
например, после отмены команды соединение остаётся рабочим, и повтор ничего бы не дал.

Запросы чтения ORM передают разрешение своему SQL-вызову; вложенные вызовы и наблюдатели его не наследуют.
Для прямого raw SQL повтор по умолчанию запрещён. Прежде чем разрешить его, автор должен установить
безопасность: строки в результате или начальное `SELECT` не исключают побочных эффектов. Время каждой
попытки сообщается отдельно, без паузы между попытками; чувствительные значения скрыты и в событиях ошибок.

### <a id="command-timeout"></a>`command_timeout`

Наибольшее время в секундах, которое одна команда может ждать ответа базы. Текст из URL преобразуется
в число; типизированные настройки передаются в `asyncio.timeout()` без отдельной проверки
положительности в hare. `None` отключает таймаут; ноль или отрицательное значение планирует отмену
на следующей итерации цикла событий. Без таймаута запрос к серверу, который перестал отвечать,
но не закрыл соединение
(сеть разделилась, процесс завис), ждёт бесконечно. Когда время выходит, вызов бросает `TimeoutError`, а
запрос отменяется. По умолчанию выключено, чтобы не прерывать долгие миграции и массовые операции. Время
отсчитывает сам hare на обоих драйверах (собственный `command_timeout` у `asyncpg` не срабатывает, если
сервер перестал отвечать, а у `rust_pg` такой настройки нет) — для каждого вызова, выполняющего запрос, и
для массовой загрузки `COPY`, но не для `begin`/`commit`/`rollback`/`savepoint` и не для `stream()`.
У команд управления транзакцией отдельные ограничения жизненного цикла, включая ограниченное ожидание
завершения после отмены; `command_timeout` ими не управляет. Перед повторным использованием соединения
отменённой команды hare ждёт безопасного завершения. Если подтвердить завершение невозможно,
соединение отбрасывается.

В `rust_pg` команда транзакции, отменённая во время выполнения, отправляет PostgreSQL запрос отмены по
отдельному соединению; следующая команда транзакции ждёт, пока этот запрос будет доставлен, поэтому
запоздавший запрос отмены никогда не отменит вместо неё следующую команду.

Отменённый запрос останавливается и на сервере, в том числе за пулером вроде PgBouncer. Пулер передаёт
запрос отмены дальше, только пока клиентское соединение, которое он называет, ещё открыто. Поэтому
соединение, вынутое из пула из-за превышения времени, закрывается только после того, как его запрос
отмены доставлен, — или, если ответа на него нет ещё за один `command_timeout` (сеть перестала
отвечать), закрывается тогда, и вызов всё равно заканчивается примерно через два `command_timeout`.
См. [Проверка связи и неотвечающий сервер](../../connections/connections.ru.md#health-checks).

## <a id="rotating-credentials"></a>Меняющийся пароль

Пароль, который меняется, — токен облачного IAM, динамический пароль хранилища секретов — берётся не из
настройки `password`, а из функции. Её задаёт `password_provider`: обычная или асинхронная функция,
возвращающая пароль, или её путь через точку в адресе базы или файле настроек:

```python
async def get_database_password() -> str:
    return await secrets.get("library-db")


await Hare.init(
    config={
        **HARE_CONFIG,
        "connections": {
            "default": {
                "engine": "postgresql",
                "credentials": {
                    "host": "db.internal",
                    "user": "library",
                    "database": "library",
                    "password_provider": get_database_password,
                    "password_refresh_seconds": 300,
                },
            }
        },
    }
)
# или: postgresql://library@db.internal/library?password_provider=library.secrets.get_database_password
```

| Параметр | По умолчанию | Что задаёт |
|---|---|---|
| `password_provider` | нет | Функция, дающая пароль. Вместе с `password` — `ConfigurationError`. Она должна вернуть непустую строку, иначе `ConfigurationError`. |
| `password_refresh_seconds` | `600` | Сколько секунд пароль используется, прежде чем функцию спросят снова (`value > 0`, иначе `ConfigurationError`). Без `password_provider` — `ConfigurationError`. |

Пул открывает новые соединения с паролем, который функция дала последним; уже открытые соединения
остаются. `asyncpg` спрашивает пароль, открывая соединение, — когда тот старше
`password_refresh_seconds`; `rust_pg` открывает соединения сам, поэтому hare спрашивает в фоне каждые
`password_refresh_seconds` и передаёт пулу новый пароль. Если функция не смогла дать новый пароль, на
обоих драйверах остаётся последний — с предупреждением в журнале; если пароля ещё нет или сервер в нём
отказал, её ошибка пробрасывается. Если сервер отказал в пароле — его сменили до обновления, — функцию
спрашивают сразу, а команда выполняется ещё раз: отказ во входе случился до того, как команда дошла до
сервера, поэтому это верно и для записи. Хост с несколькими адресами (`localhost` — `127.0.0.1` и `::1`)
сообщает отказ того адреса, который ответил, а не отказ в соединении на другом. Внутри транзакции её
соединение уже открыто, и ничего не повторяется. Диалект без смены пароля (SQLite, ClickHouse) отвергает
`password_provider` как неизвестную настройку.

## <a id="url-parameters-and-tls"></a>Параметры адреса и TLS

Шифрование соединения (TLS) задаётся одним из параметров: `?sslmode=` (значения libpq `disable`, `allow`,
`prefer`, `require`, `verify-ca`, `verify-full`), `?ssl=` (те же значения или `true`/`false`: `true` —
это `require`, `false` — `disable`) или `?ssl_mode=` — в одном адресе только один из них. Значение
передаётся в настройку конкретного драйвера: `ssl_mode` у `rust_pg` (режима `allow` у него нет —
`UnSupportedError`), `ssl` у `asyncpg`. Любое другое значение даёт `ConfigurationError`.

`?ssl_root_cert=` задаёт файл сертификатов, по которым проверяется сертификат сервера, на обоих драйверах
(у `asyncpg` — вместе с режимом TLS: `SSLContext` в `ssl=` хранит свои сертификаты сам, и вместе они дают
`ConfigurationError`). Файл, который нельзя прочитать или в котором нет сертификата, даёт
`ConfigurationError` до открытия соединения.
`rust_pg` также сообщает через `ConfigurationError` об ошибках настройки TLS, в том числе если включена
проверка сертификата, а в системе нет пригодных корневых сертификатов. Такие ошибки не повторяются как
сетевые.

С `rust_pg` (`postgresql://`) каждый параметр адреса должен быть понятен драйверу: `min_size`/`max_size`,
`max_inactive_connection_lifetime`, `statement_cache_size`, `ssl_root_cert`, `application_name`,
`schema`, `tenant_schema_template`, `tenant_row_level_security`, `host`, `port`, параметры TLS,
`password_provider`/`password_refresh_seconds` и параметры из таблицы выше. Любой другой (например,
`max_queries` из `asyncpg`) даёт `ConfigurationError`, а не отбрасывается молча. С `asyncpg`
(`postgresql+asyncpg://`) параметр должен быть `ssl_root_cert` или одним из тех, что принимают
`asyncpg.connect()`/`create_pool()`. Известные числовые настройки URL разбираются; типизированные
значения передаются asyncpg без изменения. Неразбираемый текст, например `?min_size=abc`, даёт
`ConfigurationError` при настройке; ограничения драйвера проверяются при использовании значения.
Значение, заданное дважды — в самом адресе и параметром (`...@host:5432/db?port=6432`), — тоже даёт
`ConfigurationError`, а не тихо теряет одно из двух.

Если подключиться не удалось, в сообщении остаётся причина, которую назвал драйвер. Неверный пароль,
неизвестная роль или несуществующая база дают `ConfigurationError` на обоих драйверах: повтор тут не
поможет, и `connect_max_retries` их не повторяет. Недоступный сервер и сервер, у которого кончились
подключения, память или диск (SQLSTATE класса 53, «too many clients»), дают `DBConnectionError`, и
`connect_max_retries` их повторяет. Пул, который не смог открыться, закрывает уже открытые им соединения.
Если `user`, `password`, `host` или `database` не заданы, оба драйвера берут их из переменных окружения
libpq `PGUSER`, `PGPASSWORD`, `PGHOST`, `PGDATABASE` (а затем — имя пользователя ОС и `localhost`).

Зарезервированные разделители внутри имени пользователя и пароля кодируются через `%`: `@`, `:`,
`/`, `?`, `#`, `[` и `]`. Например, `p@s?a=b` записывается как `p%40s%3Fa%3Db`; в Python целый
компонент кодирует `urllib.parse.quote(password, safe="")`. Раскодирование выполняется один раз:
`%252F` означает буквальный текст `%2F`. В отдельных полях `credentials` имя пользователя и пароль
передаются без URL-кодирования. Явно пустой пароль или параметр остаётся пустым; пропущенное значение
может браться из окружения драйвера. URL не содержит фрагмента после `#`; некорректный адрес полностью
скрывается при выводе конфигурации. Значение параметра может содержать `@`, имя базы раскодируется (`/my%20db`
→
`my db`). Каталог unix-сокета можно указать как `?host=/var/run/postgresql` с пустым именем хоста или
закодировать через `%` прямо на месте хоста (`postgresql://user@%2Fvar%2Frun%2Fpostgresql/db`).
Идентификатор зоны адреса IPv6 тоже кодируется через `%` (`[fe80::1%25eth0]` → `fe80::1%eth0`).
DNS-имена хостов приводятся к нижнему регистру; пути сокетов и идентификаторы зон IPv6 сохраняют регистр.

## <a id="search-path"></a>Схема и путь поиска

`schema` задаёт одно точное имя общей схемы: `schema="Team,Archive"` — имя с запятой.
Для упорядоченного пути используйте `search_path=SearchPath("Team,Archive", "public")`;
`SearchPath` импортируется из `hare.dialects.postgresql`. Допускается и последовательность точных имён.
В URL параметр `search_path` использует синтаксис настройки PostgreSQL с URL-кодированием значения:
в именах без кавычек ASCII-буквы приводятся к нижнему регистру, остальные сохраняют регистр, как в базе
UTF-8. Знаки пунктуации разрешены; имена разделяются запятыми и пробельными символами сканера PostgreSQL.
Кавычки сохраняют регистр, запятые и удвоенные кавычки внутри имени. Пустые имена запрещены, длину
идентификаторов обрабатывает сервер. `$user` и `pg_temp` сохраняют смысл PostgreSQL.
`SearchPath()` задаёт пустой путь.

Без `search_path` путь состоит из единственного имени `schema`; без обоих параметров действует
настройка сервера. `server_settings["search_path"]` принимает тот же синтаксис настройки; одновременно
задавать отдельный параметр `search_path` нельзя. Подключение арендатора добавляет его схему в начало
пути, сохраняя `schema` для обращения к общим таблицам. Оба драйвера, проверки transaction pooler,
теневые схемы и `dbshell` используют одно кодирование пути.

## <a id="session-time-zone"></a>Часовой пояс сеанса

Оба драйвера работают в каждом сеансе с `TimeZone=UTC`, какой бы часовой пояс ни был задан по умолчанию у
сервера, базы или роли: от пояса сеанса зависят приведения даты и времени, `CURRENT_DATE` и значения по
умолчанию `Now()`, а hare хранит моменты времени в UTC. Если в `server_settings` указан другой `TimeZone`
(`UTC`, `Etc/UTC`, `GMT` и подобные допускаются), будет `ConfigurationError`. Пояс, в котором значения
показываются приложению, задаёт `Hare.init(timezone=...)`.

## <a id="driver-differences"></a>Готовый SQL на двух драйверах

Оба драйвера возвращают из готового SQL одинаковые значения Python: `numeric` — точный `Decimal` (с любым
числом цифр), `json`/`jsonb` — их текст, `interval` — `timedelta` (месяц считается за 30 дней, год — за
365), `inet` — `ipaddress.ip_address`/`ip_interface`, `cidr` — `ipaddress.ip_network`, `oid`/`xid` —
`int`, типы `reg*` — имена, `tsvector`, `citext`, `ltree` и `hstore` (и в массиве, в том числе пустое
значение) — текст, который печатает PostgreSQL, `ROW(...)` — кортеж. Эти четыре типа asyncpg читает через
бинарные кодеки hare. Они устанавливаются при открытии и обновляются на явных границах изменения
схемы перед следующей командой ORM, в том числе на подключении, удерживаемом транзакцией. Commit,
rollback и откат savepoint повторно инвалидируют снимки каталога при изменении видимости.
Удаление зарегистрированного типа приводит к замене затронутых подключений пула после возврата;
обычный DDL и добавление расширений не требуют переподключения. Собственное текстовое чтение asyncpg
роняет процесс на пустом значении в массиве этих типов расширений. После изменения схемы в обход
редактора hare вызовите `await connection.invalidate_schema_cache()` до использования этих типов.
Время `24:00:00`, которое не
помещается в `datetime.time`, вызывает ошибку, а не читается как полночь. Значение типа, который
`rust_pg` не умеет разбирать (`point`, `pg_lsn` и другие), он возвращает текстом — так, как его печатает
PostgreSQL; в параметрах он принимает `timedelta` и объекты `ipaddress`. Для остальных типов результат
готового SQL зависит от драйвера: диапазон — это `Range` из `asyncpg` или
`hare.dialects.postgresql.fields.Range`, `money` — текст у `asyncpg` (`'$1.00'`) или `Decimal` у
`rust_pg`, бесконечный `timestamptz` — `datetime.max`/`min` без пояса или в UTC. Поля моделей
(`RangeField`, `DatetimeField` и другие) читают всё это одинаково на обоих драйверах. Параметр, тип
которого не подходит колонке, даёт `OperationalError`, а не преобразуется. Ошибка базы сохраняет в
сообщении `DETAIL` и `HINT` сервера, а исключение драйвера, из которого она получена, — `sqlstate`,
`constraint_name`, `table_name` и другие поля.

Значения готовой команды передаются драйверу как есть, поэтому видно, что с ними делают asyncpg и
rust_pg. hare согласует их там, где может:

- **Неверное число параметров** даёт `OperationalError` на обоих: asyncpg отказывает до отправки, для
  rust_pg отказывает сервер; подключение остаётся рабочим.
- **Значение, которого нет у типа Python**, — `interval 'infinity'` или интервал в миллионы лет,
  `'24:00:00'::time`, дата до 1 года или после 9999-го — даёт `OperationalError` в запросе hare.
  `interval` читается на обоих так же, как в asyncpg: год — 365 дней, месяц — 30.
- rust_pg разбирает бинарные значения до возврата результата; ошибки преобразования сообщает
  выполняющий вызов. Повторное чтение строки использует разобранные значения и создаёт Python-объекты
  по мере обращения.
- asyncpg записывает `Decimal` с более чем 131072 цифрами до запятой как `0` — это предел его кодека;
  rust_pg такое значение отклоняет. Фильтр по `DecimalField` сравнивает такое число как первое за
  пределом колонки, поэтому до драйвера оно не доходит.
- Вход без пароля даёт `ConfigurationError`, как и с неверным паролем, на обоих — rust_pg отказывает до
  запроса пароля сервером.

Native-драйвер выбирает декодеры по физическим типам колонок и разбирает каждое бинарное значение
один раз до публикации результата. Для неподдерживаемого значения, отличного от NULL, он запрашивает
у сервера текстовое представление и подставляет полученный текст без повторного разбора строки.
SQL NULL не требует текстового преобразования. Повреждённое значение поддерживаемого типа вызывает
ошибку преобразования вместо перехода к серверному тексту. Повторное чтение результата использует
разобранные значения; Python-объекты создаются по мере обращения.

Native-драйвер проверяет длины, счётчики и лишние байты в каждом вложенном бинарном значении.
Массивы, записи и границы диапазонов используют общий контекст декодирования. Вложенность
получаемого дерева контейнеров ограничена 256 уровнями для контроля native-стека; измерения
массива входят в этот предел. TSQUERY хранится плоско, поэтому количество его операторов
не расходует лимит вложенности. Для Python-параметров отдельно отслеживаются предки:
циклические списки, словари и диапазоны отклоняются, общий ациклический дочерний объект
допустим. Лимит вложенности Python-входа в native-драйвере также равен 256 уровням.
