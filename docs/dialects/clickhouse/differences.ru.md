# Что работает иначе в ClickHouse

В ClickHouse нет частей SQL, на которые hare иначе опирался бы: ограничений уникальности и внешних
ключей, `UPDATE` на месте, `RETURNING`, `ON CONFLICT`, блокировок строк. Транзакции и генерируемые
ключи есть только на сервере с ClickHouse Keeper. Каждая строка ниже говорит, что hare делает вместо
этого.

| Чего нет в ClickHouse | Что делает hare |
|---|---|
| Транзакций по умолчанию | `atomic()` даёт `UnSupportedError`, если подключение не просит их через `transactions=true`, — см. [Транзакции и блокировки](transactions-and-locks.ru.md). Без них собственные многокомандные записи hare идут одна за другой, и сбой оставляет записанными команды до него. |
| Точек сохранения | Вложенный `atomic()` присоединяется к внешней транзакции; ошибка, покинувшая его, откатывает всю транзакцию. |
| Генерируемых ключей | В ClickHouse 25.1 и новее с Keeper ключи берутся из серии до записи строк (`generateSerialID`) — см. [Модели](models.ru.md#keys). Иначе модель, ключ которой генерирует база, отклоняется при привязке. |
| Ограничений уникальности и внешних ключей | hare сам проверяет объявленные в модели уникальность и связи до записи — см. [Модели](models.ru.md#uniqueness-and-relations). |
| `UPDATE` строк на месте | `save()`, `QuerySet.update()` и `bulk_update()` выполняют мутацию `ALTER TABLE ... UPDATE`, завершённую до возврата из вызова. Таблица с `ClickhouseTableOptions(lightweight_updates=True)` получает вместо неё лёгкий `UPDATE` (ClickHouse 25.7) — см. [Модели](models.ru.md#lightweight-updates). |
| Числа строк от UPDATE или DELETE | Строки, которые затронет мутация или DELETE, считаются прямо перед ней — если другой клиент изменит их в промежутке, изменится и число. |
| `RETURNING` | Строки читаются по ключам: после изменения, до удаления; значения, которые сервер дал вставленным строкам (`db_default`, колонки `MATERIALIZED`), — после вставки. Строка, которую другой клиент изменил между чтением и записью, читается такой, какой была при чтении. `returning(old=...)` даёт `UnSupportedError` — значения до изменения не сохраняются. Значение, которое выражение пишет в целое или десятичное поле, вычисляется `SELECT` до записи, а значение вне диапазона поля даёт `ValidationError`, и ни одна строка не записывается. |
| `ON CONFLICT` | `bulk_create(ignore_conflicts=True)` и `bulk_create(update_fields=[...], on_conflict=[...])` сначала читают ключи пачки по полям конфликта: уже хранимые строки пропускаются или изменяются через `bulk_update()`, остальные вставляются. Конфликтующую строку, которую другой клиент вставит между чтением и вставкой, hare не увидит. |
| Блокировок строк | `select_for_update()` блокирует строки в ClickHouse Keeper при `transactions=true` и `keeper_hosts` — см. [Транзакции и блокировки](transactions-and-locks.ru.md#row-locks). Без них он даёт `UnSupportedError`, а ретранслятор transactional outbox не запускается. |
| `NULL` от агрегата по пустому набору | `Sum`, `Max`, `Min`, `Avg`, `StdDev` и `Variance` пишутся в форме `-OrNull` (`sumOrNull(...)`), поэтому на пустом наборе дают `None`, как в любой другой базе, а не значение типа колонки по умолчанию; `Count` даёт `0`. В запросе с `GROUP BY` в группе есть хотя бы одна строка, поэтому агрегат без `_filter` остаётся в простой и более быстрой форме (`sum(...)`). Выборочное отклонение по одному значению — `None`, как в SQL, а не NaN ClickHouse. |
| Связанных подзапросов до 25.4 | `EXISTS`, связанный равенством колонок, — фильтр или исключение через связь «ко многим», `<m2m>__isnull`, `Exists(...)` с равенствами `OuterReference`, — выполняется как `(колонки) IN (SELECT ...)`, а любой другой связанный подзапрос даёт `UnSupportedError`. См. [Связанные подзапросы](#correlated-subqueries). |
| `LIKE ... ESCAPE` | Шаблон экранируется обратной косой чертой — собственным символом экранирования ClickHouse. |
| Курсора транзакции | `stream()` читает строки и вне транзакции: сервер отдаёт их по мере вычисления. Ранний выход из `async for` закрывает поток и возвращает соединение. |

## <a id="long-in-lists"></a>Длинные списки `__in`

Сервер медленно разбирает список литералов: 100 000 значений занимают почти секунду. Список `__in`
или `__not_in` из 500 и более значений одного простого типа — UUID, целых, текстов, дат или строк из
них для ключа из нескольких колонок — передаётся одним параметром: чтение отправляет значения рядом с
командой внешней таблицей (`x IN hare_set_1`), которую сервер читает как данные за несколько
миллисекунд, а любая другая команда (мутация, `DELETE`) пишет их списком литералов. SQL запроса один и
тот же при любой длине списка, поэтому у него один план.

Индексы — это индексы пропуска данных: `Index(fields=...)` создаёт индекс `minmax` с гранулярностью
1, а остальные типы есть в `hare.dialects.clickhouse.indexes` — см.
[Модели](models.ru.md#data-skipping-indexes). `hare inspectdb` и `hare drift` читают таблицы, колонки,
первичные ключи, комментарии, индексы пропуска, опции таблиц, представления и словари из таблиц
`system`.

## <a id="correlated-subqueries"></a>Связанные подзапросы

ClickHouse выполняет связанные подзапросы с 25.4 (до 25.7 — под настройкой
`allow_experimental_correlated_subqueries`, которую hare ставит). Часть из них он всё ещё считает
неверно или отклоняет, поэтому на любой версии:

- **`EXISTS`**, связанный равенством колонок, пишется как `(колонки) IN (SELECT ...)` — собственный
  связанный `EXISTS` сервера теряет строки (25.8).
- **Подзапрос, который сам сортирует или срезает свои строки** (`Subquery(... .order_by("-created")[:1])`
  с `OuterReference`), даёт `UnSupportedError` — сервер его отклоняет.
- **Подзапрос в `ORDER BY` или выбранный рядом с `WHERE`** вычисляется в производной таблице: строки
  выбираются без `WHERE`, условия и ключи сортировки становятся её скрытыми колонками, а внешний
  запрос фильтрует, сортирует и срезает их. SQL длиннее, результат — тот, что просит запрос.
- `UPDATE` или `DELETE`, в условии которого есть связанный подзапрос, даёт `UnSupportedError` —
  мутация их не выполняет.

## <a id="json"></a>JSON

В ClickHouse 25.3 и новее `JSONField` — колонка `JSON`, пути которой хранятся типизированными
подколонками; на более старом сервере это колонка `String` с текстом JSON, которую читают функции
`JSON*`. Тип `JSON` хранит меньше, чем текст JSON:

- Хранится только объект: список, строка или число на верхнем уровне дают `ValidationError` до
  отправки.
- `null` внутри объекта и пустой объект не хранятся: `{"a": null, "b": 1}` читается как `{"b": 1}`.
  Поэтому `field__path=None` и `field__path__isnull=True` находят путь без значения — `null` там
  неотличим.
- Порядок ключей не сохраняется.

Пути ключей, `__has_key`, `__has_keys`, `__has_any_keys`, `__contains` и `__contained_by` работают на
обоих типах. `__contains` и `__contained_by` сравнивают, как `jsonb` в PostgreSQL, — объект по ключам,
массив по элементам в любом порядке — и строятся из переданного значения: его ключи и скаляры
передаются параметрами, а SQL следует его форме. Миграция переводит колонку `String` в `JSON` через
`MODIFY COLUMN`, когда у сервера есть этот тип.

## <a id="bulk-loads"></a>Массовая загрузка

`bulk_create()` отправляет строки одной двоичной вставкой — в формате ClickHouse `Native`, колонка за
колонкой — вместо текста `INSERT ... VALUES`: литералы для значений не пишутся, а сервер не разбирает
SQL. Так строки и должны попадать в ClickHouse, и поэтому много строк стоит писать через
`bulk_create()`, а не через `create()` в цикле.

- `batch_size` делит объекты на столько вставок; без него они идут одной.
- Значения — те же, что пишет `create()`: момент без часового пояса — это его время по UTC, значение
  JSON — его текст или объект.
- Перед вставкой ключи пачки проверяются одним `SELECT` (ключи уходят внешней таблицей — см.
  [Длинные списки `__in`](#long-in-lists)) на каждую объявленную
  уникальность и на каждую связь — см. [Модели](models.ru.md#uniqueness-and-relations); строки,
  повторяющие ключ внутри пачки, находятся без запроса.
- [Наблюдатели](../../observability/observers.ru.md), спаны и счётчик запросов видят вставку как
  `INSERT INTO <таблица> (<колонки>) FORMAT Native` — строки не входят ни в какой текст SQL.
- `use_copy=True` просит ту же загрузку и здесь ничего не меняет. `returning=True` дочитывает строки
  по ключам после вставки; параметры конфликтов читают хранимые ключи до неё.
- С `async_insert=true` сервер собирает строки многих вставок, прежде чем записать их; с
  `wait_for_async_insert=false` вызов возвращается до записи и не сообщает об ошибке.
