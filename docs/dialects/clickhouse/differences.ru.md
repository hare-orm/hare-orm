# ClickHouse: что работает иначе

В ClickHouse нет частей SQL, на которые hare иначе опирался бы: ограничений уникальности и внешних
ключей, `UPDATE` на месте, `RETURNING`, `ON CONFLICT`, блокировок строк, числа строк, изменённых записью.
Транзакции и генерируемые ключи есть только на сервере с ClickHouse Keeper. Каждая строка ниже говорит, что
делает hare: где у ClickHouse есть другая запись того же SQL, hare пишет её; где в языке её нет, вызов
отклоняется до отправки SQL.

| Чего нет в ClickHouse | Что делает hare |
|---|---|
| Транзакций по умолчанию | `atomic()` даёт `UnSupportedError`, если подключение не просит их через `transactions=true`, — см. [Транзакции и блокировки](transactions-and-locks.ru.md). Без них собственные многокомандные записи hare идут одна за другой, и сбой оставляет записанными команды до него. |
| Точек сохранения | Вложенный `atomic()` присоединяется к внешней транзакции; ошибка, покинувшая его, откатывает всю транзакцию. |
| Генерируемых ключей | С ClickHouse Keeper ключи берутся из серии до записи строк (`generateSerialID`) — см. [Модели](models.ru.md#keys). Без него модель, ключ которой генерирует база, отклоняется при привязке. |
| Ограничений уникальности и внешних ключей | Уникальность или связь с `db_constraint=True` отклоняется — у модели при привязке (`ConfigurationError`), у миграции, объявляющей уникальность, до её первой команды (`UnSupportedError`); см. [Модели](models.ru.md#uniqueness-and-relations). |
| `CHECK`, пропускающего строку, условие которой даёт `NULL` | ClickHouse такую строку отвергает (`IntegrityError`): `CheckConstraint(check=Q(price__gte=0))` отвергает `price=None` — проверка, пропускающая `NULL`, называет его: `Q(price__isnull=True) \| Q(price__gte=0)`. Проверка, которую добавляет миграция, проверяет только строки, записанные позже, — см. [Операции](../../migrations/operations.ru.md). |
| `UPDATE` строк на месте | `save()`, `QuerySet.update()` и `bulk_update()` выполняют мутацию `ALTER TABLE ... UPDATE`, завершённую до возврата из вызова — см. [`UPDATE` строк на месте](#an-update-of-rows) |
| Числа строк, изменённых UPDATE или DELETE | `update()`, `delete()` и `bulk_update()` возвращают `None` (`Features.reports_written_row_count`) — см. [Число записанных строк](#written-row-count) |
| `RETURNING` | `returning()` у `update()` или `delete()` и `bulk_create(returning=True)` дают `UnSupportedError`; значения, которые сервер дал записанной строке, остаются непрочитанными в экземпляре — см. [`RETURNING`](#returning) |
| `ON CONFLICT` | `bulk_create()` с `ignore_conflicts`, `update_fields`, `on_conflict` или `on_conflict_constraint` даёт `UnSupportedError` (`Features.supports_insert_conflicts`); transactional outbox, который так пишет свои события, отклоняется при привязке его модели — см. [Outbox](../../integrations/outbox.ru.md). |
| Батчей у UPDATE | `BackfillColumn` заполняет все строки одной мутацией, `batch_size` не используется: мутация не блокирует строк, которые пощадил бы батч, и каждая переписывает изменяемые части. |
| Блокировок строк | `select_for_update()` и `atomic(lock_timeout=...)` дают `UnSupportedError` — см. [Транзакции и блокировки](transactions-and-locks.ru.md). |
| `NULL` от агрегата по пустому набору | Агрегат, результат которого на пустом наборе был бы значением, которого нет ни в одной строке, пишется в форме `-OrNull` (`maxOrNull(...)`) и даёт `None`; `Sum` даёт собственный `0` ClickHouse — список см. в [`NULL` от агрегата по пустому набору](#null-from-an-aggregate) |
| `LIKE ... ESCAPE` | Шаблон экранируется обратной косой чертой — собственным символом экранирования ClickHouse. Пустой текст содержится в любом тексте, как в PostgreSQL (`contains=""`, `contains=F("name")` при пустом имени): ClickHouse не сопоставляет пустую строку шаблону `'%%'`, поэтому hare пишет такой шаблон как `'%'`. |
| Простого `UPDATE` и отказа в `NULL` в готовом SQL | Ваш SQL (`RunSQL`, `raw()`, `execute()`) выполняется так, как его принимает ClickHouse: `UPDATE` нужна настройка `enable_block_number_column` (`ALTER TABLE ... UPDATE` — нет), а `NULL` в колонке не `Nullable` пишется пустым значением типа (`0`, `''`). Записи hare такой `None` отвергают. |
| Обратной косой черты как обычного символа имени в кавычках | Имя с обратной косой чертой — таблицы, колонки, псевдонима — пишется с удвоенной чертой: одиночную ClickHouse читает как экранирование. |
| Рекурсивного запроса, добавляющего строки через `UNION DISTINCT` | `with_recursive()` нужен `max_depth`, который заканчивает цикл в строках, — см. [Рекурсивные запросы и CTE](../../querying/queryset-methods.ru.md#recursive). Без него обход даёт `UnSupportedError`. |
| `NULL` первым при сортировке по убыванию | ClickHouse ставит `NULL` последним в обоих направлениях — см. [`NULL` первым при сортировке по убыванию](#null-first-in-a) |
| Курсора транзакции | `stream()` читает строки и вне транзакции: сервер отдаёт их по мере вычисления. Ранний выход из `async for` закрывает поток и возвращает соединение. |
| Смещения зоны от UTC с секундами | ClickHouse хранит смещение зоны в целых минутах: местное среднее время до стандартного времени зоны (Москва до 1919 года, `+02:30:17`) читается без секунд — `Extract("second")`, `Trunc()` и `__time` такого момента в этой зоне (или при `use_timezone=False` в ней) отличаются от PostgreSQL на эти секунды. |

## <a id="an-update-of-rows"></a>`UPDATE` строк на месте

`save()`, `QuerySet.update()` и `bulk_update()` выполняют мутацию `ALTER TABLE ... UPDATE`, завершённую
до возврата из вызова. Таблица с `ClickhouseTableOptions(lightweight_updates=True)` получает вместо неё
лёгкий `UPDATE` — см. [Модели](models.ru.md#lightweight-updates). `delete()` выполняет
лёгкий `DELETE`, а если его условие читает `union()`/`intersection()`/`difference()`, — мутацию
`ALTER TABLE ... DELETE`: лёгкий `DELETE` сервера на таком условии падает. Упавшая мутация
останавливается (`KILL MUTATION`) до того, как вызов выдаст ошибку: иначе сервер повторял бы её, из-за
неё падала бы каждая следующая мутация таблицы, и она ещё могла бы примениться после ошибки вызова.
Мутация не выполняет связанных подзапросов: `update()`, который записывает в поле `Subquery` с
`OuterReference`, фильтруется или удаляет по такому подзапросу, даёт `UnSupportedError`. Мутация
`bulk_update()` пишет не больше 1000 строк (`Features.max_bulk_update_rows`): значения каждой строки она
находит перебором списка строк, поэтому более длинный список дороже на строку и выходит за предел AST
сервера. Ключи её строк читает подзапрос самого списка, одинаковый на каждой реплике: она выполняется с
`allow_nondeterministic_mutations = 1`, без чего таблица `ReplicatedMergeTree` не принимает мутацию с
подзапросом, — `update()`, отфильтрованный подзапросом другой таблицы, сервер там отвергает, ведь реплики
могут прочитать разные строки.

## <a id="written-row-count"></a>Число записанных строк

ClickHouse не сообщает, сколько строк изменила мутация или лёгкий `UPDATE`/`DELETE`, поэтому `update()`,
`delete()` и `bulk_update()` возвращают `None`; чтобы узнать, что изменилось, прочитайте строки. Удаление,
которое hare выполняет сам, — каскад в Python, модель с переопределённым `delete()` — считает прочитанные
для него строки. Без числа строк:

- `save()` или `delete()` строки, которую удалил другой клиент, не обнаруживается — `DoesNotExist` не
  возникает;
- модель с `Meta.optimistic_lock_field` отклоняется при привязке: устаревшая версия осталась бы
  незамеченной;
- `bulk_update()` считает записанным каждый объект и применяет ко всем его версию, снимок изменённых полей
  и значения `auto_now`.

## <a id="returning"></a>`RETURNING`

`update().returning()`, `delete().returning()` и `bulk_create(returning=True)` дают `UnSupportedError` до
отправки SQL. Значение, которое сервер даёт строке, записанной `save()` или `create()`, — `db_default`,
колонка `MATERIALIZED` — остаётся в экземпляре непрочитанным: поле держит `DatabaseDefault`,
вычисляемое поле не загружено, а `refresh_from_db()` читает их. Ключ, который генерирует сервер, берётся до
вставки (см. [Модели](models.ru.md#keys)); модель, ключ которой оставлен `db_default`, отклоняется при
записи строки.

## <a id="null-from-an-aggregate"></a>`NULL` от агрегата по пустому набору

`Max`, `Min`, `Avg`, `StdDev`, `Variance` и собственные агрегаты ClickHouse `ArgMax`, `ArgMin`, `AnyValue`,
`AnyLast`, `Quantile` и `Median` (и с `exact=True`) пишутся в форме `-OrNull`
(`maxOrNull(...)`), поэтому на пустом наборе дают `None`, а не значение типа колонки по умолчанию;
`Count` даёт `0`, а `Sum` — собственный `0` ClickHouse (`0.00` для десятичного). В запросе с `GROUP BY`
в группе есть хотя бы одна строка, поэтому агрегат без `_filter` остаётся в простой и более быстрой форме
(`max(...)`). Выборочное отклонение по одному значению — `None`, как в SQL, а не NaN ClickHouse.

## <a id="results"></a>Результаты самого ClickHouse

hare не заставляет ClickHouse давать результат PostgreSQL. Она отказывает там, где ClickHouse молча
превратил бы значение в другое или оставил его нечитаемым, пишет формы, которые хранит сама
(перечисление по метке, адрес как `IPv6`, путь JSON), и выполняет свои функции собственными средствами
ClickHouse; всё остальное — результат самого ClickHouse, и он отличается от результата PostgreSQL:

- **Деление и остаток от деления на ноль** дают `inf` или `nan` для `float` и собственную ошибку
  ClickHouse для целых; **математическая функция вне области определения** (`Sqrt(-1)`, `Ln(0)`) даёт
  `nan` или `inf`. hare не проверяет ничего из этого. `MOD` и отрицательный ноль — тоже собственные.
- **Частное десятичных.** Деление, `Avg()`, `StdDev()` и `Variance()` десятичных вычисляются точно и
  отсекаются, а не округляются, до 20 знаков после запятой; у `numeric` PostgreSQL свои правила масштаба.
  `Round()` — это `round()` ClickHouse.
- **Количества, длины, номера строк и ранги** (`Count()`, `Length()`, `StrIndex()` и оконные функции
  `RowNumber()`, `Rank()`, `DenseRank()`, `NTile()`) — знаковые `Int64`: собственный `UInt64` ClickHouse
  не находит общего типа со знаковым целым в `Coalesce()`, `Case()` и `Greatest()`.
- **Целочисленная арифметика**, которую читает запрос, за пределами диапазона своего типа отклоняется
  (`integer out of range`); значение, которое записывает `update(n=F("n") + 1)`, ClickHouse приводит к
  типу колонки, «заворачивая» его за пределами диапазона (`2147483647 + 1` хранится как `-2147483648` в
  `Int32`). `/` двух
  целых даёт точное частное, в том числе дробь (`Features.divides_integers_exactly`), — поле вывода
  выражения `FloatField`. Десятичное, которое выражение вычисляет с большим числом знаков, чем у поля,
  ClickHouse отсекает, а не округляет: `update(price=F("price") + Decimal("0.005"))` оставляет `12.34`,
  где PostgreSQL и SQLite пишут `12.35`.
- **`Cast()`** к целому отбрасывает дробную часть, тогда как PostgreSQL округляет; целое за пределами
  диапазона целевого поля даёт исключение. Десятичный тип округляет половиной от нуля до своих знаков, а
  `float` становится десятичным по кратчайшей записи цифр. Приведение к логическому — `toBool()`
  ClickHouse, который принимает и `yes`, `no`, `on`, `off`. Приведение к тексту — `toString()`: `1e308`,
  `-inf`, десятичное без хвостовых нулей, момент в виде `2024-01-02 03:04:05.678900`. Число, обрамлённое
  пробелами (`' 42 '`), не читается, а текст, не являющийся значением типа, даёт исключение.
  `max_length` у `CharField` ничего не обрезает.
- **`Concat()`** склеивает текст, который ClickHouse даёт значению колонки (`toString()`); наивное
  дата-время (`use_timezone=False`) пишется по местному поясу машины. Значение Python, переданное
  литералом, — это его текст в Python: логическое `true` или `false`, `float` через `repr()`
  (`1000000000000000.0`), дата или дата-время — текст ISO. Текстовый оператор фильтра (`contains`,
  `startswith`, `iexact`, ...) для колонки логического, `float` или десятичного типа сопоставляет текст,
  который ClickHouse даёт значению.
- **Смена регистра.** `Upper()`, `Lower()` и операторы фильтра `i...` идут через `upperUTF8()` и
  `lowerUTF8()` — собственные функции сервера.
- **`Substr`, `Chr` и `Ord`** — это `substringUTF8()` (начало 0 отклоняется, отрицательное начало
  считается с конца, отрицательная длина оставляет символы с конца), `char()` (кодовая точка, которой
  не соответствует ни один символ, отклоняется, 0 даёт `\x00`) и кодовая точка первого символа для
  `Ord`. У текстовых функций нет 32-битного предела длины, позиции и количества, они принимают выражение
  любого типа; литерал не того типа отклоняется.
- **`FIRST_VALUE` и `LAST_VALUE`** — собственные функции ClickHouse, как и порядок UUID (сначала младшие
  64 бита: ключ `uuid7` не сортируется по времени, сортируйте по колонке с датой) и адресов `IPv6`.
  Перечисление упорядочивается по метке: так его хранит hare. Время суток упорядочивается и
  сравнивается как хранимый текст: `10:00:00+03:00` идёт после `08:00:00+00:00`, хотя это более ранний
  момент.
- **`NaN` в `FloatField`** хранится. **Нулевой байт** в тексте или значении JSON хранится так, как его
  хранит ClickHouse.
- **Ошибки.** Десятичное сверх своих цифр даёт `the value has more digits than the decimal holds`; перевод
  колонки в `NOT NULL`, пока в ней есть `NULL`, даёт `column X of table Y holds NULL`.

## <a id="null-first-in-a"></a>`NULL` первым при сортировке по убыванию

ClickHouse ставит `NULL` последним в обоих направлениях; hare пишет сортировку по убыванию как
`DESC NULLS FIRST`, так что `NULL` встаёт последним по возрастанию и первым по убыванию, и страницы
после курсора, `reverse()` и `last()` не теряют строк. `ValueRange` окна со смещением сортирует по
значению как по `Float64`, а `NULL` — как по бесконечности с той стороны, куда встаёт `NULL`:
собственный диапазон ClickHouse вокруг `NULL` захватывает другие строки.
`ArrayAgg(order_by=...)` ставит `NULL` в значении сортировки туда, куда его ставит сортировка.

## <a id="long-in-lists"></a>Длинные списки `__in`

Сервер медленно разбирает список литералов: 100 000 значений занимают почти секунду. Список `__in` или
`__not_in` из 500 и более значений одного простого типа — UUID, целых, текстов, дат или строк из них для
ключа из нескольких колонок — передаётся одним параметром: чтение отправляет значения рядом с командой
внешней таблицей (`x IN hare_set_1`), которую сервер читает как данные за несколько миллисекунд, а любая
другая команда (мутация, `DELETE`), как и чтение в транзакции, которая не читает внешних таблиц, пишет их
списком литералов. SQL запроса один и тот же при любой длине списка, поэтому у него один план.

Индексы — это индексы пропуска данных: `Index(fields=...)` создаёт индекс `minmax` с гранулярностью 1, а
остальные типы есть в `hare.dialects.clickhouse.indexes` — см.
[Модели](models.ru.md#data-skipping-indexes). `hare inspectdb` и `hare drift` читают таблицы, колонки,
первичные ключи, комментарии, индексы пропуска, опции таблиц, представления и словари из таблиц `system`.

## <a id="correlated-subqueries"></a>Связанные подзапросы

ClickHouse выполняет связанные подзапросы, но часть из них считает неверно или отклоняет:

- **`EXISTS`**, связанный равенством колонок — и строки колонок составного ключа, — пишется как
  `(columns) IN (SELECT ...)` — собственный связанный `EXISTS` сервер не выполняет в `ON` соединения и
  над `UNION DISTINCT` (25.8). `EXISTS` над `union()` пишется как `EXISTS` любой из частей, каждая так
  же. Связанный в своём `WHERE` не только равенствами (`version__gt=OuterReference("version")`, как
  [`LatestVersions`](../../integrations/request-queries.ru.md#latestversions)) выполняется как
  собственный `EXISTS` сервера; в `UPDATE` или `DELETE` или связанный вне своего `WHERE` он даёт
  `UnSupportedError`. Форма, которую сервер пока не выполняет, даёт `UnSupportedError` с его сообщением.
- **Группировка по связанному подзапросу** (`values("author_name").annotate(...)` над `Subquery` с
  `OuterReference`) даёт `UnSupportedError` — сервер по таким не группирует.
- **Подзапрос, который сам сортирует или срезает свои строки** (`Subquery(... .order_by("-created")[:1])`
  с `OuterReference`), даёт `UnSupportedError` — сервер его отклоняет.
- **Подзапрос, выбирающий `Count`, `Sum` или другой агрегат своих строк и связанный по колонке, общей у
  строк внешнего запроса** (`Book.objects.annotate(n=Subquery(Award.objects.filter(author=OuterReference(
  "author"))...))`), даёт `UnSupportedError` (`Features.supports_correlated_aggregates`): сервер читает
  каждую его строку столько раз, сколько внешних строк держат то же значение, и столько же раз её
  считает. Связанный по первичному ключу или уникальному полю внешней модели (`OuterReference("pk")`) он
  работает, как и `Max`, `Min` и `Avg` по любой колонке. Считайте через связь — `annotate(Count("books"))`.
- **Подзапрос в `ORDER BY` или выбранный рядом с `WHERE`** вычисляется в производной таблице: строки
  выбираются без `WHERE`, условия и ключи сортировки становятся её скрытыми колонками, а внешний запрос
  фильтрует, сортирует и срезает их. SQL длиннее, результат — тот, что просит запрос.
- `UPDATE` или `DELETE`, в условии которого есть связанный подзапрос, даёт `UnSupportedError` — мутация
  их не выполняет.
- **`OuterReference` через связь** (`OuterReference("author__name")`) читает колонку таблицы,
  присоединённой к запросу вокруг подзапроса, а по таким сервер не связывает: это `UnSupportedError`.
  Пройдите связь внутри подзапроса и свяжите его колонкой самой внешней таблицы
  (`Author.objects.filter(books__id=OuterReference("id"))`) или прочитайте поле связи без подзапроса
  (`F("author__name")`).
- Таблица, которую подзапрос присоединяет, читается через производную таблицу, как и его собственная: в
  ClickHouse таблица с псевдонимом отзывается и на своё имя, и таблица подзапроса забрала бы имя внешнего
  запроса.

## <a id="server-faults"></a>Ошибки версии сервера

hare не обходит ошибку версии ClickHouse; остаётся собственная ошибка или собственный результат сервера:

- **Колонка, ставшая `Nullable`** (`AlterField` на `null=True`): ClickHouse до 26.3 читает карту NULL,
  которой нет у частей, сохранённых до изменения, как NULL во всех значениях — `filter(title__isnull=True)`
  находит все такие строки. На этих версиях перепишите колонку после миграции сами:
  `ALTER TABLE "article" UPDATE "title" = "title" WHERE 1` (в `RunSQL` после `AlterField`).
- **`update()`, ставящий константу под отрицанием, которое сворачивается в константу**
  (`exclude(owner__isnull=True).update(balance=0)` при `owner` без NULL): ClickHouse до 26.3 отказывает с
  *Cannot convert column ... because it is non constant in source stream*.
- **`Count()` колонки, допускающей NULL, в окне** (`Window(Count("rating"))`): все версии до 26.9
  отказывают с *Not found column ... in block* (`NOT_FOUND_COLUMN_IN_BLOCK`).
- ClickHouse 25.12 отказывает запросу, который соединяет связь многие-ко-многим ради агрегата рядом с
  объектом `select_related()` (`Player.objects.annotate(Count("skills")).select_related("team")`), с
  *Cannot fold actions for projection* (`LOGICAL_ERROR`) — ошибка его перестановки соединений; 25.10 и 26.x
  выполняют его.

## <a id="text-order"></a>Порядок текста

ClickHouse упорядочивает и сравнивает текст по его байтам UTF-8, как SQLite по умолчанию; PostgreSQL — по
правилу сравнения (collation) своей базы, порядок локали в котором ставит `a` рядом с `A`, а буквы с
диакритикой — рядом с их основой. `order_by()`, `__gt`/`__lt` и `Min`/`Max` у `CharField`, `TextField` и
`CharEnumField` (сравнивается по метке) следуют порядку базы; `Collate(...)` просит у базы свой порядок —
в ClickHouse только в `order_by()` (`order_by(Collate("name", "en"))` пишется как
`ORDER BY name ASC COLLATE 'en'`): больше нигде сервер правило сравнения не принимает.

## <a id="json"></a>JSON

`JSONField` — колонка `JSON`, пути которой хранятся типизированными подколонками (кроме `payload` и
`headers` outbox — см. [Outbox](../../integrations/outbox.ru.md#encoding)); через
clickhouse-driver, который не читает колонку `JSON`, это колонка `String` с текстом JSON, которую читают
функции `JSON*`. Какая из них у подключения, следует из его драйвера ещё до открытия — `hare drift`,
`hare sqlmigrate` и миграции сравнивают, печатают и создают колонку этого подключения. Таблицу, созданную
через один драйвер, через другой
тоже читают, пишут и фильтруют; `hare drift` через другой сообщает `AlterField` колонки — они
по-разному хранят `null`, см. ниже. Тип `JSON` хранит меньше, чем текст JSON, и
значение, которое он прочитал бы иначе, даёт `ValidationError` до отправки — колонка `String` через
clickhouse-driver хранит всё это:

- Хранится только объект: список, строка или число на верхнем уровне отклоняются.
- Ключ со значением `None` или пустым объектом на любой глубине отклоняется (`{"a": None}`,
  `{"items": [{"b": {}}]}`) — такого пути тип не хранит. `None` или пустой объект внутри массива
  (`[None, 1]`, `[{}]`) хранится. Поэтому `field__path=None`, `None` в `field__path__in=[...]` и
  `field__path__isnull=True` находят путь без значения — у строки, всё значение которой NULL, пути нет, —
  `field__path__not=None` и `None` в `field__path__not_in=[...]` его исключают, а сравнение пути
  (`field__path__lt=10`) его не находит.
- Целое вне диапазона `Int64` и `UInt64` (от `-2**63` до `2**64 - 1`) отклоняется — тип хранит его как
  `float`.
- Порядок ключей не сохраняется.
- Точка в ключе остаётся частью ключа: каждое соединение задаёт `json_type_escape_dots_in_keys`, а hare пишет
  точку так, как её экранирует сервер, — `%2E`, в том числе в мутации `update()`, которая читает JSON с
  собственными настройками сервера. Ключ, в котором уже есть текст `%2E`, даёт `ValidationError`: сервер
  прочитал бы его обратно как точку.
- Массив целых чисел и `float` хранит их все как `float`: `[1, 2.5]` читается как `[1.0, 2.5]`; массив,
  целые которого (в том числе во вложенных массивах) больше `2**53` — его `float` точно не хранит, —
  отклоняется.
  Логическое значение остаётся логическим, а строка — строкой, даже похожая на дату или момент
  (`"2024-01-02"`): каждое подключение выключает `input_format_try_infer_dates` и
  `input_format_try_infer_datetimes`. Но `update()` пишет мутацией, которая читает JSON с собственными
  настройками сервера: в массиве чисел и логических значений `true` становится `1`, а строка, похожая на
  дату, читается как `date` или `datetime`, если профиль сервера по умолчанию не ставит эти две настройки
  в `0`.

Пути ключей, `__has_key`, `__has_keys` и `__has_any_keys` работают на обоих типах; `__filter`,
`__contains` и `__contained_by` не работают — в JSON ClickHouse нет вхождения, и они дают
`UnSupportedError`; фильтруйте по путям ключей. `__has_key`, `__has_keys` и `__has_any_keys` находят только
ключ объекта (`JSONHas()`). Миграция переводит колонку `String` в `JSON` через `MODIFY COLUMN`.

`JSONField`, сравниваемый целиком (`=`, `__not`, `__in`, `__not_in`) в колонке `JSON`, приводится к
`JSON` и сравнивается самим ClickHouse, поэтому порядок ключей не важен; `__in` сравнивает так каждое
значение, через `OR`. Колонка `JSON` хранит только объект: сравниваемое значение, которое не объект
(список, строка, число), даёт `ValidationError`. В колонке `String` с текстом JSON — через clickhouse-driver —
сравнивается текст JSON в том виде, в каком он записан.

Сравнение порядка пути (`__gt`, `__gte`, `__lt`, `__lte`, `__range`, `order_by()`) использует значение
`Dynamic`, которое ClickHouse читает из текста JSON (`JSONExtract(..., 'Dynamic')`, настройка сессии
`allow_suspicious_types_in_order_by=1`). ClickHouse упорядочивает `Dynamic` сначала по имени его типа,
потом по значению: `Float64` `2.5` идёт перед `Int64` `9`, логическое — перед числами, а строки — после.
Сравнение пути, в котором лежат и строки, и числа, даёт `NO_COMMON_TYPE` ClickHouse. Порядок `jsonb`
(объекты, массивы, логические, числа, строки, `null`) есть только в PostgreSQL, а сравнение с объектом или
массивом — собственное сравнение ClickHouse.

`Cast(..., TextField())` и `Concat` от `JSONField` дают текст, который пишет ClickHouse: порядок ключей
колонки (собственный у типа `JSON`, записанный — в колонке `String`) и её запись числа (`1e+20`, `12.0`).
Текстовый оператор фильтра по пути сопоставляет текст, который ClickHouse читает из значения.
`JSONObject()` и `JSONArray()` пишет `toJSONString()`: десятичное без хвостовых нулей, `DateTime64` в виде
`2024-02-29 13:45:06.789000`, `NaN` как `null`, байты — шестнадцатеричной записью, которую хранит колонка.

`BinaryField` — колонка `String` с шестнадцатеричной записью байтов строчными буквами: clickhouse-connect
читает `String` как текст и пишет байты, не являющиеся UTF-8, их шестнадцатеричной записью, поэтому сырые
байты нельзя было бы прочитать обратно. Шестнадцатеричная запись читается обратно точно через оба
драйвера и упорядочивается так же, как байты; `unhex()` даёт байты в SQL.

## <a id="bulk-loads"></a>Массовая загрузка

`bulk_create()` отправляет строки одной двоичной вставкой — в формате ClickHouse `Native`, колонка за
колонкой — вместо текста `INSERT ... VALUES`: литералы для значений не пишутся, а сервер не разбирает
SQL. Так строки и должны попадать в ClickHouse, и поэтому много строк стоит писать через `bulk_create()`,
а не через `create()` в цикле.

- `batch_size` делит объекты на столько вставок; без него они идут одной.
- Значения — те же, что пишет `create()`: момент — это мгновение, которое он обозначает (момент без
  часового пояса при `use_timezone=False` — мгновение его местного времени, и читается он обратно как это
  местное время), значение JSON — его текст или объект.
- [Наблюдатели](../../observability/observers.ru.md), спаны и счётчик запросов видят вставку как
  `INSERT INTO <table> (<columns>) FORMAT Native` — строки не входят ни в какой текст SQL.
- `use_copy=True` просит ту же загрузку и здесь ничего не меняет. `returning=True` и параметры
  конфликтов дают `UnSupportedError`.
- С `async_insert=true` сервер собирает строки многих вставок, прежде чем записать их; с
  `wait_for_async_insert=false` вызов возвращается до записи и не сообщает об ошибке.
