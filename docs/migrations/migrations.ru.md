# Создание и применение миграций

Команды `hare`, которые создают и применяют миграции, вызванные из Python; ограничение ожидания
блокировки при миграции; объединение многих миграций в одну; класс `Migration`, который объявляет файл
миграции; как миграция записывает перечисления полей-перечислений и заменяемые модели.

## <a id="migrations-api"></a>Команды как функции (`hare.migrations.api`)

Каждая команда миграций — функция: CLI только разбирает аргументы, вызывает её и печатает результат.
Вызывайте их из сценария развёртывания, теста или служебного эндпоинта, не запуская отдельный процесс:

```python
from hare.migrations.api import checkmigrations, makemigrations, migrate, plan, sqlmigrate, squashmigrations

async def makemigrations(
    *,
    config: Mapping[str, Any] | HareConfig | str,
    app_labels: Sequence[str] | None = None,
    empty: bool = False,
    merge: bool = False,
    name: str | None = None,
    rename_questions: RenameQuestions | None = None,
) -> MigrationChanges: ...

async def squashmigrations(
    *,
    config: Mapping[str, Any] | HareConfig | str,
    app_label: str,
    end_name: str,
    start_name: str | None = None,
    squashed_name: str | None = None,
) -> SquashedMigration: ...

async def migrate(
    *,
    config: Mapping[str, Any] | HareConfig | str,
    app_labels: Sequence[str] | None = None,
    target: str | None = None,
    fake: bool = False,
    dry_run: bool = False,
    reporter: Callable[[str, list[PlanStep], bool, bool], object] | None = None,
    progress: Callable[[str, str, str], object] | None = None,
    lock_timeout: float | None = None,
) -> None: ...

async def plan(
    *,
    config: Mapping[str, Any] | HareConfig | str,
    app_labels: Sequence[str] | None = None,
    target: str | None = None,
) -> list[str]: ...

async def sqlmigrate(
    *,
    config: Mapping[str, Any] | HareConfig | str,
    app_label: str,
    migration_name: str,
    backward: bool = False,
) -> list[str]: ...

async def checkmigrations(
    *,
    config: Mapping[str, Any] | HareConfig | str,
    app_labels: Sequence[str] | None = None,
) -> list[MigrationRisk]: ...
```

`config` — всё, что принимает [`Hare.init()`](../connections/configuration.ru.md#hare-init):
`HareConfig`, словарь, путь к файлу `.json`/`.yml` или `"module.VARIABLE"`.

- `makemigrations()` возвращает миграции, которые приводят историю каждого приложения к его моделям, —
  **ещё не записанные**: в `MigrationChanges.writers` по одному `MigrationWriter` на новую миграцию
  (пусто, если ничего не изменилось), в `warnings` — возможные переименования, которые не удалось
  распознать, в `data_loss_warnings` — изменения, теряющие сохранённые значения, в `safety_risks` —
  `MigrationRisk` новых миграций (найденные без чтения базы, поэтому каждая существующая таблица
  считается большой — см. [Проверка миграций](zero-downtime.ru.md#checking-migrations)). Запишите каждую
  через `writer.write()` (возвращает путь к файлу); `writer.as_string()` — текст файла,
  `writer.name`/`writer.app_label` её называют. Поле, переименованное с сохранением колонки, узнаётся по
  колонке: добавленное поле, чей `source_field` называет колонку удалённого
  (`a2 = IntField(source_field="a")` вместо `a`), или поле, которое своим именем забирает обратно колонку,
  державшуюся у удалённого поля под `source_field` (снова `a`), — это `RenameField`, колонка остаётся.
  Любое другое переименование решают ответы `rename_questions` (см. [Переименования](#renames)). Поле
  ключа, которое одновременно переименовали и изменили
  (часть составного первичного ключа, поле ключа партиционирования), не отличить от нового поля:
  `makemigrations` даёт `ConfigurationError`, называя `RenameField`, — напишите это переименование
  вручную, а затем изменение. Приложению без пакета миграций пакет создаётся. `empty=True` делает по
  одной пустой миграции на приложение, `merge=True` — по одной миграции, соединяющей разветвившуюся
  историю; обоим нужны `app_labels`, и вместе их задать нельзя. `ConfigurationError` — для неизвестного
  приложения, для разветвившейся истории без `merge` и для `merge` истории, где соединять нечего.
- `squashmigrations()` сжимает подряд идущие миграции приложения — от `start_name` (без него — от первой)
  до `end_name`, каждая задаётся именем или однозначным началом имени — в одну (см.
  [Сжатие миграций](#squashing-migrations)). Возвращает `SquashedMigration`: `writer` (миграция, ещё не
  записанная; `None`, если в диапазоне одна миграция), `replaced_names`, `squashed_operation_count`
  (операций до сокращения) и `elided_operation_count` (выброшенных `RunPython`/`RunSQL` с `elidable`).
  `ConfigurationError` — для неизвестного приложения или миграции, начала после конца, начала имени,
  подходящего к нескольким миграциям, и имени, которое у приложения уже занято.
- `migrate()` применяет или откатывает миграции до `target` — `"app_label"` (последняя миграция
  приложения), `"app_label.migration_name"` или `"app_label.zero"` (откатить всё); без него каждое
  приложение доходит до последней миграции. Миграции всех подключений составляют один план в порядке их
  зависимостей: миграция приложения на одном подключении, зависящая от миграции приложения на другом,
  выполняется после неё, а откат идёт в обратном порядке; идущие подряд шаги одного подключения выполняются
  вместе под блокировкой миграций этого подключения. `reporter(connection_alias, plan_steps, fake, dry_run)`
  вызывается с каждой такой группой шагов перед её выполнением, `progress(event, app_label, migration_name)`
  — вокруг каждой миграции; оба могут быть `async def`.
- `plan()` возвращает (и печатает) упорядоченные шаги, которые сделал бы `migrate()`; `sqlmigrate()`
  возвращает SQL одной миграции (с `backward=True` — её отката), не выполняя его, — тот SQL, который
  выполняет `migrate()`: DDL следует из одного состояния миграций, у каждого объекта имя, которое ему даёт
  hare, из базы ничего не читается.
- `checkmigrations()` возвращает риски миграций, которые применил бы `migrate()`, — см.
  [Проверка миграций](zero-downtime.ru.md#checking-migrations).

```python
changes = await makemigrations(config="settings.HARE_ORM", app_labels=["models"])
for writer in changes.writers:
    print("writing", writer.write())
await migrate(config="settings.HARE_ORM")
```

`makemigrations()` и `squashmigrations()` привязывают модели в собственном контексте и к базе не
подключаются. `migrate()`, `plan()` и `sqlmigrate()` сами вызывают `Hare.init()` и оставляют контекст
инициализированным — по окончании вызовите `await Hare.close_connections()`.

## <a id="renames"></a>Переименования

По одним моделям не отличить переименованное поле от удалённого и нового — `makemigrations` спрашивает.
Вопрос задаётся только об одном удалённом и одном добавленном поле модели, объявленных в
точности одинаково (тип и параметры, без имён); если так объявлено несколько полей, ничего не
спрашивается — что во что переименовано, не угадывается, пары задаёт только ответ `--rename`,
данный заранее. Так же с моделью: одна удалённая и одна добавленная модель приложения, объявленные в
точности одинаково (поля и опции), — модель, которую в одном запуске переименовали и изменили, — это два
запуска: сначала переименуйте, потом меняйте. И с моделью другого приложения, которая без изменений
забирает таблицу удалённой модели: перенесена ли она туда?

- Да: `RenameField` (колонка переименовывается, строки остаются), `RenameModel` (таблица
  переименовывается, если названа по классу) или перенос — `CreateModel`/`DeleteModel` с
  `state_only=True`, таблица остаётся.
- Нет или нет ответа: поле или модель удаляются и добавляются — их строки теряются — с предупреждением
  «возможно, нераспознанное переименование», где назван `--rename`, который это переименует.

```python
class RenameQuestions:
    def __init__(self, renames: Mapping[str, str] | None = None) -> None: ...
    def ask(self, question: str) -> bool: ...
```

`hare makemigrations` спрашивает в терминале (см. [`hare makemigrations`](cli.ru.md#makemigrations));
функции принимают `rename_questions`: в `renames` — ответы, данные заранее, по тому, что
переименовывается, — `"app.Model.old_field": "new_field"` (модель — под новым именем, если её тоже
переименовали), `"app.OldModel": "NewModel"`, `"old_app.Model": "new_app.Model"`, — а вопрос без ответа
там уходит в `ask()`, который отвечает «нет»; переопределите его, чтобы спрашивать самому. Каждый вопрос
задаётся за запуск один раз.

```python
changes = await makemigrations(
    config="settings.HARE_ORM",
    rename_questions=RenameQuestions({"shop.Item.title": "name", "shop.Order": "Purchase"}),
)
```

Переименование меняет то, что называет поле или таблицу структурно, — см.
[`RenameField`](operations.ru.md#rename-field); готовый SQL остаётся таким, как вы его написали.

## <a id="lock-timeout"></a>Ожидание блокировок

```python
await migrate(config="settings.HARE_ORM", lock_timeout=5)   # или "migrations": {"lock_timeout": 5}
```

```text
hare migrate --lock-timeout 5
```

Миграция, меняющая нагруженную таблицу, ждёт блокировку, которую держит каждая открытая транзакция с этой
таблицей, — а пока она ждёт, каждый следующий запрос к таблице встаёт в очередь за ней. С `lock_timeout`
(секунды, от `0.001` до `2147483.647`) команда миграции, которая дольше ждёт блокировку, взятую другим
сеансом, завершается ошибкой: миграция откатывается, не записывается в журнал, и `migrate` даёт ошибку
базы (`OperationalError` — «canceling statement due to lock timeout» в PostgreSQL, «database is locked» в
SQLite); повторите её, когда таблица менее загружена. `migrate(lock_timeout=...)` и `--lock-timeout`
важнее `migrations.lock_timeout` из конфига; неверный тип или значение вне диапазона дают
`ConfigurationError`. В ClickHouse таймаута блокировки для DDL нет: миграция, запущенная с ним, даёт
`UnSupportedError`.

| Миграция | PostgreSQL | SQLite |
|---|---|---|
| Атомарная | `SET LOCAL lock_timeout` в её транзакции | `busy_timeout` соединения на время её транзакции, затем прежнее значение |
| Неатомарная | отдельное соединение с `SET lock_timeout` на всю миграцию (соединение из пула потеряло бы настройку), все запросы с именем этого подключения идут через него; после миграции закрывается | `busy_timeout` соединения на всю миграцию, затем прежнее значение |

## <a id="squashing-migrations"></a>Сжатие миграций

```text
hare squashmigrations app 0012                                      # с 0001 по 0012
hare squashmigrations app 0005 0012 --squashed-name accounts_rework  # с 0005 по 0012
```

Сжатая миграция содержит операции заменяемых миграций по порядку, но сокращённые: модель, созданная и
затем изменённая, создаётся сразу изменённой; поле, добавленное и удалённое, исчезает; так же и модель,
созданная и удалённая; переименования подряд становятся одним; более поздние параметры модели заменяют
более ранние. Операция переставляется через другую, только если они не касаются общих моделей, — через
`RunPython`/`RunSQL`, который может касаться любой, перестановок нет. Поле, добавленное с
`db_index=True`, входит в `CreateModel` своей модели со своим флагом; связь один-к-одному с составным
ключом входит вместе с `AddConstraint`, делающим её уникальной, — если операцию между ними нельзя
переставить, сжатая миграция удаляет это ограничение сразу после `CreateModel` (`RemoveConstraint` по его
полям) и добавляет там же, где его добавляли исходные миграции.
`RunPython`/ `RunSQL` сохраняются, если не объявлены с `elidable=True`; функция `RunPython`, определённая
в файле заменяемой миграции, копируется в новый файл вместе с импортами своего модуля, которыми
пользуется (функция, использующая другие имена своего модуля — константу, вспомогательную функцию, —
отклоняется: перенесите их в функцию или в импортируемый модуль). Новая миграция называется по первой
заменяемой (`0005_accounts_rework`; без `--squashed-name` — `0001_squashed_0012_<name>`), зависит от того
же, от чего заменяемые зависят вне диапазона, и получает `atomic = False`, если такая есть среди
заменяемых. При сжатии диапазона со сжатой миграцией она заменяется своими исходными миграциями.

Диапазон нельзя сжать в одну миграцию, если внутри него стоит миграция другого приложения — от неё
зависит миграция диапазона, а сама она зависит от более ранней миграции диапазона: сжатая миграция
зависела бы от миграции, которая зависит от неё самой. `squashmigrations` бросает `ConfigurationError` с
именами всех трёх и ничего не записывает; сожмите отдельно диапазон до этой более ранней миграции и
миграции после неё.

`replaces` определяет, как мигрирует база, пока файлы заменяемых миграций ещё лежат на диске:

| Заменяемые миграции, применённые к базе | `migrate` |
|---|---|
| Ни одной | Выполняет сжатую миграцию и записывает в журнал её и все заменяемые. |
| Все | Ничего не выполняет и записывает сжатую миграцию. |
| Часть | Выполняет оставшиеся заменяемые по одной, затем записывает сжатую миграцию. |

Откат сжатой миграции откатывает и снимает из журнала их все. Миграция, зависящая от заменяемой — того же
приложения или другого, — зависит вместо неё от сжатой. Когда все базы применили все заменяемые миграции,
удалите их файлы (а затем и `replaces` сжатой миграции); база, применившая только часть, при удалённых
файлах даёт `MigrationLoadError` с перечнем недостающих.

## <a id="migration"></a>`Migration`

```python
class Migration:
    operations: list[Operation] = []
    dependencies: list[tuple[str, str]] = []
    run_before: list[tuple[str, str]] = []
    replaces: list[tuple[str, str]] = []
    initial: bool | None = None
    atomic: bool = True
```

При `atomic = True` (по умолчанию) вся миграция, включая её запись в таблице миграций, выполняется в
одной транзакции, если база поддерживает транзакции для команд изменения схемы. При `atomic = False`
операции выполняются по одной вне транзакции, кроме операции, объявленной с `atomic=True`
(`RunPython`/`RunSQL`): она выполняется и откатывается целиком в собственной транзакции.

Миграция, которая выполняется вне транзакции, — в ClickHouse это любая миграция, транзакций для изменения
схемы там нет, — до первой своей операции проверяется на то, в чём соединение откажет: опции таблицы
модели, которых нет у сервера, или опции, не подходящие модели, а также индекс или ограничение, которые
база не может хранить (направление ключа индекса на ClickHouse, частичное или отложенное уникальное
ограничение там, где у диалекта их нет, ограничение исключения вне PostgreSQL), — у создаваемой модели,
в `AddIndex`/`AddConstraint` или в изменяемом объекте, — дают `UnSupportedError`/`ConfigurationError`,
и схема остаётся нетронутой. Сбой во время
выполнения операций оставляет применёнными те, что были до него: `migrate` сообщает, что миграция
прервана на полпути, не записывает её как применённую, а схему исправляют вручную.

### <a id="migration-lock"></a>Один `migrate` за раз

`migrate` держит блокировку миграций всё время своей работы: второй `migrate` той же базы — из другого
процесса или с другой машины — ждёт её, затем видит миграции, применённые первым, применёнными и
применяет только оставшиеся. PostgreSQL берёт advisory-блокировку уровня транзакции на отдельном
соединении; SQLite — блокировку ОС на файле `<база>-migrate-lock` рядом с файлом базы (для базы в памяти —
никакой); ClickHouse — эфемерный узел ClickHouse Keeper `/hare/migrations/<база>/migrate` (в имени
каждый байт, кроме букв, цифр и `_.-~`, записан как `%XX`), если у соединения задан
[`keeper_hosts`](../dialects/clickhouse/connecting.ru.md), — без него блокировки нет, и одновременно может
работать только один `migrate` базы ClickHouse; удаление базы (`db_delete()`) удаляет и
`/hare/migrations/<база>`. Любая блокировка снимается, когда процесс завершается. Пробный запуск (dry
run) блокировку не берёт.

### <a id="sqlite-table-rebuild"></a>Перестройка таблицы (SQLite)

SQLite применяет большинство изменений колонок, пересоздавая таблицу: по модели создаётся копия, заполняется
из старой таблицы и переименовывается на её место. Счётчик `AUTOINCREMENT` копии продолжает счётчик старой
таблицы, поэтому идентификатор удалённой последней строки больше никогда не выдаётся; представление,
ссылающееся на таблицу, продолжает работать; все триггеры и индексы, объявленные в моделях, создаются
заново, в том числе частичное `UniqueConstraint(condition=...)`, — созданные через `RunSQL` уходят вместе со
старой таблицей, поэтому опишите их как `Trigger`/`Index` модели или выполните их `RunSQL` снова после
изменения. Если меняется тип поля, каждое сохранённое значение преобразует SQLite: дата-время — в свою дату
(для значения с поясом — дату момента в UTC), текст даты или дата-времени — в свою дату, дата — в свою
полночь (в UTC при `use_timezone=True`), число и логическое значение — друг в друга (не ноль — истина),
текст — в логическое значение, если он читается как `true`, `false`, `1` или `0` (в любом регистре, без
пробелов по краям), логическое значение — в собственный текст SQLite (`1` или `0`), целое число с плавающей
точкой — в целое. Дробное значение, превращаемое в целое, не отбрасывается, а даёт
`FieldNarrowingDataLossError` (см. [`AlterField`](operations.ru.md#alter-field)). Отказ получает только
сохранённое значение, которое новый тип не читает, — `OperationalError` до изменения таблицы (`the column
holds "abc", which is no integer`); ни одна пара типов не отвергается из-за отсутствия приведения.
Поле геометрии или вектора, у которого меняются тип, SRID, число координат или длина (колонка хранит
любую геометрию или вектор), сначала записывает новым полем каждое сохранённое значение, и значение, которое
оно отвергает, так же даёт `OperationalError`.
Изменение, после которого колонка объявлена как прежде, — только собственный индекс поля или его сторона в
Python (`sensitive`, `related_name` связи), — сохраняет таблицу: индекс удаляется или создаётся отдельной
командой, и у связи тоже, если её ключевые колонки и то, на что указывает их `REFERENCES`, не меняются.

### <a id="sqlite-foreign-key-check"></a>Внешние ключи во время миграции (SQLite)

SQLite выполняет каждую миграцию с `PRAGMA foreign_keys = OFF` (это нужно для пересоздания таблиц). Перед
фиксацией атомарной миграции и после каждой операции неатомарной `PRAGMA foreign_key_check` проверяет,
что ни одна строка не ссылается на отсутствующую родительскую; нарушение даёт
`hare.exceptions.IntegrityError` со списком нарушающих строк и откатывает миграцию (или атомарную
операцию). Подключение, настроенное с выключенным `foreign_keys`, не проверяется. Удаление в `RunPython`
такой миграции само выполняет каждое `on_delete`, как на базе без внешних ключей, — пока они выключены,
база ничего не каскадирует.

### <a id="loading-and-planning"></a>Загрузка и планирование

Если `migrate` передано несколько целей, каждая планируется от состояния, которое оставляют предыдущие;
цели, которые одновременно применили бы и откатили одну и ту же миграцию, дают `QueryError`.

Файлы миграций перечитываются при каждой загрузке: файл, изменённый после первого импорта, будет учтён
следующим `migrate`/`plan` в том же процессе.

## <a id="runtime-enums"></a>Перечисления полей-перечислений

Миграция хранит элементы перечисления `CharEnumField`/`IntEnumField` такими, какими они были при её
записи: их держит тип колонки (`Enum8`/`Enum16` в ClickHouse) или его `CHECK`, поэтому элемент, добавленный
в класс позже, — изменение, которое увидит следующий `makemigrations` и применит миграция после него.
Перечисление может быть и созданным во время работы приложения — например, из вариантов, заданных в
панели администратора:

```python
Status = StrEnum("Status", {"NEW": "new", "DONE": "done"})
status = fields.CharEnumField(Status, default=Status.NEW)
```

Миграция не импортирует перечисление такого поля — у созданного во время работы и нет атрибута модуля, откуда
его можно импортировать: она объявляет его у себя в начале в функциональной форме, на той же основе
(`StrEnum`, `IntEnum`, `IntFlag`, `Enum`, тип данных, примешанный через `type=`) и с элементами в том же
порядке — один раз, сколько бы полей, значений по умолчанию и условий ограничений его ни использовали:

```python
from enum import StrEnum

Status = StrEnum('Status', {'NEW': 'new', 'DONE': 'done'})

class Migration(migrations.Migration):
    operations = [
        ops.AddField(model_name='Book', name='status',
                     field=fields.CharEnumField(default=Status.NEW, enum_type=Status, max_length=4)),
    ]
```

Перечисление, которое называют только значение по умолчанию или условие, без поля-перечисления в миграции,
импортируется, если его `__module__` и `__qualname__` ведут к самому классу или если оно объявляет
`migration_import_path`. Перечисление, которое функциональная форма записать не может, — с несколькими
основами-перечислениями или несколькими типами данных — отклоняется с `ConfigurationError`. Два разных
перечисления с одним именем объявляются как `Status` и `Status2`. Автоматическое создание миграций сравнивает
перечисление по содержимому — основе, имени и элементам по порядку, — а не по классу: то же перечисление,
созданное заново после перезапуска, ничего не меняет, а добавленный, удалённый, переименованный, изменённый
или переставленный элемент даёт `AlterField`.

## <a id="swappable-models"></a>Заменяемые модели в миграциях

Пакет пишет свои миграции один раз, а проект направляет их на свою модель через
[настройку замены](../models/relations.ru.md#swappable-models). `makemigrations` записывает связь,
объявленную через `swappable("USER_MODEL")`, этим же вызовом, а её зависимость — как
`migrations.swappable_dependency("USER_MODEL")`, а не как миграцию приложения, на которое настройка
указывает сейчас:

```python
from hare import fields, migrations
from hare.migrations import operations as ops
from hare.models import swappable


class Migration(migrations.Migration):
    dependencies = [migrations.swappable_dependency("USER_MODEL")]

    operations = [
        ops.CreateModel(
            name="Consent",
            fields=[
                ("id", fields.IntField(primary_key=True)),
                ("user", fields.ForeignKeyField(swappable("USER_MODEL"), related_name="consents", null=True)),
            ],
        ),
    ]
```

- `swappable_dependency("USER_MODEL")` — это `(app_label, "__first__")`, первая миграция приложения, на
  которое указывает настройка (для собственного приложения миграции — никакой). Она вычисляется при
  импорте файла, поэтому hare должен быть настроен до загрузки миграций; иначе загрузка даёт
  `MigrationLoadError` с просьбой сначала вызвать `Hare.init()`. `swappable_dependency` — это класс
  `SwappableDependency` (`hare.migrations`): тот же кортеж, который хранит настройку, из которой взят, в
  `.setting`.
- `CreateModel` модели с `Meta.swappable` записывает его в `options`. Пока модель заменена, каждая
  операция с её таблицей (`CreateModel`, `AddField`, `AddIndex`, ... и их откат) меняет только состояние
  миграций — `migrate` не создаёт для неё таблицу, а `migrate <app> zero` работает одинаково с настройкой
  и без неё. `sqlmigrate` и `plan` показывают внешний ключ на таблицу модели, которая используется на
  самом деле.
- Смена модели, на которую указывает настройка, ничего не меняет в миграциях пакета: поле сравнивается
  как та же ссылка. Собственная модель проекта получает обычный `CreateModel` в приложении проекта.
- `makemigrations` работает и тогда, когда у приложения проекта, на которое указывает настройка, ещё нет
  миграций: `swappable_dependency` пакета на него не записывается, пока не появится первая миграция этого
  приложения. Модель проекта, которая ссылается обратно на модель пакета, образует с ней цикл;
  `makemigrations` разбивает его на две миграции так же, как для любых двух приложений, переносимых
  вместе.
- `makemigrations` и `squashmigrations` сортируют импорты и форматируют записываемые файлы через ruff,
  если он установлен, поэтому записанная миграция проходит `ruff check`/`ruff format --check`.

Выбирайте настройку до создания таблиц пакета. `migrate` отказывается работать, пока у таблицы, созданной
применённой миграцией, есть внешний ключ `swappable()` — собственный у связи или у автоматической
промежуточной таблицы связи многие-ко-многим, — который ссылается не на ту таблицу, что у модели,
на которую указывает настройка сейчас, а `hare drift` сообщает о такой колонке с именем настройки. Чтобы
перевести существующий проект на другую модель, напишите свою миграцию: создайте таблицу новой модели,
скопируйте строки, перенаправьте внешние ключи таблиц пакета (`RunSQL`) и только потом смените настройку.
