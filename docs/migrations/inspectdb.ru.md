# Модели по существующей базе

`hare inspectdb [tables...] [--connection ALIAS] [--schema SCHEMA]` читает таблицы существующей базы —
PostgreSQL, SQLite или ClickHouse — и печатает модуль моделей для них: поля, связи, индексы,
ограничения и опции таблиц, так же, как их написал бы `makemigrations`. То же доступно из кода
([ниже](#generating-model-source-programmatically)).

```bash
hare inspectdb --connection default --schema public users orders > app/models.py
```

## <a id="reconstruction-rules"></a>Что восстанавливается

`inspectdb` сообщает об ошибке, а не создаёт молча неверную модель, если встречает совпадение имён,
которое нельзя выразить: две таблицы, различающиеся только регистром, иначе дали бы два одинаковых
имени классов Python (один молча заменил бы другой), а колонка внешнего ключа, имя атрибута которой
после отбрасывания суффикса (`event_id` → `event`) совпадает с другой обычной колонкой, иначе
потеряла бы одно из двух полей. Оба случая дают явную ошибку. Он также восстанавливает составной
внешний ключ одним `ForeignKeyField` (а не полем на каждую колонку) и индекс по выражению SQL, а не
по списку колонок, — оба превращаются в настоящий код модели, а не в комментарий `# TODO`.

Внешний ключ, объявленный с `ON DELETE SET DEFAULT`, восстанавливается как `on_delete=SET_DEFAULT`
с `DEFAULT` колонки в качестве `db_default` (`ForeignKeyField` с настоящим ограничением его требует).
Если у колонки нет `DEFAULT`, база на самом деле сбрасывает её в `NULL` (или останавливает удаление,
если колонка `NOT NULL`), поэтому `inspectdb` записывает `SET_NULL` (или `NO_ACTION`) с комментарием
`# TODO` вместо поля `SET_DEFAULT`, которое нельзя было бы импортировать.

Другие правила восстановления:

- Колонка внешнего ключа, которая одновременно первичный ключ таблицы, становится
  `OneToOneField(..., primary_key=True)`; колонка внешнего ключа без суффикса `_id` (`owner_code`)
  получает `source_field="owner_code"`.
- Если у таблицы две и больше связей с одной и той же таблицей (в том числе пара ссылок таблицы на
  саму себя), каждая получает `related_name="<таблица>_<поле>_set"`, чтобы их обратные связи не
  совпадали.
- Частичный индекс сохраняет своё условие `WHERE` как `PartialIndex(condition=RawSQLTerm(...))` —
  в том виде, в каком его сообщает база, и в PostgreSQL, и в SQLite. Индекс по выражению
  (`lower(note)`) восстанавливается как `Index(RawSQLTerm(...))` на обоих диалектах, а составной
  внешний ключ восстанавливается и в SQLite.
- Индекс или ограничение сохраняют своё имя в базе (`Index(..., name="orders_placed_idx")`), если
  это не имя, которое hare создаёт для такого объявления, и не имя, которое PostgreSQL даёт
  безымянному индексу или ограничению `UNIQUE` (`<таблица>_<колонки>_idx`/`_key`); обычный индекс
  по одной колонке со своим именем становится именованной записью `Meta.indexes`, а не
  `db_index=True`.
- Уникальный индекс восстанавливается тем объявлением, которому принадлежит его имя: безымянным
  `UniqueConstraint(fields=...)` при имени, которое hare создаёт для такого ограничения (или
  которое PostgreSQL даёт безымянному `UNIQUE`), `Index(unique=True)` при имени, которое hare
  создаёт для такого индекса, иначе — именованным `UniqueConstraint` со своим
  `condition=` (частичный уникальный индекс, условие — готовый SQL) и `deferrable=`/`initially_deferred=`
  (в том числе у `DEFERRABLE UNIQUE` по одной колонке).
- Условие `CHECK` восстанавливается без пары скобок, в которую его оборачивает PostgreSQL
  (`CheckConstraint(check=RawSQLTerm("age >= 0"))`).
- То, что не может объявить ни один индекс hare, — колонку `INCLUDE (...)`, порядок `DESC`/`NULLS FIRST`
  или `COLLATE` у ключа, `NULLS NOT DISTINCT`, — в восстановленный индекс не попадает и перечисляется
  в `# TODO`.
- Внешний ключ на таблицу другой схемы, чем проверяемая, остаётся обычной колонкой с `# TODO`,
  называющим цель: связь может указывать только на модель из того же запуска.
- Партиция партиционированной таблицы PostgreSQL не показывается (её заменяет сама партиционированная
  таблица), если её не назвать явно; `drift` тоже не считает партиции неизвестными таблицами.
- Колонка идентификатора PostgreSQL (`GENERATED ... AS IDENTITY`, не первичный ключ) становится
  целочисленным полем с `generated=True` и `# TODO`: hare никогда не записывает её и читает
  присвоенное значение обратно, но собственных команд для колонки идентификатора у него нет. Числовое
  значение по умолчанию в кавычках (`'-1.5'::double precision`) восстанавливается числом.
- Колонка `UNIQUE` или с индексом, тип поля которой нельзя индексировать (`JSONField`),
  теряет индекс с `# TODO`, а не даёт модель, которую нельзя импортировать.
- Внешний ключ с `UNIQUE` по одной колонке восстанавливается как `OneToOneField`.
- Собственный индекс внешнего ключа (обычный индекс ровно по его колонкам ключа) не записывается —
  у `ForeignKeyField` [он есть по умолчанию](../models/relations.ru.md#index-on-the-key-column); внешний
  ключ без такого индекса и без другого индекса, начинающегося с его колонок, получает
  `db_index=False`.
- Значение по умолчанию колонки JSON (`'{}'::jsonb`) восстанавливается самим документом
  (`db_default={}`), а выражение по умолчанию в SQLite (`DEFAULT (datetime('now'))`) сохраняет свои
  скобки: `SqlDefault("(datetime('now'))")`.
- Колонка или таблица, имя которой в Python совпало бы с одним из импортов создаваемого модуля
  (колонка `fields`, таблица `model`), получает подчёркивание в конце (`fields_` с
  `source_field="fields"`, класс `Model_` с `Meta.table = "model"`), а связи указывают на
  переименованный класс.

## <a id="generating-model-source-programmatically"></a>Код моделей из программы

`hare inspectdb` печатает то, что возвращает `hare.inspectdb.SchemaInspector`:

```python
from hare.inspectdb import SchemaInspector

source = await SchemaInspector.inspect(connection, ["users", "orders"], schema="public")
```

`inspect(connection, tables=None, schema=None)` создаёт один модуль, готовый к импорту, для этих
таблиц (без `tables` — для всех таблиц схемы `schema`; `schema` при `None` — схема подключения по
умолчанию, а у диалекта без схем она не учитывается). Ошибки: `UnsupportedDialectError` для диалекта,
который не умеет читать схему базы, `SchemaNotFoundError`/`TableNotFoundError` для отсутствующей схемы
или таблицы и `DuplicateModelClassNameError` для двух таблиц с одним именем класса.
`SchemaInspector.render_module(table_infos, dialect)` строит код для таблиц, уже прочитанных через
`DatabaseCatalog` (см. [Модель по прочитанной схеме таблицы](../models/runtime-models.ru.md#building-a-model-from-an-introspected-table)).

Каждая таблица сначала превращается в такое же состояние модели, какое есть у объявленной модели
(`hare.inspectdb.InspectedModelBuilder(table_info, ModelGenerationOptions(dialect, app_label)).build()` возвращает
`InspectedModel`, где `state` — `ModelState` миграций из настоящих объектов полей, индексов и
ограничений, — а также заметки `# TODO` и раскладку `Meta`). Код — это то же состояние, записанное
так, как его записывает файл миграции: каждое поле, индекс и ограничение — вызовом из своего
`deconstruct()`; `ModelFactory` строит класс из того же самого состояния, поэтому сгенерированный
код и класс, построенный во время работы, никогда не расходятся.
