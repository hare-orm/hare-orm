# Распределённые транзакции

`Transactions.distributed()` согласует записи в несколько баз PostgreSQL через двухфазную фиксацию.
Надёжно сохранённое решение координатора определяет, нужно ли фиксировать подготовленных участников
или откатывать их. После сбоя восстановление завершает это решение, когда базы снова доступны.
Записи становятся видимыми в каждой базе отдельно; единого одновременного снимка нескольких баз нет.

```python
class Transactions:
    @staticmethod
    def distributed(
        coordinator: str, participants: Sequence[str]
    ) -> AbstractAsyncContextManager[DistributedTransactions]: ...
```

Выдача книги записывается в базу библиотеки, экземпляр снимается с полки в базе склада, а залог читателя
— в базе расчётов: все три записи подчиняются одному решению о фиксации:

```python
from hare.query.expressions import F
from hare import Transactions

async with Transactions.distributed(coordinator="library", participants=["inventory", "billing"]) as distributed:
    await Loan.objects.using(distributed.coordinator).create(book_id=book.pk, reader_id=reader.pk)
    await Inventory.objects.using(distributed["inventory"]).filter(book_id=book.pk).update(
        available=F("available") - 1
    )
    await Deposit.objects.using(distributed["billing"]).create(reader_id=reader.pk, amount=5)
```

`distributed.coordinator` и `distributed[alias]` дают уже открытый клиент координатора и каждого
участника, чтобы передавать его как `using=`; `distributed[coordinator]` — тоже клиент координатора.
Протокол использует команды PostgreSQL `PREPARE TRANSACTION`/`COMMIT PREPARED`/`ROLLBACK PREPARED`.
Подготовленные участники сохраняют свои транзакции до фиксации или отката, в том числе после падения
процесса. [`on_rollback()`](transactions.ru.md#on-rollback) выполняет компенсирующее действие приложения.
Участник может оставаться подготовленным, когда фиксация в другой базе уже видна; восстановление
должно завершить оставшихся участников.

## <a id="how-the-commit-runs"></a>Как проходит фиксация

При обычном выходе из блока:

1. Каждый участник выполняет `PREPARE TRANSACTION`. При ошибке очистка пытается откатить всех участников
   и координатора, а исходное исключение передаётся дальше. Неудачный или неподтверждённый откат
   подготовленной транзакции требует восстановления.
2. Координатор обычным `COMMIT` записывает строку в свою таблицу `hare_distributed_decisions` (создаётся
   автоматически при первом использовании) вместе с записями блока в базе координатора.
   **Это надёжно сохраняет решение о фиксации**; участники после него должны зафиксироваться. Их записи
   не становятся видимыми одновременно. Отдельный внешний сервис координатора не требуется.
3. Каждому участнику отправляется `COMMIT PREPARED`. Если у кого-то это не удалось, решение о фиксации
   уже сохранено на шаге 2 — поэтому даётся
   `DistributedTransactionPartiallyCommittedError`, а не ошибка, будто не удалось всё; выполните
   `hare distributed-recover`, чтобы довести дело до участников, названных в исключении.

Если собственный `COMMIT` координатора на шаге 2 завершился с неизвестным исходом (соединение оборвалось
после того, как сервер его получил), даётся `DistributedTransactionCommitAmbiguousError`: каждый участник
всё ещё держит подготовленную транзакцию, и `hare distributed-recover` завершает их по записи о решении.
`COMMIT`, который точно не прошёл (база его отклонила или соединение оборвалось до отправки), решение тоже не
записал: очистка пытается выполнить `ROLLBACK PREPARED` для каждого участника и поднимает ошибку этого
`COMMIT`. Участник, чей откат не удалось подтвердить, остаётся задачей восстановления.

Исключение внутри самого блока (до шага 1) откатывает всё как обычно. Пустой `participants`, подключение,
указанное дважды (в том числе координатор среди участников), и подключение, уже находящееся в транзакции,
дают `QueryError` до того, как что-либо открывается. Пустое имя подключения (`""` или `None`) — это
подключение по умолчанию, как в `Transactions.atomic()`: такое имя среди участников называет
координатора, когда он и есть подключение по умолчанию, то есть подключение, указанное дважды.

Отмена во время `PREPARE TRANSACTION` у участника ждёт завершения защищённой операции в течение
ограниченного времени. Если подготовка подтверждена, очистка пытается выполнить `ROLLBACK PREPARED`;
при неизвестном исходе проверяет наличие подготовленной транзакции через новое соединение.
Истечение ожидания или недоступность сервера могут оставить исход неизвестным или транзакцию
подготовленной. После восстановления связи запустите `hare distributed-recover`: отмена не гарантирует
немедленный откат.

## <a id="databases"></a>Базы с двухфазной фиксацией

Она есть только в PostgreSQL: в SQLite и ClickHouse `PREPARE TRANSACTION` нет. Каждое подключение,
переданное в `distributed()`, — координатор и все участники — должно поддерживать двухфазную фиксацию
(`Features.supports_two_phase_commit`); иначе `UnSupportedError`.

## <a id="max-prepared-transactions"></a>Настройка сервера `max_prepared_transactions`

Во многих установках PostgreSQL по умолчанию `max_prepared_transactions = 0`, что полностью отключает
`PREPARE TRANSACTION`. `distributed()` в этом случае даёт `ConfigurationError` с именем подключения —
задайте ненулевое значение в `postgresql.conf` и перезапустите PostgreSQL. Когда же заняты все места
(«maximum number of prepared transactions reached»), `ConfigurationError` указывает на
`hare distributed-recover` и `pg_prepared_xacts` — места занимают оставшиеся подготовленные транзакции.
Любая другая ошибка `PREPARE TRANSACTION` передаётся как есть.

## <a id="recovering-stuck-prepared-transactions"></a>Восстановление зависших подготовленных транзакций

Если `COMMIT PREPARED` у участника не удался сразу (шаг 3 выше) или процесс упал посреди протокола,
`hare distributed-recover` находит и завершает такие транзакции:

```console
$ hare distributed-recover --coordinator library
$ hare distributed-recover --coordinator library --finish
$ hare distributed-recover --coordinator library --finish --older-than 60
```

Без `--finish` команда только сообщает, что нашла. Запись о решении без `resolved_at` означает, что
распределённая транзакция уже зафиксирована, — каждому участнику, у которого ещё висит эта подготовленная
транзакция, нужен `COMMIT PREPARED`. Подготовленная транзакция этого координатора без соответствующей
записи о решении считается отменённой: `ROLLBACK PREPARED`. `--older-than` (целое неотрицательное число
секунд, по умолчанию 300) пропускает всё, что ещё может выполняться в живом вызове; `0` ничего
не пропускает, что бы ни показывали часы сервера. Свежая запись о commit защищает от rollback
и участника, подготовленного раньше: восстановление предложит его commit, когда запись о решении
достигнет возрастного порога.
Повторный запуск безопасен.

CLI использует тот же сервис восстановления, который доступен приложению:

```python
from hare.transactions import DistributedRecovery

report = await DistributedRecovery.run("library", older_than_seconds=300)
report = await DistributedRecovery.run("library", finish=True, older_than_seconds=300)
```

`entries` содержит подготовленные транзакции, подходящие для восстановления. При `finish=True`
`attempts` хранит каждую запись и её `error` (либо `None`), `completed_xids` перечисляет завершённые
записи решений, а `decision_errors` содержит пары `(xid, error)` для ошибок обновления журнала.
Ошибка одного участника оставляет всё решение незавершённым. Следующий запуск заново проверяет,
каким участникам ещё требуется действие, и завершает старую запись решения, если все участники
успели завершиться до сбоя. Выполняйте восстановление с `finish=True` вне пользовательской
транзакции. Отмена прекращает следующие действия, но уже отправленное в базу действие могло пройти.

Завершение подготовленной транзакции инвалидирует метаданные схемы драйвера, в том числе при
восстановлении. Если её завершает временное подключение, исходный пул инвалидируется до его
закрытия: следующая команда ORM обновит метаданные изменений схемы, сделанных этой транзакцией.
