# Метки SQL-комментарием (`hare.instrumentation.QueryTags`)

Помечает каждый SQL-запрос, выполненный внутри блока, комментарием в конце в стиле
[sqlcommenter](https://google.github.io/sqlcommenter/). Главное применение — по тексту SQL из
`pg_stat_statements`/`auto_explain`/журнала медленных запросов найти место в приложении, откуда он
пришёл, без зависимости hare-orm от какой-либо системы трассировки.

```python
from hare.instrumentation import QueryTags

with QueryTags.scope(application="ops", job="sync_pending_widgets"):
    await Widget.objects.filter(status="pending").all()
    # SQL здесь заканчивается так: ... /*application='ops',job='sync_pending_widgets'*/
```

- Комментарий **добавляется в конец**, никогда в начало: комментарий в начале мешал бы кэшу
  запросов PostgreSQL, который опирается на начало текста, и путал бы инструменты, читающие только
  первые N символов запроса.
- Значения кодируются как в URL; ключи сортируются, поэтому один и тот же набор меток всегда даёт
  один и тот же текст комментария, в каком бы порядке его ни передали.
- Вложенные блоки не сливаются: блок `QueryTags.scope()` внутри другого добавляет к своим запросам
  только свои метки — метки внешнего блока снова действуют после выхода из внутреннего.
- Без активных меток `sql` возвращается без изменений (тот же объект) — в обычном случае без меток
  накладных расходов нет.
- Действует на каждый вызов, выполняющий запрос, включая DDL-сценарий через `execute_script()`:
  сценарий из нескольких запросов получает ровно один комментарий в конце, а не по одному на запрос.
- `QueryExecuted.sql` и `QueryCall.sql` содержат уже помеченный текст: метки добавляются до того,
  как запрос уходит в драйвер.

`QueryTags.set(tags)`/`QueryTags.reset(token)` — низкоуровневые примитивы, на которых построен
`QueryTags.scope()`, — для случаев, когда один блок `with` не может охватить всё время жизни меток
(например, через границу `await`, охватывающую несколько вызовов колбэков).
