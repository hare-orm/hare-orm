# Поиск повторяющихся запросов (N+1)

Детектор, который во время работы считает одинаковые по форме запросы одной единицы работы и
сообщает, когда их число в скользящем окне времени достигает порога. Это наблюдатель
`QueryExecuted`, поэтому никаких изменений в бэкендах ему не нужно.

```python
from hare.contrib.repeated_queries import RepeatedQueryDetector

detector = RepeatedQueryDetector(threshold=10, window_seconds=1.0, action="warn")
detector.start()  # один раз, при запуске процесса или приложения
...
detector.stop()

# или на время блока:
async with RepeatedQueryDetector(threshold=10, window_seconds=1.0):
    ...
```

```python
async def handle_job():
    RepeatedQueryDetector.reset_counts()  # новая единица работы — см. ниже
    ...
```

`start()` добавляет наблюдателя детектора на весь процесс (повторный `start()` того же детектора
ничего не делает, как и `stop()` незапущенного). Каждый детектор — отдельный экземпляр со своими
настройками и счётчиками: два детектора с разными порогами работают рядом. `detector.get_counts()` —
его счётчики в текущей единице работы: ключ формы → `ShapeStats(sql_sample, window_start, count)`
текущего окна этой формы.

Текст SQL каждого запроса — с местами для параметров, без самих значений — приводится к ключу «формы»
(`RepeatedQueryDetector.shape_key()` — только нормализация пробелов, без разбора) и считается по
формам в пределах единицы работы. Когда счётчик формы *достигает* `threshold` в пределах одного окна
`window_seconds`, `action` срабатывает ровно один раз на окно — а не на каждый следующий вызов — и
получает `RepeatedQueryReport(shape_key, count, threshold, window_seconds, sql_sample, call_site)`.
`call_site` — стек кода приложения, отправившего запрос, на котором порог был достигнут, до самого
внутреннего кадра вне hare: наблюдатель выполняется прямо в задаче, которая отправила запрос.

`threshold` должен быть `int` в диапазоне `1..REPEATED_QUERY_MAX_THRESHOLD` (1 000 000), а
`window_seconds` — конечным числом в `(0, REPEATED_QUERY_MAX_WINDOW_SECONDS]` (одни сутки). Иначе
(`threshold=0`, который никогда не сработает, или нулевое/отрицательное окно, при котором счёт
начинается заново на каждом запросе) при создании детектора поднимается `ConfigurationError`. Оба
предела лежат в `hare.contrib.repeated_queries.constants`. `action="warn"` (по умолчанию) пишет
предупреждение через `hare.core.log.logger.warning`; вместо этого можно передать функцию
(`Callable[[RepeatedQueryReport], None]`) — метрику или структурированное событие журнала.
Исключение из неё записывается в журнал и до запроса не доходит — чтобы тест падал на N+1,
проверяйте [`collect()`](#collect). Любая другая строка — `ConfigurationError`.

## <a id="units-of-work"></a>Единицы работы

Своего понятия «запроса» у hare-orm нет. Интеграции с [FastAPI](../integrations/fastapi.ru.md), [Litestar](../integrations/litestar.ru.md)
и [Robyn](../integrations/robyn.ru.md) вызывают `RepeatedQueryDetector.reset_counts()` в начале каждого запроса; в
остальных местах — в обработчике заданий, в цикле потребителя — вызывайте его в начале каждой единицы
работы, в задаче, которая её выполняет. С этого момента каждый детектор считает с нуля в этой задаче
и в запущенных из неё задачах, которые добавляют к тем же счётчикам. Без `reset_counts()` счёт
задачи начинает её первый запрос, поэтому у долгоживущей задачи счётчики растут через то, что вы
считали бы отдельными единицами.

## <a id="collect"></a>Подсчёт внутри блока: `collect()`

```python
RepeatedQueryDetector.shape_key(sql: str) -> str
RepeatedQueryDetector.collect() -> RepeatedQueryCollection

class RepeatedQueryCollection:  # `with` и `async with`
    total: int                                           # все посчитанные запросы
    entries_by_shape_key: dict[str, RepeatedQueryEntry]
    def __iter__(self) -> Iterator[RepeatedQueryEntry]   # в порядке первого появления
    def __len__(self) -> int                             # число различных форм
    def count_for(self, sql_or_shape_key: str) -> int    # 0 для невиданной формы
    def repeated(self, threshold: int = 2) -> list[RepeatedQueryEntry]  # самые частые первыми

@dataclass
class RepeatedQueryEntry:
    shape_key: str
    count: int
    sql_sample: str   # первый SQL этой формы
    call_site: str    # стек первого запроса этой формы, до самого внутреннего кадра вне hare
```

Считает запросы по формам для одного блока кода — «сколько одинаковых запросов сделал этот запрос
к API». Не требует ни детектора, ни `reset_counts()` и работает независимо от того, запущен ли
какой-нибудь детектор. Обычное применение — проверить, что у эндпоинта нет N+1:

```python
async with RepeatedQueryDetector.collect() as collection:
    await client.get("/books")
assert collection.repeated(threshold=2) == [], [entry.sql_sample for entry in collection.repeated()]
```

`collect()` наблюдает `QueryExecuted` через [`Observers.observing()`](observers.ru.md#where-observers-live),
поэтому подсчёт идёт синхронно в задаче, отправившей запрос: к выходу из блока каждый его запрос уже
посчитан (`wait_for_pending()` не нужен), а `call_site` указывает на настоящий кадр приложения.
`with` и `async with` ведут себя одинаково — вход и выход не выполняют ввода-вывода. Поведение:

- **Параллельные задачи**, у каждой свой `collect()`, никогда не видят запросов друг друга.
- **Вложенные блоки**: запрос во внутреннем блоке считается и во внутреннем блоке, *и* во всех
  внешних.
- **Дочерние задачи**, созданные внутри блока (`asyncio.create_task`, `gather` корутин, ...),
  наследуют контекст и тоже считаются — они работают от имени блока. Их запросы после выхода из
  блока не считаются.
- Один объект подсчёта нельзя войти повторно, пока он активен (`QueryError`); `repeated()`
  отвергает `threshold < 1` с `QueryError`.
- Выход в другой задаче, чем вход (например, асинхронная фикстура-генератор pytest, чей teardown
  выполняется в другой задаче), не вызывает ошибки: подсчёт закрывается, перестаёт считать, а его
  наблюдатель убирается из контекста задачи, которая выходит.

`shape_key()` — публичная нормализация, общая для обоих режимов (повторное применение ничего не
меняет, поэтому `count_for()` принимает и текст SQL, и ключ формы).

## <a id="the-sql-text-heuristic"></a>Эвристика по тексту SQL

«Форма» — это сам текст SQL с местами для параметров, а не какой-либо структурный ключ,
который hare-orm строит внутри. Это практичная эвристика, и на практике она работает хорошо: обычные
значения фильтров передаются параметрами, а не вписываются в текст SQL, и при кэшированной, и при
обычной сборке запроса, поэтому два вызова, различающиеся только значениями фильтров, дают одну
форму. Это касается и имени текущего часового пояса в операторах фильтра `__year`/`__month`/... вида
`EXTRACT(... AT TIME ZONE 'zone')`: оно, как и любое другое значение, попадает в итоговый SQL
параметром, поэтому два одинаковых фильтра с учётом часового пояса, выполненные при разных
настроенных поясах, здесь намеренно считаются *одной* формой. Массовая загрузка `COPY` считается как любой
другой запрос, по тексту `COPY <table> (<columns>) FROM STDIN` — по одному на партию, на N+1 он на
практике не похож.
