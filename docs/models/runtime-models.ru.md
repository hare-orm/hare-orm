# Модели, зарегистрированные во время работы

Класс модели, построенный, пока приложение работает, — например, по таблице, прочитанной из базы, —
регистрируется после `Hare.init()` и снова убирается без перезапуска.

```python
Hare.register_live_models(
    models: Iterable[type[Model]],
    app_label: str,
    connection_alias: str = "default",
    *,
    managed: bool | None = None,
) -> None
Hare.unregister_live_models(models: Iterable[type[Model]]) -> None
```

Оба принимают коллекцию классов моделей — одна модель передаётся списком из одного элемента.
Регистрирует подклассы `Model` **после** того, как `Hare.init()` уже выполнен, — для класса, который
появляется только во время работы (например, построен по схеме живой базы), а не объявлен заранее в
`apps` настроек. Нужен активный `HareContext` (иначе `ConfigurationError`) и `connection_alias`, который
действительно настроен (иначе `ConfigurationError` с этим именем); `ConfigurationError` будет и если
имя таблицы модели совпадает с уже зарегистрированной. `app_label` может быть любой строкой — не
обязательно одним из настроенных приложений.

Регистрация атомарна: если она не удалась (цель связи не найдена, имя обратной связи совпадает с
полем связанной модели и т. п.), модель не остаётся в реестре, ни одна связанная модель не сохраняет
добавленную ею обратную связь, а её `managed` и подключение восстанавливаются — исправьте класс и
зарегистрируйте его снова. Регистрация *другого* класса под именем, уже занятым в `app_label`, даёт
`ConfigurationError` — сначала вызовите `unregister_live_models()` для старого; повторная регистрация
того же класса ничего не делает.

`register_live_models()` регистрирует несколько моделей за один шаг — это нужно моделям, связи
которых указывают друг на друга (A → B и B → A): по одной их зарегистрировать нельзя (цели первой
ещё нет). Регистрация атомарна для всей группы: если не удалась хотя бы одна модель, не остаётся ни
одной. `unregister_live_models()` удаляет такую группу вместе — связи между удаляемыми моделями этому
не мешают.

Почти всегда используется с `managed=False` — иначе модель попытаются вести и `makemigrations`/
`hare drift`, споря с тем, кто на самом деле управляет её таблицей. `managed` записывается в
[`Meta.managed`](meta-options.ru.md) *до* настройки связей; `None` (по умолчанию) оставляет то, что
указано в собственном `Meta.managed` модели.

`unregister_live_models()` отменяет регистрацию: модель уходит из реестра, обратные связи (обратные
ссылки внешних ключей и «один-к-одному», созданные поля «многие-ко-многим»), которые она добавила
моделям, на которые указывают её связи, удаляются, и все кэши, построенные для неё или для этих
моделей, сбрасываются. Колонки её внешних ключей тоже сбрасываются, поэтому новый класс с тем же
именем — или тот же класс — потом можно зарегистрировать снова. Класс, регистрация которого
отменена, не может выполнять запросы (`ConfigurationError`). Отмена регистрации модели, на которую
ещё указывает другая зарегистрированная модель (внешний ключ, «один-к-одному», «многие-ко-многим»),
даёт `ConfigurationError` с именами ссылающихся полей и ничего не меняет — сначала отмените
регистрацию ссылающихся моделей. Связь модели с самой собой не мешает.

```python
from hare.inspectdb import DatabaseCatalog, ModelFactory

table_info = await DatabaseCatalog.inspect_table(connection, "orders")
Order = ModelFactory.from_table_info(table_info, connection.dialect.name, app_label="live")
Hare.register_live_models([Order], app_label="live", connection_alias="default", managed=False)
...
Hare.unregister_live_models([Order])
```

Чтобы прочитать несколько таблиц сразу, `DatabaseCatalog.inspect_tables(connection, ["orders",
"customers"])` возвращает по одному `TableInfo` на каждое имя в том же порядке — в PostgreSQL за
постоянное число запросов к системному каталогу, сколько бы таблиц ни было.

## <a id="building-a-model-from-an-introspected-table"></a>Модель по прочитанной схеме таблицы

```python
ModelFactory.from_table_info(
    table_info: TableInfo,
    dialect: str,
    *,
    app_label: str,
    foreign_key_target_overrides: dict[str, str] | None = None,
    skip_many_to_many_through_tables: bool = True,
) -> type[Model]
```

Строит класс модели для одной таблицы прямо через `type()` — это тот же класс, что получился бы при
выполнении кода, который создаёт для неё [`hare inspectdb`](../migrations/inspectdb.ru.md): оба пути
используют одно состояние модели (`hare.inspectdb.InspectedModelBuilder` превращает таблицу в тот же
`ModelState`, что есть у объявленной модели), поэтому поля, составные первичные ключи, индексы и ограничения не могут разойтись. Класс не
регистрируется — передайте его в `register_live_models()`.

- `app_label` — метка, которой уточняются цели внешних ключей, в том числе составных
  (`"<app_label>.<КлассЦели>"`); обычно та же метка, под которой вы регистрируете модель. Модели
  целевых таблиц должны быть зарегистрированы раньше.
- `foreign_key_target_overrides` — `{целевая_таблица: "app.Model"}`, полностью заменяет ссылку для этой
  таблицы; нужно, чтобы направить внешний ключ на уже зарегистрированную модель, имя класса которой
  не следует правилам именования `inspectdb`.
- `skip_many_to_many_through_tables` — таблица только из колонок внешних ключей похожа на промежуточную
  таблицу `ManyToManyField`; по умолчанию она отклоняется с `ManyToManyThroughTableSkippedError`
  (там, где генератор кода вставил бы комментарий `# NOTE`). `False` строит для неё обычную модель.

Таблица без первичного ключа и без уникального индекса по всем колонкам становится моделью с
`Meta.primary_key = None` (см. [Опции Meta](meta-options.ru.md#primary_key)).
